# catalog-engine / parse_gate.py

**Revision:** 1
**Last modified:** 2026-10-27T13:40:00Z

## Overview

`scripts/catalog-engine/lib/parse_gate.py` turns a project's pre-build verification script into one
test-catalog record per `CM-*` gate (type `pre-build-gate`), and exposes the same recognition to other
tools (the pairing audit) through a small command line, so that **no two consumers can disagree about
which gates exist**. It is project-agnostic: it contains no helper name, only structure.

## The three registration forms

| Form | What it looks like | Record `wiring_form` | Description comes from |
|---|---|---|---|
| F1 echo banner | `echo -n "  CM-X: what it checks... "` | `echo-banner` | the banner text |
| F2 wrapper call | `<helper> "CM-X" "desc" ...` where `<helper>` is a shell function whose body prints the verdict from its first positional argument (`echo -n "  ${lbl}: ${desc}... "`, `log_pass "${tok}: ..."`) | `wrapper-call:<helper>` | the argument the banner prints after the label (when there is one); otherwise empty with the honest gap `no-gate-description` |
| F3 verdict line | `log_pass "CM-X: text"` / `log_fail "CM-X: text"` with no F1 banner | `log-verdict` | the verdict text |

Precedence per gate id is F1 > F2 > F3; within a form the first occurrence wins. Adding F2/F3 therefore
never changes an F1 record. Wrapper functions are **detected from their bodies**; a function counts when its
body prints a verdict whose label variable is bound from `$1` (`local lbl="$1"`). One-line definitions
(`f() { ...; }`) are read as their own body; an unclosed body stops at the next sibling definition.

Why: before ATM-1473 only F1 existed, so every gate registered through a helper was invisible to the catalog
(82 `_r5_run_gate` names, 0 catalogued), and the pairing audit's literal token scan could not see them either.

## Command line

```bash
python3 -I scripts/catalog-engine/lib/parse_gate.py --selftest            # golden-good + golden-bad + negative controls; exit 0 GREEN / 1 RED
python3 -I scripts/catalog-engine/lib/parse_gate.py --wrapper-ids FILE    # F2 gate ids, one per line (exit 2 on IO error)
python3 -I scripts/catalog-engine/lib/parse_gate.py --verdict-ids FILE    # F3-only gate ids
python3 -I scripts/catalog-engine/lib/parse_gate.py --unrecognised FILE [--exempt a,b]   # exit 1 if any helper shape is unrecognised
python3 -I scripts/catalog-engine/lib/parse_gate.py --report FILE         # detected wrappers and per-wrapper gate counts
```

## The blind-spot guard

`--unrecognised` lists every line-leading `<ident> "CM-X"` call whose `<ident>` is defined as a function in the
file (or has a gate-like name) but is **not** a detected wrapper. A non-empty list means a gate registration the
catalog and the pairing audit cannot see. Resolve it by making the helper print its verdict from its first
positional argument, or exempt the ident with a recorded reason (a helper that only takes a CM-* string as data).
Scope limit, stated honestly: only a call whose **first** argument is a quoted `CM-*` name is in scope; a helper
defined in a sourced file under a name that neither matches the file's functions nor looks gate-like is outside it.

## Effect on the catalog fingerprint

`generate_catalog.py` derives the corpus fingerprint from the sorted **distinct source paths** of the records,
not from record count or content, so recognising more gates in an already-scanned file does not change the
fingerprint (`CM-TEST-CATALOG-FRESH` is unaffected); the derived `catalog.json` / `Catalog.md` do change and are
regenerated by the committer with the sanctioned generator.

## Tests

not register), four refusal fixtures, CLI exit-code checks, eight paired mutants of the parser that must each be
killed. `GATE_FILE=<gate file>` additionally asserts that the catalog covers every F2/F3 call site of that file.
