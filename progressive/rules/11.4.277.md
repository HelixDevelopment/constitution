### §11.4.277 — llmctl model validation gate: every model run through llmctl (Vision included) by a project or any of its components / services / submodules (recursively) passes deterministic known-answer validation BEFORE decision-bearing use; decision-bearing use runs with `LLMCTL_VALIDATE_STRICT=1` and gates on `llmctl require-validated <profile>`; models are acquired and run ONLY through the constitution-vendored llmctl (`submodules/llmctl`); a wrong answer means the model or runtime is defective and is investigated, never retried-until-green; llmctl units are host-safe by construction (User mandate, 2026-10-12)

**Forensic anchor — operator mandate (2026-10-12, paraphrased from the intake; the verbatim text is in the consuming project's request-history record per §11.4.208/§11.4.210):** every model that is run through llmctl, Vision models included, and that the project or ANY of its components / services / submodules (recursively) uses MUST first go through deterministic validation and verification; for Vision, screenshots whose content is KNOWN are prepared IN ADVANCE and the model's answers are compared with the expected answers; a wrong answer means the model / runtime is defective and MUST be investigated and fixed.

**Reference implementation (named once, so every "llmctl does X" below is checkable).** llmctl is vendored into this constitution as the submodule `submodules/llmctl` (SSH url `git@github.com:vasic-digital/llmctl.git`), pinned to the tag `v3.2.2` (commit `5c3dea57fb35215cdaa4b7412da438e7a8d96d86`) and listed in `helix-deps.yaml` (§11.4.31). Every statement below that describes llmctl describes THAT pin, read from its source (`lib/validate.sh`, `lib/validate_judge.py`, `lib/hardware.sh`, `lib/service_linux.sh`, `lib/svc_hook.sh`, `validation/suites/`); a later pin may differ, and a consumer that bumps the pin re-reads this clause against it (§11.4.26). Values marked "reference value" are what llmctl v3.2.2 ships (`git diff v3.2.1 v3.2.2` touches none of `lib/validate.sh`, `lib/validate_judge.py`, `lib/hardware.sh` or `validation/`, and the `lib/service_linux.sh` edits are comments only, so the gate, pressure-gate, suite and unit-template values are the same as in v3.2.1; the v3.2.2 code change that bears on this clause is named under (A.1)); they are HOST-DEPENDENT calibrations of a mechanism, not constants of this constitution, and a consumer MAY be stricter but never looser. The models and profiles llmctl selects are likewise decided per host from that host's measured capabilities (`llmctl plan`, catalog tiers); this clause names no model as mandatory and a profile passing on one host says nothing about any other host.

**Forensic FACTS — host incident, 2026-10-12 (genericised; full citations in the consuming project's own continuation record).** A llmctl-managed systemd unit carried `Restart=always`, `RestartSec=5` and a `MemoryMax` EQUAL to the host's total RAM. The unit was OOM-killed 8 times in about one hour; every restart re-read roughly 3.3 GB of model files from disk. Observed on the host: load average about 160, kernel CPU time 85–98 %, memory PSI `full` 97–99 %. The host stalled and was force-powered-off by the operator. Root-cause chain (measured, not assumed): (1) no restart bound, so a deterministic failure became an infinite re-read loop; (2) a memory ceiling equal to total RAM, so the cgroup limit never protected the host; (3) no pre-flight pressure check, so a start was attempted on an already-stressed host; (4) nothing stopped a second model from being loaded beside the first. This is the class §12.3 (container hygiene), §12.6 (memory ceiling) and §12.12 (process/thread limits) already forbid; (E) below makes it binding on llmctl units in particular and records the values with which llmctl v3.2.2 closes it.

**What this is NOT (the §11.4.227 boundary).** It does not replace §11.4.107 / §11.4.117 / §11.4.163 (analyzer self-validation, pixel oracle, media validation); it VALIDATES the model those analyzers depend on. It does not replace §11.4.160 (HelixQA frame bridge); it is the precondition the bridge's vision step must satisfy. It does not replace §12.6 / §12.12; it adds llmctl-unit-specific obligations on top. It adds no new escape hatch to any of them.

**The mandate (ALL hold):**

**(A) VALIDATION GATE — UNDETERMINED IS NEVER A PASS.** A model is NEVER used by any project component for a decision that feeds a verdict, a gate, a recording check, a translation, a review or any user-visible output ("decision-bearing use") until `llmctl require-validated <profile>` exits 0, i.e. the profile holds a FRESH PASS record for the model, engine and launch it is actually running as. "Used by a component" is recursive over submodules (§11.4.28): a consumer inherits the obligation for every model any vendored submodule runs. Decision-bearing use MUST run with `LLMCTL_VALIDATE_STRICT=1` (the reference gate then also stops a profile whose validation is UNDETERMINED) AND MUST gate on `llmctl require-validated <profile>` before each such use; `LLMCTL_VALIDATE_ON_START=0` exists for explicit, human-attended diagnostics only — a profile started with it is not validated and `require-validated` refuses it, unless a fresh PASS record for the same key (model, engine, launch, suites, age) already exists. A profile that names no validation suite is never reported as validated. Use of an unvalidated model is a §11.4.277 violation at the evidence layer even if every downstream test is green.

**(A.1) Reference gate semantics (llmctl v3.2.2).** (1) Exit codes of `llmctl validate`, `llmctl vision validate` and `llmctl validate-all`: `0` every check passed; `1` any WRONG result (never excused, never loosened; `1` outranks `2`); `2` could not determine (not downloaded, not served, endpoint down, no suite, insufficient resources). `75` is the pressure-gate refusal code (`hw_pressure_gate`); `llmctl validate` maps a refusal to `2` (UNDETERMINED, nothing recorded as a FAIL), because a refusal is not a verdict. `98` is "port already in use": it is produced by the unit's `ExecCondition` portcheck skip and, in the v3.2.2 pin, by the onnx server (`lib/onnx_server.py`) when its bind fails with EADDRINUSE (a main-process exit, which `RestartPreventExitStatus` does cover; before v3.2.2 that server exited `1` and was retried into the start limit); UNKNOWN (§11.4.6): the exit status of a `llama-server` bind failure, since the v3.2.2 source sets `98` only in the portcheck and the onnx server; systemd tests `RestartPreventExitStatus` against the MAIN process only (see (E)). A judge crash that exits `1` without the judge's explicit `VERDICT: FAIL` is treated as UNDETERMINED, never as a wrong answer. `llmctl require-validated <profile>` exits `0` only for a fresh PASS record, `1` when the profile is not validated (reasons listed), `2` for an unknown profile or an uncomputable key. (2) Enforced, not advisory: after `start`, `switch`, `auto`, `enable` and `restart` the post-start hook runs each running profile's suites unless a fresh passing record already covers it; FAIL (1) STOPS the profile through the normal stop path and the command exits non-zero; UNDETERMINED (2) does not stop it unless `LLMCTL_VALIDATE_STRICT=1`, in which case it stops it. (3) The systemd path: units started by systemd (boot, `Restart=`, restart) are validated by the unit's post-start waiter ONLY when the port registry is active and ONLY for catalog LLM profiles (a scaled instance `<profile>.<N>` has no catalog entry of its own and is covered by its base profile); outside that scope the gate does not run, so a consumer MUST NOT assume a systemd-started unit was validated — it asks `require-validated`. (4) `llmctl validate <profile> --host URL` validates an external endpoint as EVIDENCE ONLY and never records local state.

**(B) ACQUIRE AND RUN ONLY THROUGH THE VENDORED llmctl.** Models are fetched, verified, installed, started and stopped ONLY through llmctl as vendored in `submodules/llmctl` (§11.4.74 catalogue-first / extend-don't-reimplement; §11.4.76 / §11.4.161 for any container leg). Ad-hoc `llama-server` invocations, hand-written unit files, manual `curl`-downloaded GGUFs, or per-project re-implementations of model management are forbidden. A missing llmctl capability is added to llmctl itself and propagated via §11.4.26 (a pin bump, never a local fork, §11.4.251). Download sources, catalog checksums and licences are recorded; a downloaded file whose SHA256 does not match the catalog value is deleted (the catalog allows a null `sha256` for small non-LFS config files; llmctl then records `none` and no checksum is claimed for that file) and the profile is not validated (§11.4.270 existence-verdict discipline applies to the model as a dependency). Credentials (model-hub tokens) follow §11.4.10: never in a repo, never printed. OPERATOR DECISION (explicit): llmctl vendors this constitution as its own `constitution` submodule, so vendoring llmctl here creates a mutual reference. It is kept as a depth-1 hub entry that consumers MUST NOT initialise recursively (`git submodule update --init submodules/llmctl` WITHOUT `--recursive`); `helix-deps.yaml` carries the non-recursive marker `recursive_init: false`. The cycle is finite only because llmctl's own `constitution` pin (`4091798`, as of the v3.2.2 pin; it was `3e8e855` at v3.2.1) is a commit that contains no `submodules/llmctl`; bumping that pin to a commit that does contain it MUST be refused, and `CM-LLMCTL-SUBMODULE-NONRECURSIVE` (implemented) fails on a missing marker or on such a pin. The gate reads the llmctl commit RECORDED in this repo for `submodules/llmctl` (falling back loudly to the checked-out HEAD only if that commit is unresolvable), inspects the own-org submodules that commit pins (`constitution` and `submodules/containers`), and fails when a pin's tree has an entry named `llmctl` at ANY path or its `.gitmodules` names this constitution or llmctl, reporting the path; an unresolvable pin is BLIND (exit 2).

**(C) VISION KNOWN-ANSWER VALIDATION.** For every Vision-capable model: (1) a FIXTURE CORPUS of screenshots with KNOWN content is prepared IN ADVANCE, before the model is ever run against it (the order is recorded: the expectation manifest's commit precedes the first validation run); fixtures are rendered or captured from controlled sources so the truth is known by construction, not by reading the model's answer; (2) a machine-readable EXPECTED-ANSWER MANIFEST (one record per fixture: fixture id, SHA256, the question(s), the closed expected answer(s) or required / forbidden substrings / numbers, and the reason the answer is known) is committed alongside; (3) the corpus covers, at minimum, every class of content the CONSUMER's own screens depend on, and includes NEGATIVE controls whose correct answer is "not that" (a blank frame, a frame with the wrong content) — a class the corpus does not cover is a class the model is NOT validated for, and the consumer says so; (4) the run is DETERMINISTIC: temperature 0, fixed seed, top-k 1, no prompt cache, with the exact model + `mmproj` identity and the exact engine build recorded in the key (H); (5) every answer is judged by a mechanical judge (normalised substring / ordered / forbidden / first-number / regex / JSON checks) — never by another model, never by eyeballing (§11.4.262(C)); (6) the judge is itself self-validated against known-good / known-bad canned answers BEFORE any request is sent (§11.4.107(10)): a judge that accepts a deliberately wrong answer is the bluff; (7) REPEATABILITY: the suite includes determinism repeats whose answers MUST be identical; the reference value is ONE repeat (`determinism_repeat` of `vision-golden-v1` lists one probe) and a consumer MAY — and for decision-bearing Vision use SHOULD — require more repeats; a non-deterministic answer under pinned settings is itself a defect finding (runtime nondeterminism, GPU kernel race, or an unpinned input), not noise to average away.

**(C.1) What the reference suite `vision-golden-v1` actually is (honest coverage, llmctl v3.2.2).** 11 generated fixtures: 9 golden fixtures carrying 16 probes (large text, shape counting, a login form, a list view, a table, a dialog, a dark theme, small text, colour blocks) and 2 golden-bad control fixtures (blank, wrong content) carrying 2 control-self probes, which must NOT be answered as the golden content; 1 determinism-repeat probe; 19 judge self-test entries (reported separately from the 21 probe-level results). The 21 results of each of the two recorded live runs (same host, same day) decompose as 16 golden probes + 2 control-self probes (the golden-bad fixtures' probes) + 2 discrimination controls (the golden-bad answers must differ from the golden answers named in the fixtures' `discriminates` field) + 1 determinism repeat. Fixtures are generated by a stdlib-only, byte-reproducible script with an embedded 5x7 bitmap font. It makes NO claim about CJK or right-to-left scripts, photographic content, real application screenshots, other fonts or resolutions, or any class not in the list above; a consumer whose screens depend on such a class adds fixtures and a manifest for it (suite content is hashed into the record, so a changed suite voids earlier records). The other suites llmctl ships are `chat-v1`, `coder-v1` and `embedding-v1`.

**(D) WRONG ANSWER = DEFECT, INVESTIGATED NOT RETRIED.** A fixture answered wrongly means the model, the quantization, the `mmproj`, the prompt template, the image preprocessing or the engine build is defective for this use — until proven otherwise by evidence. The response is §11.4.102 root-cause investigation with a §11.4.115 RED baseline on the broken artifact (reproduce the wrong answer from a fresh process, record it), then a fix that changes the actual cause (a different quant, a correct `mmproj` pairing, an engine upgrade/patch via llmctl, a chat-template correction), then re-validation from the clean baseline (§11.4.4). FORBIDDEN: retrying until green, raising temperature, re-seeding to find a passing seed, lowering the pass threshold, dropping or softening the failing fixture, widening the manifest's accepted answers after seeing the output, swapping the judge, or marking the model "advisory" and using it anyway (§11.4.269 critic-advisory-only does not apply: an unvalidated model is not usable at the evidence-acceptance point at all). The pass bar is 100 % of non-quarantined probes; a probe may be quarantined only through a §11.4.271 waiver with a tracked item (§11.4.197) and never for a class the consumer's own screens depend on.

**(E) HOST-SAFETY CLAUSE (binding on every llmctl unit and on every validation run).** The mechanism is mandatory; the numbers are the llmctl v3.2.2 reference values and are HOST-DEPENDENT (consumers MAY be stricter, never looser).
1. **Bounded restarts.** Every llmctl unit carries `Restart=on-failure` with a growing delay (reference: `RestartSec=5`, `RestartSteps=4`, `RestartMaxDelaySec=120`), `StartLimitBurst=3` and `StartLimitIntervalSec=900` placed in `[Unit]` (systemd ignores `StartLimitIntervalSec` in `[Service]`), and `RestartPreventExitStatus=SIGKILL SIGTERM 98`: a SIGKILL (the OOM-kill signature), a deliberate stop (SIGTERM) and exit 98 (port already in use; see (A.1) for where it comes from — `RestartPreventExitStatus` applies to the main process only) are NEVER auto-restarted where it applies, because each only repeats itself. `Restart=always`, or any fixed short `RestartSec` loop, is FORBIDDEN. A unit that exhausts its start limit stays failed (until `reset-failed`) and the crash-loop condition is surfaced in `llmctl status`; it never self-resets silently. Composes §12.3(3).
2. **Memory ceilings well below host RAM.** Every engine unit carries `MemoryHigh` and `MemoryMax` strictly below total RAM and `MemorySwapMax=0` (a model that swaps is a stalled host, not a slow model). Reference derivation: each profile gets its own drop-in with `MemoryHigh` = 1.25x and `MemoryMax` = 1.5x of the profile's plan footprint (provenance `measured` where a live run has measured it, otherwise the catalog's declared figure), floors High 1024 MiB / Max 1280 MiB, and for a GPU-mode profile whose footprint is not yet measured a floor of High 5120 MiB / Max 6144 MiB (the declared RAM figure is then a placeholder, not a measurement), always below 90 % of total RAM; a unit whose drop-in is missing falls back to a template backstop below total (High 70 % / Max 85 %). A `MemoryMax` equal to or above total RAM is a defect. The caps are calibrated by MEASUREMENT: the one measured data point on record is a single host, run 2 of 2 of the `vision` catalog profile (run 1 did not record the unit's memory), peak 3005 MiB (unit `MemoryPeak` 3151007744 B) against the 5120/6144 MiB floors — committed in llmctl at the `v3.2.2` tag as `docs/qa/vision-live-2026-10-13-run2/` (`cgroup_peak.txt`, `verdict.txt`); it is evidence about one host and one profile, not a constant, and the floors were not changed by it.
3. **Pre-flight pressure gate — refuse, do not start.** Before ANY start or restart of an ENGINE unit (its `ExecStartPre` gate, so systemd restarts and boot starts are gated too; the gate WAITS up to `LLMCTL_GATE_WAIT` = 120 s, polling every 5 s, for the pressure to clear before it refuses), before `sched_start` / `enable`, and before a validation run starts a profile, llmctl refuses with exit `75` and a recorded "refused" message, with NO partial start, when memory PSI `some` avg10 > 10, or `full` avg10 > 2, or `MemAvailable` < the profile's footprint + 4 GiB (reference values; overridable for tests by `LLMCTL_GATE_SOME_MAX` / `LLMCTL_GATE_FULL_MAX` / `LLMCTL_GATE_RESERVE_MB`; a missing PSI file skips only the PSI test). Validation re-checks PSI after the model has loaded and before the first probe, and stops a profile it started itself if the host has since become stressed. `switch` runs a PSI-only pre-stop gate (reserve 0) BEFORE anything is stopped, so a refused switch leaves the running set untouched, and then `_sched_start_impl` still applies the normal footprint gate (memory PSI + `MemAvailable` ≥ footprint + 4 GiB) to the target. The decision-gateway unit is NOT an engine unit: it has no `ExecStartPre` pressure gate and is bounded by its own caps of 20 % / 25 % of RAM (capped at 3 / 4 GiB), not by the per-profile rule in (2). The reference gate reads memory PSI and `MemAvailable` only; I/O PSI, swap-in rate and load-average bounds are consumer-optional additions and NOT claimed by llmctl v3.2.2. The 2026-10-12 values (PSI full 97–99 %, load ≈ 160) are the forensic case, not a threshold.
4. **Co-residency is a budget, not a count.** llmctl admits a start only when the COMBINED footprint of the profile and everything already reserved fits the host's live RAM and VRAM budgets (scheduler reservations; `auto` may evict non-enabled services LRU-first; `switch` stops everything and starts one). On a host whose budget fits one model, exactly one model is resident; a start that does not fit is refused, not queued silently and not co-loaded. The budgets are host data, never a literal of this clause. Validation runs are serialised with production use of the same resource (§11.4.119).
5. **Never on a stressed or recovering host.** After a host crash / forced power-off the first action is the §12.3(4) clean-slate check; a unit enabled for boot still passes the pre-flight gate (4) before it loads a model, and nothing in this clause authorises any power-state transition (CONST-033).
6. **Resource limits on validation itself.** A validation run is subject to §12.6 / §12.12, the build-concurrency caps carried in the consumer manuals and the 30–40 % test-resource rule; it is never run in parallel with another heavy workload (build, other model, container storm) on the same host.

**(F) EVIDENCE — what exists and what is owed.** llmctl v3.2.2 appends per validation run to `${LLMCTL_VERIFY_DIR}/validate-<profile>.log` (mode 0600): the key, the endpoint (redacted), every probe's raw model answer, the expected checks and the per-probe verdict; the machine-readable record is `${LLMCTL_STATE_DIR}/validation/<profile>.json`. The consumer's evidence tree (`docs/qa/<run-id>/model-validation/`, §11.4.83) additionally preserves, per §11.4.5 / §11.4.69 / §11.4.262: the exact command line, the SHA256 of the model / `mmproj` / each fixture / the engine binary, the build flags, the pre-flight PSI / memory reading and a host-class fingerprint (GPU model + VRAM + driver/CUDA + OS + kernel). UNKNOWN (§11.4.6): llmctl v3.2.2 does NOT hash-chain its evidence log (§11.4.268) and does not record the host-class fingerprint; both are consumer obligations until llmctl gains them, and a consumer that has not implemented them says so rather than claiming the chain.

**(G) OTHER MODEL KINDS.** The same gate applies to every non-Vision model run through llmctl, each with its own known-answer suite declared BEFORE the run. llmctl v3.2.2 ships suites for chat, coder and embedding models (`chat-v1`, `coder-v1`, `embedding-v1`; its shipped catalog has no embedding profile, so that suite is exercised there by a fixture profile only); every other kind (speech-to-text with a WER bound, text-to-speech round-tripped through a self-validated STT, reranker ordering, translation engines — content stays under §11.4.255 / §11.4.256) needs its own closed-form oracle supplied as DATA. Where a kind has no closed-form oracle the consumer MUST say so explicitly as `UNKNOWN` / `PENDING_FORENSICS`, and the model stays unvalidated for decision-bearing use (§11.4.6, §11.4.123).

**(H) WHAT THE RECORD BINDS, AND RE-VALIDATION.** The llmctl v3.2.2 record binds, and `require-validated` re-compares on every call: (1) `model_sha256` — a hash of the catalog's declared file names and their catalog SHA256 values (`none` where the catalog declares null; the `mmproj` file is one of those catalog files, so a changed `mmproj` entry changes it); (2) `model_files` — name, size and mtime of each file on disk (NOT a re-hash of the bytes; byte-level checksums are `llmctl models verify`'s job and the on-disk size/mtime is only a change detector); (3) `engine_tag` — for the llama engine the `llama-server --version` line (`build N, commit X`) only; for colibri the submodule commit; for onnx a hash of the server script; (4) `launch_fingerprint` — SHA256 of the unit's executable and arguments with `--host` / `--port` removed, so sampling, context and batch arguments present in argv are bound; (5) each suite's content hash; plus `status`, `epoch` / `timestamp` and the evidence path. The record is void — `require-validated` refuses — when ANY of these differ from the current key, when the record is not a PASS, when it has no usable epoch or is stamped in the future, or when it is older than `LLMCTL_VALIDATION_MAX_AGE` (reference value 604800 s = 7 days; a consumer SHOULD tighten to at least once per release candidate, §11.4.40). NOT bound by the record (UNKNOWN as to any later pin): host class (GPU model, VRAM, driver / CUDA version, OS, kernel), engine build flags beyond the version line, an externally-supplied chat template, and quantization other than through the file identity. A consumer's validation record therefore MUST bind those in addition (or record them as an explicit gap) and a change of any of them voids its record: a fresh validation is REQUIRED, never "carried over".

**(I) PER-HOST VALIDATION RECORD.** The llmctl record lives in the host's own state directory, so validation is per host by construction, not global: a model validated on host A is NOT thereby validated on host B, and `llmctl validate --host URL` against another machine's endpoint is evidence only, never that machine's record. The consuming project keeps a record of which {model identity × host} pairs are validated — first for the current host, then for each remote workstation it uses, reached over SSH with key-based authentication already provisioned on the host (never passwords, never keys or tokens committed, §11.4.10; remote commands run llmctl on that host, through the same pre-flight and limits, and remote access obeys §12.12 and §11.4.263). A remote host that cannot be reached, or whose pre-flight refuses, is recorded `not_validated: <reason>` and the dependent checks SKIP-with-reason per §11.4.3 (never a faked PASS). UNKNOWN (§11.4.6): llmctl v3.2.2 has no cross-host record store; the set of remote workstations and their capabilities is supplied by the consumer as data.

**(J) CONSUMER ADOPTION (§11.4.35).** The consuming project declares as DATA: its model inventory (profile, purpose), the fixture-corpus and manifest paths for any suite it adds, the number of determinism repeats, any pressure / memory thresholds it tightens, the maximum record age, the remote-host list, and the evidence location. The first consumer expected to adopt feeds its Vision model into the §11.4.278 HelixQA "eyes".

**Honest boundary (§11.4.6).** Validation shows the model answers the declared fixture set correctly under pinned settings on the validated host, on the evidence available at the time: llmctl v3.2.2's own evidence for the Vision gate is TWO live runs (both 2026-10-13, on ONE host, committed as `docs/qa/vision-live-2026-10-13/` and `docs/qa/vision-live-2026-10-13-run2/`) of the `vision` catalog profile, each pass=21, fail=0, undetermined=0 (21 = 16 golden + 2 control-self + 2 discrimination controls + 1 determinism repeat, with the judge self-test 19/19 reported separately, see (C.1)); `vision-pro` and every other profile were not run and remain not validated, and variation across hosts, profiles and further runs is UNKNOWN. It does NOT prove correctness on screens or inputs outside the corpus (that is §11.4.118 discovery-pressure plus the §11.4.278 per-screen oracles), does NOT prove the model is safe or licensed for every use, and does NOT make a Vision answer a substitute for a deterministic oracle where one exists (§11.4.117 pixel/OCR oracle and the accessibility tree stay primary; the model corroborates). The host-safety clause bounds the observed failure mode; it does not guarantee a host cannot stall for reasons outside llmctl.

**Classification: universal (§11.4.17)** — no vendor, hardware, model or project literal is mandated; llmctl's reference values are host-dependent calibrations and the consumer supplies fixtures, thresholds, host classes and paths as DATA per §11.4.35.
