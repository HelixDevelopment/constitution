### §11.4.293 — Scope discipline and image no-worse proof: all work serves the main Roadmap's workable items and stays inside the codebase context of the issue it fixes, every commit names the Roadmap item it serves and every out-of-scope edit carries a reason from a closed list; every produced flashing image is LIVE-tested and compared, test by test, with the previously flashed image's baseline run on the same board and harness, and only the closed verdict NO-WORSE-PROVEN lets it be released or tagged as no worse (User mandate, 2026-11-03)

**Forensic anchor — operator addendum (2026-11-03 16:45, CRITICAL), as relayed by the conductor in the operator's words of intent (the operator's own message is not quoted here):** "(A) SCOPE DISCIPLINE: all work focuses on the main Roadmap's workable items; every change must stay strictly inside the codebase context of the issue being fixed, with as few changes outside that context as possible; each commit/patch names the Roadmap item it serves and out-of-scope edits need a recorded justification [...] (B) IMAGE NO-WORSE PROOF: every produced flashing image MUST be LIVE tested, validated and verified deterministically against machine-produced evidence, including evidence that the new image does not work worse and does not have more issues than the previous image created [...] every next image except one that is purely new features MUST be MORE STABLE [...] No bluff: INCONCLUSIVE never counts as no-worse; a test that was PASS on the baseline and is INCONCLUSIVE/SKIPPED/absent on the new image is a regression."

**The gap this anchor closes (stated so it is not restated elsewhere, §11.4.227).** §11.4.58 gives a parallel work unit a file-scope manifest and §11.4.191 binds a logical group's work to its track; neither binds every commit to a named Roadmap item nor refuses an unexplained edit outside the issue's codebase context. §11.4.40 requires a full-suite retest before a tag; §11.4.114 makes the last known good the oracle when a regression is reported; §11.4.135 keeps a standing regression-guard suite and refuses a release without verdicts for it; §11.4.236 gates the QA hand-off on a candidate-fingerprinted PASS; §11.4.200 verifies the flashed image on the intended board. None of them compares the new image's per-test LIVE verdicts with the previous flashed image's verdicts on the same board and harness, none defines the closed no-worse verdict, none requires each bug-fixing image to be more stable than the one before, and none says that a test that PASSed on the baseline and is INCONCLUSIVE, SKIPPED or absent on the new image is a regression. This anchor adds exactly those and restates none of the others.

**(A) SCOPE DISCIPLINE.** (1) FOCUS: all work serves a workable item of the consuming project's main Roadmap (the roadmap the project declares as DATA, §11.4.35). Work that serves no Roadmap item is first reported as one (§11.4.202) and placed on the Roadmap, or it is not done; an operator order is recorded (§11.4.210) and is its own justification. (2) CONTEXT: every change stays strictly inside the codebase context of the issue it fixes: the files, modules and surfaces named by the item's scope (§11.4.148 description, §11.4.58 file-scope manifest) and the tests that cover them. Edits outside that context are as few as possible, and an edit that improves code unrelated to the item is a separate item, never a rider. (3) EVERY COMMIT OR PATCH NAMES ITS ITEM: a `Roadmap-Item: <id>` trailer (one per item served; the consumer may declare another field name as DATA) names the Roadmap item or items it serves. (4) OUT-OF-SCOPE EDITS CARRY A RECORDED REASON FROM A CLOSED LIST: every path the commit touches outside the item's context is listed in an `Out-of-scope: <path> — <reason> — <justification>` trailer, where `<reason>` is exactly one of `fix-gate-or-test` (a gate or test the fix itself needs), `generated-regeneration` (a generated file regenerated by its own generator, §11.4.77), `upstream-merge` (a merge of upstream, §11.4.288), `operator-order` (an operator order, with the id of its record, §11.4.66). There is no fifth reason. An out-of-scope path with no trailer, or with a reason outside the list, is a scope violation; it is split into its own item or reverted before the change lands.

**(B) IMAGE NO-WORSE PROOF — the comparison.** Every produced flashing image (an image written to a board: system, boot, vendor or a full update package) is LIVE-tested, validated and verified deterministically against machine-produced evidence (§11.4.289, §11.4.262, §11.4.50) on the physical board after the flash is verified on the intended target (§11.4.200). The evidence includes a COMPARISON of the new image's per-test LIVE verdict set with the BASELINE: the run of the previously flashed image (the image this board carried and was validated with before the new one) on the SAME board (board serial), with the SAME harness (harness version or fingerprint), the SAME suite (the same test-id set definition) and the SAME command. Both runs record their image identity (version and the sha256 of every flashed image file) and are machine-written (§11.4.262). Each per-test verdict is the deterministic verdict of the declared number of runs (§11.4.50), from the closed set `PASS` / `FAIL` / `INCONCLUSIVE` / `SKIPPED` / `BLIND` / `ERROR`; any other value counts as not PASS. A test the baseline ran and the new run does not report is `absent`, and absent is not PASS.

**(C) THE VERDICT — closed set, three values.**

| Verdict | Holds when | Release and tag |
|---|---|---|
| `NO-WORSE-PROVEN` | a baseline exists that matches clause (B), AND no test that was `PASS` on the baseline is anything but `PASS` on the new image, AND the new image's count of not-PASS verdicts over the baseline's test set is not higher than the baseline's, AND every targeted issue flipped RED to GREEN with evidence (clause (D)) | allowed, subject to every other seam |
| `REGRESSED` | a matching baseline exists and any condition of `NO-WORSE-PROVEN` fails; the record names each failing condition with a reason code from `baseline-pass-lost`, `issue-count-higher`, `targeted-flip-missing` | refused (clause (F)) |
| `INCOMPARABLE-BASELINE-MISSING` | no baseline matching clause (B) exists, or either run lacks a recorded image identity, board serial, harness fingerprint, suite definition or command | a blocker, never a pass (clause (F)) |

There is no fourth verdict. INCONCLUSIVE never counts as no-worse: a test that was `PASS` on the baseline and is `INCONCLUSIVE`, `SKIPPED`, `BLIND`, `ERROR` or absent on the new image is a regression (`baseline-pass-lost`), exactly like a `FAIL`. A test that is quarantined (§11.4.248) or removed after the baseline stays in the comparison as absent. Tests that exist only in the new run are reported separately as new-test verdicts; they do not enter the comparison, and a non-`PASS` among them is a tracked issue (§11.4.202). A missing baseline is cured only by producing it: flash the previous image (kept as the immutable artifact of §11.4.264) on the same board and run the same suite with the same command, then compare.

**(D) MORE STABLE — every next image that fixes anything.** Every next image, except one whose Roadmap scope is purely new features, MUST be MORE STABLE than the image before it, proven by the comparison: no regression, a not-PASS count lower than or equal to the baseline's, and every targeted flip present. A targeted issue is a Roadmap item of type `Bug` (or any item whose closure claims a defect removed) that the image claims to fix; its flip is the §11.4.292(E) pair: the test reads the symptom signature TRUE (RED) on the baseline image and FALSE (GREEN) on the new image, with the same command, board and signature. A purely new-feature image (no item in its scope claims a defect removed) has no targeted flips and still MUST be `NO-WORSE-PROVEN` on every pre-existing test. A targeted issue that is `UNREPRODUCED` under §11.4.292 cannot supply a flip, so an image that claims it as fixed cannot be `NO-WORSE-PROVEN` until its live RED exists.

**(E) THE RECORD.** The comparison is machine-written as one record per image: both image identities, the board serial, the harness fingerprint, the suite definition id, the command, both per-test verdict sets (path and sha256), the per-test diff (every test whose verdict changed, with both verdicts), the two not-PASS counts, the targeted-issue list with each flip's evidence, the verdict and its reason codes. A verdict written by hand, or derived from runs on different boards, harnesses, suites or commands, is not a verdict (§11.4.7 same conditions, §11.4.240 producer is not verifier).

**(F) RELEASE, TAG AND CHANGELOG.** `REGRESSED` and `INCOMPARABLE-BASELINE-MISSING` refuse every release and its tag. Where the consuming project's own release rules allow a dev-class tag at any time (the provisional-eligible classes of §11.4.290(G), consumer DATA), that dev tag may still be created, but its changelog states the verdict FIRST, with the regressed tests and reason codes or the missing-baseline blocker, and the image is never described as no worse, stable or validated. Every image's changelog states the verdict, the baseline image identity, the board, the harness, the suite, both not-PASS counts, every regressed test, every targeted flip and the record path with its sha256, next to the §11.4.290(G) VERIFIED / PROVISIONAL / REOPENED / OVERDUE lists. A `REGRESSED` image triggers §11.4.114 isolation against the baseline image and a §11.4.292 reproduction of each regression; it is never re-run until green (§11.4.267).

**(G) WHAT THIS ANCHOR DOES NOT CHANGE.** §11.4.40 (the full-suite retest; the comparison uses its runs and adds the baseline), §11.4.114 (the last known good is the oracle; the baseline image is that oracle for the next image), §11.4.135 (the standing regression-guard suite and its verdict coverage), §11.4.200 (verify-after-write on the intended board), §11.4.236 (QA-deploy readiness), §11.4.248 (quarantine stays visible), §11.4.264 (one immutable artifact), §11.4.290 (PROVISIONAL-DONE and VERIFIED-DONE; an item in an image may still be provisional, the image's own comparison is not) and §11.4.292 (reproduce first) keep their full text. A comparison does not prove the image correct (§11.4.108 and §11.4.185 still decide); it proves that the image is not worse than the one before on the measured set.

**Honest boundary (§11.4.6).** The gate shipped with this anchor proves the RULE is present exactly once, complete, mirrored in the four context carriers, indexed and generated, and wired into the seams that carry rules. It does NOT prove that any commit carries a `Roadmap-Item:` trailer, that any image was compared, or that any comparison is correct: those item-level seams are the recommended gates `CM-COMMIT-NAMES-ROADMAP-ITEM` and `CM-IMAGE-NO-WORSE-PROVEN`, registered as deferrals `OWED-GATE-175` and `OWED-GATE-176` and NOT claimed implemented (§11.4.227(A)). The comparator itself is the consuming project's work: the constitution defines the inputs, the verdict set and the record, and ships no flashing tool. A no-worse verdict is bounded by the suite: a defect no test exercises is invisible to it (§11.4.118).
