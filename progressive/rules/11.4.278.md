### §11.4.278 — Mandatory HelixQA UI QA with Vision eyes: every project with a UI on ANY platform or OS passes HelixQA full suites over all screens, flows, use cases and edge cases, driven and read by a Vision model validated under §11.4.277 that recognises the real content of every screen / page / component / widget, against deterministic expected-content oracles, with no skip flags and a per-frame evidence path for every verdict (User mandate, 2026-10-12)

**Forensic anchor — operator mandate (2026-10-12, paraphrased from the intake; the verbatim text is in the consuming project's request-history record per §11.4.208/§11.4.210):** every project that has a UI, on any platform and any operating system (web, desktop, Android, Android TV, iOS, installer wizard, and so on), MUST be covered by full HelixQA test suites over ALL screens, flows, use cases and edge cases; HelixQA MUST have real "eyes" — a Vision model that recognises the real content of each screen, page, component and widget; no bluff.

**Why this exists (genericised FACTS).** §11.4.27 makes HelixQA the QA-orchestration submodule, §11.4.158 / §11.4.159 / §11.4.160 / §11.4.163 require recordings to be read and validated, §11.4.117 and §11.4.193 require a pixel/vision oracle when the semantic tree is blank, and §11.4.52 / §11.4.238 require autonomous validation to be the DISCOVERER. What none of them states as ONE universal obligation is: (1) that EVERY UI project, on EVERY platform, is covered by a HelixQA full suite over its WHOLE information architecture; (2) that the "eyes" doing the reading are themselves proven correct before they are trusted (§11.4.277), so a Vision model that hallucinates cannot certify a screen; and (3) that coverage is a closed, enumerated, machine-checkable set rather than a happy-path sample. Without (2) the vision step is the most fluent bluff surface in the whole pipeline: it can describe a plausible screen that is not there.

**What this is NOT (the §11.4.227 boundary).** It does not replace §11.4.158 (intensive record-and-read), §11.4.159 (window-scoped MP4 + vision validation), §11.4.160 (frame bridge), §11.4.163 (media pipeline), §11.4.117 (pixel oracle), §11.4.193 (anti-blind-typing), §11.4.143 (real-user-journey for video-streaming apps) or §11.4.185 (manual QA as final human confirmation). It binds them into a per-platform, whole-IA coverage obligation and adds the Vision-validation precondition. The accessibility tree / DOM / uiautomator remain PRIMARY oracles where they are trustworthy (§11.4.117); the Vision model corroborates and covers the pixels the tree cannot.

**The mandate (ALL hold):**

**(A) UNIVERSAL SCOPE — every UI, every platform, every OS.** Every project (and every submodule that ships a user-facing surface) that has a UI of ANY kind MUST pass HelixQA full suites for EACH platform/surface it ships: web (every supported browser engine × viewport class), desktop (every shipped OS: Linux, Windows, macOS — native, Electron/Tauri/Qt), mobile (Android phone/tablet, iOS/iPadOS), TV (Android TV / leanback / tvOS, remote-control navigation), wearable/automotive surfaces if shipped, TUI/CLI-with-screens, installer / setup wizards (including OS installer and first-run flows), embedded/kiosk displays, and admin/back-office UIs. A platform the project ships and does not cover is a §11.4.278 violation (composes §11.4.81 cross-platform parity and §11.4.25 full-automation coverage). A platform that genuinely cannot be driven or captured (FLAG_SECURE/DRM-black surface, no emulator, hardware not available) is recorded `structurally_impossible` with citations per §11.4.112 or `topology_unsupported`/`operator_attended` per §11.4.3 with a tracked item (§11.4.197) — never silently omitted, never a fake PASS.

**(B) WHOLE-IA COVERAGE IS A CLOSED, ENUMERATED SET.** For each surface the project maintains a machine-readable SCREEN-AND-FLOW CATALOGUE (the §11.4.219 per-app screen catalogue where the project has one; otherwise a catalogue created under this clause) enumerating: every screen/page/dialog/sheet/toast/empty-state/error-state/loading-state, every component and widget × state (§11.4.218), every flow and use case, and every declared edge case (valid / invalid / boundary / empty / max / concurrent / offline / slow-network / permission-denied / interrupted / rotated / locale-RTL / large-text / dark+light theme / low-memory, plus failure injection per §11.4.85). Coverage is the ratio of catalogue entries with a read-verified PASS record to catalogue entries; the required ratio is 100 % of non-waived entries. An entry added to the product without a catalogue entry is caught by a discovery sweep (§11.4.118: the catalogue is cross-checked against the build's actual route/activity/view/window inventory, so an undeclared screen is a finding). Waivers go through §11.4.271 only.

**(C) HelixQA IS THE DRIVER AND THE ORCHESTRATOR; THE SUITES ARE FULL.** HelixQA (§11.4.27; vendored per §11.4.74/§11.4.28) drives the suites: test banks per surface, challenge scripts per use case, the exercise → record → read → score pass of §11.4.158(C), the §11.4.160 frame bridge (frame at ≤ 5 s intervals and at every state transition), and the §11.4.163 media pipeline. "Full suite" means: every catalogue entry exercised by the UI-driven variant (§11.4.48) AND the intent/API variant (§11.4.49) where both exist, run on the real build artifact on a clean target (§11.4.108, §11.4.139), not on a mock, a stub or a hand-fed screenshot. The suites are ALL-types per §11.4.27 / §11.4.169 (functional, e2e, regression, visual, accessibility, performance/jank, security, stress/chaos, localisation, upgrade/install) — vision is added to that matrix, never substituted for any of it.

**(D) THE EYES: A VISION MODEL VALIDATED UNDER §11.4.277.** The Vision model HelixQA uses to read screens MUST hold a current §11.4.277 validation record for its exact model identity (as bound by the llmctl record, §11.4.277(H), plus the host-class elements the consumer binds) BEFORE its output counts in any verdict: `llmctl require-validated <profile>` exits 0 and the vision step runs with `LLMCTL_VALIDATE_STRICT=1`; HelixQA refuses to run its vision step otherwise (fail-closed, §11.4.252/§11.4.254) and the run's vision-dependent checks are reported `not_validated` (never green). The Vision model also obeys the §11.4.277(E) host-safety clause (pre-flight pressure refusal, bounded restarts, memory caps below RAM and co-residency bounded by the host's live budgets — host-dependent reference values as recorded there); a vision run that would breach it is deferred, not forced. HelixQA's "eyes" therefore have two layers: the validated model for recognition, and a deterministic OCR/template/pixel layer (§11.4.117) for assertions whose truth must be exact (text strings, numbers, colours, positions, counts).

**(E) WHAT THE EYES MUST ESTABLISH — real content, not plausibility.** For every captured screen/frame the vision pass MUST produce a structured record: (1) SCREEN IDENTITY — which catalogue entry this is (and that it is NOT a neighbouring screen, a blank, a spinner-stuck, a crash dialog or an error page); (2) COMPONENT/WIDGET INVENTORY — the components present and their state (enabled/disabled/selected/focused/loading/error), each located by region; (3) CONTENT — the actual text, numbers, images and media shown, compared with the expected content for THAT screen in THAT state with THAT data (not "looks like a login screen" but "the login screen shows the labelled fields X and Y and the error text Z"); (4) HEALTH — no clipped/overlapping/off-screen elements, no untranslated or placeholder strings (`TODO`, `lorem`, raw keys, `{{var}}`), no stale/frozen frame (§11.4.107 liveness), no obstruction; (5) CONSISTENCY with the product's own data (the value shown equals the value the backend/DB/fixture holds — a sink-side cross-check per §11.4.68/§11.4.69, not the screen alone). A description that is merely plausible is a FAIL.

**(F) DETERMINISTIC EXPECTED-CONTENT ORACLES — declared BEFORE the run.** Every catalogue entry carries an EXPECTED-CONTENT SPECIFICATION written before the exercise (§11.4.159(J)): the closed set of required strings/regions/components/states/counts, the forbidden patterns, the data fixtures that make the content known (seeded accounts, fixed catalogue, frozen clock, fixed locale), and for each assertion WHICH oracle decides it (accessibility tree / DOM / uiautomator > deterministic OCR/template > validated-Vision model; the model decides alone ONLY where no deterministic oracle exists, and then the assertion is marked `model-decided` and needs a corroborating second angle per §11.4.145 / §11.4.123 or stays `PENDING_FORENSICS`). The comparator is mechanical, never a model judging a model (§11.4.262(C)/(D)), and is golden-good/golden-bad self-validated (§11.4.107(10)). Data and environment are pinned so the same build yields the same screen (§11.4.50 deterministic consistency); where a screen is inherently dynamic the spec declares the masked regions explicitly instead of loosening the whole assertion.

**(G) NO SKIP FLAGS, NO PARTIAL SUITES, NO SILENT SKIPS.** No `--skip-vision`, `--skip-platform`, `--happy-path-only`, `--screens-subset`, `--ignore-failing-screen`, `--lower-ocr-threshold`, `--accept-model-description`, `--no-recording`, `--fixture-screenshot-instead-of-live` flag or equivalent environment variable, config key or `t.Skip` exists. The ONLY permitted non-PASS outcomes are the closed set `FAIL`, `not_validated` (vision model not validated), `topology_unsupported`, `operator_attended`, `structurally_impossible` (§11.4.112) and `waived` (§11.4.271), each with a reason and a tracked item; a suite whose result set contains an unexplained skip, or whose PASS count is not equal to catalogue entries minus recorded non-PASS entries, FAILs. Skips are loud (project Definition of Done: `SKIP-OK: #<ticket>` where the language needs it). A run whose HelixQA version, Vision model identity or catalogue hash differs from the recorded one is a different run and is recorded as such.

**(H) PER-FRAME EVIDENCE PATH FOR EVERY VERDICT.** Every verdict cites, per §11.4.5/§11.4.69/§11.4.160(4)/§11.4.163(d)/§11.4.262, a per-frame evidence set under `docs/qa/<run-id>/helixqa-ui/<platform>/<surface>/<catalogue-id>/`: the raw frame (PNG) with SHA256, its capture timestamp and the window-scoped capture parameters (§11.4.159(A)), the OCR text, the Vision structured record (E), the expected-content spec, the matched / unmatched pattern lists with exact pinpoint on FAIL (§11.4.163(e)), the §11.4.277 validation-record id, the analyzer/comparator version + calibration hash, and the MP4 recording segment with project-name prefix (§11.4.155/§11.4.159(C)) and its frame offset. Evidence is machine-created and hash-chained (§11.4.268). Credential characters visible in frames are redacted before commit (§11.4.10, §11.4.193(5)). No blind typing: every input step is preceded and followed by a captured, read screen (§11.4.193).

**(I) DISCOVERY PRESSURE AND ESCAPE AUDIT.** The suite is the DISCOVERER (§11.4.238): a defect found by manual QA, an operator or a user that the HelixQA run called PASS is an operator-escape → mandatory bluff-audit and a permanent guard (§11.4.138) AND a re-validation review of the Vision model identity (§11.4.277(H)): was it the model, the fixture set, the spec, or the comparator that missed it? Every fixed defect gains a regression bank entry (§11.4.135) that drives the same screen through the same path (§11.4.146 reproduce-first, same test confirms the fix). Exploratory/monkey sweeps of the real build (§11.4.118) feed new screens back into the catalogue.

**(J) REQUIRED ARTIFACTS PER CONSUMING PROJECT.** (1) the screen-and-flow catalogue per surface (B); (2) HelixQA test banks + challenge scripts per surface and per use case, in the project's `challenges/` and bank locations, each paired with its §1.1 mutation; (3) expected-content specifications (F) and the seeded-data fixtures; (4) the §11.4.277 validation record for the Vision model identity and its fixture corpus + manifest; (5) the coverage ledger (per-entry status, last-verified run id, evidence path) kept current per §11.4.153 / §11.4.15; (6) documentation per §11.4.60 / §11.4.257 / §11.4.258: the user manual + guide + FAQ entry for each screen/flow the suite covers (and the manual itself is read-checked against the live UI so docs cannot drift), the HelixQA run guide, and architecture / data-flow / sequence / state-machine diagrams updated for any screen or flow the change adds (a screen without its doc + diagram is incomplete); (7) README quality-status badge row entries for UI-QA coverage and Vision validation (§11.4.259); (8) docs mirrored per §11.4.65 and translated where the project is localised (§11.4.255/§11.4.256); (9) the qa-readiness gate input for §11.4.236: no manual-QA hand-off until the catalogue coverage gate is GREEN.

**(K) CONSUMER ADOPTION (§11.4.35).** The consuming project states, as DATA: the surfaces and platforms it ships, the catalogue and spec paths, the HelixQA bank/challenge locations, the capture mechanism per platform (browser automation + screenshot, emulator/device `screencap`, OS-level window capture), the OCR engine + confidence floor and frame interval (calibrated on its own frames per §11.4.6/§11.4.160), the Vision model identity and its §11.4.277 validation record, the seeded-data fixtures, and the evidence root. The first consumer to adopt declares each of its shipped surfaces (§11.4.28 submodule-as-equal-codebase: web, desktop, mobile, TV, installer wizard and so on, as applicable); every other consumer adopts in the same shape and may not narrow it.

**(L) VISION MODEL IDENTITY AND TIERS (operator mandate, 2026-10-21: "balance — several vision tiers we could use, and in results we know exactly which Vision model was used").** (1) The consumer declares, as DATA, an ordered ladder of AT LEAST TWO Vision tiers (for example a small fast tier and a larger accurate tier) by llmctl profile, each with its host-tier floor and memory footprint; a tier is usable only after its own §11.4.277 validation PASS on this host, and the run uses the highest tier that is validated AND fits the host budget (§11.4.277(E)); falling back to a lower validated tier is allowed and is recorded, never silent. (2) EVERY verdict, every per-frame Vision record (E) and the run summary carry the Vision model identity as machine fields: llmctl profile, tier name, model file name and sha256 (and `mmproj` sha256), quantisation, engine and version line, launch fingerprint, validation-record id and its age; a verdict whose record lacks any of them is INVALID (§11.4.262). (3) The report of a run lists the tier mix (frames judged per tier); a PASS produced by a lower tier is never presented as one produced by a higher tier, and a run whose tier differs from the declared target says so in its first line. (4) When no tier is validated the vision step stays `not_validated` (§11.4.277(A)); the ladder never lowers the validation bar. Gate `CM-VISION-MODEL-IDENTITY-RECORDED` (recommended, gate-code owed as OWED-GATE-143: FAILs on a verdict with a missing identity field or a tier not on the declared ladder; paired §1.1 mutation: drop a field → FAIL).

**Status of this anchor (operator decision, 2026-10-13: ship as proposed, evidence PENDING).** §11.4.278 is PROPOSED. No HelixQA / consumer end-to-end evidence for it exists yet: a real HelixQA bank run that reads screens through llmctl `vision` with `LLMCTL_VALIDATE_STRICT=1` and `llmctl require-validated` gating is a separate future work item, and until it exists every mechanism gate listed below (the HelixQA and UI-QA gates) is a deferral, not a shipped mechanism.

**Honest boundary (§11.4.6).** A 100 % catalogue-coverage PASS shows that every ENUMERATED screen, flow and edge case rendered the expected content under the declared data and environments; it does NOT prove the absence of screens or states the catalogue and discovery sweep missed (§11.4.118), does NOT prove real-user taste/usability (§11.4.185 manual QA remains the final human gate, with its own machine-created record), and a Vision model's recognition is bounded by its validated corpus (§11.4.277 honest boundary) — which is why deterministic oracles outrank it wherever they exist. Where a surface is FLAG_SECURE / DRM-black, only the documented proxy oracle of §11.4.112 / §11.4.117 applies and the gap is recorded.

**Classification: universal (§11.4.17)** — no project/platform literal is hardcoded; the consumer supplies surfaces, catalogue, specs, capture tooling, OCR/Vision model identity, thresholds and evidence root as DATA per §11.4.35.

- `CM-UI-ESCAPE-TRIGGERS-REVALIDATION` — an operator-escape on a UI defect triggers the §11.4.138 audit and a §11.4.277(H) re-validation review record.
