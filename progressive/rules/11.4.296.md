### §11.4.296 — GitHub Issues are a source of workable items: the issues assigned to a declared account are imported on a declared interval, one tracker item per issue, re-checked by content hash, answered by a guarded status write-back and proven by a fail-closed gate; the direction is GitHub to tracker only (User mandate, 2026-11-05)

**Forensic anchor — operator order (2026-11-05, BACKGROUND, CRITICAL), as relayed by the conductor in the operator's words of intent (the operator's own message is not quoted here, except for the scope ruling below):** the issues of the project's GitHub repository that are assigned to the operator's account are a source of workable items. They are pulled periodically and regularly; each one is imported into the workable-items system (the SQLite database, a workable-items document per item that points to its parent ticket, and the external-tracker boards); edits and extensions made by the team are re-checked; the item's progress, testing, resolution and done status is reflected back onto the ticket; there are no duplicates (existing duplicates are grouped); the roadmap, the burn-down charts and the progress documents stay in sync; every project that inherits the constitution acts on a new ticket as soon as it appears; all of it is documented, tested and verified deterministically against machine evidence. **Scope ruling of the same evening (2026-11-05 22:24, relayed by the conductor, quoted):** "We will be importing and maintaining already opened issues (workable items) from GitHub Issues but we will NOT import our other workable items there".

**The gap this anchor closes (stated so it is not restated elsewhere, §11.4.227).** §11.4.148 binds the database, the rendered documents and the external tracker into one integrity contract and §11.4.93 makes the SQLite database the single source of truth, but neither names an external SOURCE of items: a ticket that a team member opens on the hosting platform's issue tracker is invisible to the workable-items system until someone retypes it, and no rule says how often the platform is looked at, how a duplicate is prevented, how a team edit made after the import is noticed, how the ticket learns what became of its item, or what proves any of that. §11.4.202 files owed work as items, §11.4.294(I) mirrors items to an external tracker one way (database to tracker) and §11.4.292 binds a reproduction to every defect; none of them imports a ticket. This anchor adds the source, the key, the hash, the write-back, the response time and the gate. It does not move the single source of truth: the ticket is a source and a mirror target, never a second source of truth.

**(A) SOURCE DECLARATION AND DIRECTION.** The consuming project declares, as DATA (§11.4.35), in one tracked configuration file: the repository (`<owner>/<repo>`), the assignee account or accounts whose issues are imported, the sync interval in hours, the grace in minutes, the write-back mode (`dry-run` or `apply`, default `dry-run`) and the state of the external-tracker leg. Only an issue that ALREADY EXISTS on the platform and is assigned to a declared account is imported. The direction is platform to tracker, one way in; the operator's scope ruling is quoted above, and it means: (1) the sync tooling never creates, transfers or exports an issue (no `gh issue create`, no API call that creates an issue, no bulk export of tracker items); (2) a tracker item that did not come from an imported issue never receives a comment, a label or a state change on the platform; (3) the write-back of clause (E) touches only a tracker item whose description carries the marker line `GitHub-Issue: <owner>/<repo>#<number>` of clause (C), and only the issue that marker names; (4) a configuration that declares an unmarked-item write-back, an issue creation or an export is invalid and the gate of clause (J) fails on it.

**(B) PERIODIC SYNC AND THE RUN RECORD.** The sync runs at least once per declared interval, and the interval is at most 24 hours (the cap belongs to the rule; a project that wants a shorter interval declares it). A run has five steps in this order: `pull` (read-only; the assigned issues with title, body, state, labels, assignees, milestone and comments are saved as a snapshot whose sha256 is recorded), `plan` (the snapshot is compared with the tracker, nothing is written), `apply` (items are filed or updated in one transaction after a backup of the database, §9.2), `writeback` (clause (E); a plan only in `dry-run` mode) and `check` (the gate of clause (J) runs on the snapshot and the database). Every run writes ONE run record, also when it fails, is offline or changes nothing: run id, start and end in UTC, mode, outcome, number of issues seen, items created, items updated, duplicates found, first-response comments posted or planned, write-back mode, the state of the derived documents, the state of the external-tracker leg, the snapshot sha256 and the database sha256 before and after. A run that cannot reach the platform records the outcome `INCONCLUSIVE`, writes nothing to the tracker and is never a PASS.

**(C) ONE ITEM PER ISSUE, NO DUPLICATES.** The key of an issue is `<owner>/<repo>#<number>`, compared case-insensitively on owner and repository. The workable item imported from an issue carries, as a line of the leading header block of its description (a marker quoted later in the text is text, not a key), the marker `GitHub-Issue: <owner>/<repo>#<number>`, exactly once, together with a link to the parent ticket (`Source-Issue: <url>`). Exactly one tracker item (one identifier, §11.4.54) carries the marker of a given key; two items with one key are a duplicate and a failure. The key, never the title, decides identity: a renamed issue stays one item, and a re-import of an unchanged snapshot changes nothing (idempotent). Items that existed before the import and duplicate an issue (the same ticket filed by hand) are neither deleted nor silently merged: they are GROUPED with the canonical item through the workable-items system's own group mechanism (the logic-group column), the canonical item being the one that carries the marker.

**(D) RE-CHECK BY CONTENT HASH.** On every run the content hash of each imported issue is recomputed: the sha256 of a canonical serialisation (sorted keys, no insignificant whitespace, UTF-8) of the fields a team member can edit, which are the title, the body, the state, the labels, the assignees and the comments, leaving out what the sync itself writes (its own status labels and its own comments), directly or as the hash of the per-field hashes. The hash of the last import is stored in the leading header block of the item (the line `GitHub-Content-Sha256:`). A different hash means the team edited or extended the ticket: the item's mirror of the ticket (title, the description block, labels) is updated in the same run, one history event records the old and the new hash, and nothing the tracker side owns is overwritten (the status, the reproduction and investigation states of §11.4.294, the evidence). A closure of the issue on the platform side NEVER closes the item: it flags the item for review, because a closure needs evidence (§11.4.2). An issue that is no longer assigned to a declared account, or is deleted, keeps its item and the item is flagged; an item is never deleted by the sync.

**(E) STATUS WRITE-BACK.** The ticket learns what became of its item through ONE closed vocabulary that the consumer declares as data and that covers exactly these seven classes: `acknowledged` (imported, first response), `in-progress`, `in-testing`, `resolved`, `done`, `blocked`, `reopened`; the consumer may spell each class as its own ladder rung or label, one to one, and records the table. A status of the consumer that maps to no class is reported `unmapped` and nothing is written for it. The effect on the platform is one comment per transition whose first line is an invisible machine-readable marker naming the item identifier and the class, one status label (the previous status label is removed), a closed issue only for the class `done` (and, when the consumer's table says so, closed as not planned for an item withdrawn as obsolete, never as completed) and a reopened issue only for `reopened`. The write-back is GUARDED: (1) the default mode is `dry-run`, the plan is printed and recorded and nothing is written; `apply` needs the operator's explicit enable record (a decision id or a path) in the configuration and a confirmation flag on the command line; (2) marked items only, as clause (A)(3) says; (3) idempotent: a transition whose marker comment already exists is not posted again; (4) pre-write re-read: when the issue changed since the last pull the write is refused and the run pulls again first; (5) a declared cap on the number of writes per run; (6) a failed write is recorded as `write-failed` and is never counted as written; (7) `resolved` and `done` are written only when the item reached the matching rung of the consuming project's done ladder with its evidence (§11.4.290, §11.4.294 and the project's own ladder), and the comment names that evidence by path; (8) no comment carries a credential, a local path or a claim without evidence (§11.4.10, §11.4.2).

**(F) EXTERNAL-TRACKER LEG.** After an import the items go to the external tracker through the full sync that §11.4.148 already requires (statuses, types, assignee, sub-tasks, and the two state fields of §11.4.294(I), one way, database to tracker). When the leg cannot run (no credentials, no network, a board that does not exist, a deferral the operator ordered) the run record states `blocked` with the reason as one of the closed codes `no-credentials`, `no-network`, `no-board`, `operator-deferred`, and the verdict of that leg is `UNCONFIRMED`: never `synced`, never a PASS. A blocked leg is tracked as an item (§11.4.21, §11.4.202) and its block ends by the evidence of a real sync, not by a flag.

**(G) DERIVED DOCUMENTS STAY IN SYNC.** In the same run that created or updated an item, the consumer regenerates its derived documents (the roadmap with its counts, the burn-down charts and the progress documents, §11.4.294(H)) and runs their freshness checks; the run record states `fresh` or `stale` with the reason. A run that changed an item and left a derived document stale is a failure.

**(H) RESPONSE TIME.** A new ticket is acted on as soon as it appears, in checkable terms: (1) detection within one interval: consecutive run starts are at most the interval plus the grace apart (a run record exists even for a failed or offline run, so a gap is a missing record and a failure); (2) filing in the same run: every issue the run saw has its item when the run ends, no issue is left `unfiled`; (3) first response in the same run: for every item the run created, a first-response comment with the word `acknowledged` is posted (mode `apply`) or planned and recorded (mode `dry-run`) in that run. The rule is measured from the run records, never from intent.

**(I) THE DONE LADDER IS NOT BYPASSED.** An item imported from an issue starts at the lowest status of the consumer's set and climbs the consumer's own ladder (the PROVISIONAL-DONE and VERIFIED-DONE levels of §11.4.290, or the consumer's own replacement of them, the states of §11.4.294, the evidence). The platform's `closed` state, a team member's comment and a label on the ticket are data, never evidence of done. A ticket is closed by the write-back only after the item reached the consumer's top rung.

**(J) THE EVIDENCE GATE.** The consumer ships a fail-closed gate that proves the loop from machine evidence and never from prose. It reads the configuration, the snapshot, a read-only copy of the database and the run records and checks that the rules are wired (this anchor present in the constitution pin the project uses, the project's rule document present, the sync tool present with its sub-commands, the interval within the cap, the write-back default `dry-run`), that every issue of the snapshot assigned to a declared account has exactly one item, that no marker is duplicated or points at another repository, that the content hash stored in each item equals the hash recomputed from the snapshot, that consecutive runs are within the interval plus the grace, that the first-response comment and the state of the derived documents are recorded, that no external-tracker leg is reported `synced` while the configuration says it is blocked, that the sync tooling contains no issue-creating command and no write-back path for an unmarked item, and that no recorded write-back action touched an unmarked item. The verdicts are `PASS` only with evidence supplied and every check green, `FAIL`, `BLIND` (exit 2: the control needle of the instrument failed) and `INCONCLUSIVE` (exit 3: offline, or no snapshot or no database supplied); a result is never a PASS without evidence and a PASS names its scope (`wiring` or `full`). A control needle runs before any verdict and a paired §1.1 mutation test proves that each check fails when its condition is broken.

**(K) WHAT THIS ANCHOR DOES NOT CHANGE.** §11.4.148 (the external tracker is synchronised, the database is the single source of truth), §11.4.93, §11.4.15, §11.4.21, §11.4.33 and §11.4.90 (the status closed sets), §11.4.290 and §11.4.294 (the levels and the states), §11.4.2 and §11.4.6 (evidence, no guessing) keep their full text. This anchor adds the source, the key, the hash, the write-back words, the response time and the gate; the status sets and the verdict sets are not extended.

**Honest boundary (§11.4.6).** The gate shipped with this anchor proves the RULE is present exactly once, complete, mirrored in the four context carriers, indexed and generated into the group, rule file and catalog, and wired into the seams that carry rules. It does NOT prove that any sync runs, that a snapshot is complete, that a write-back reached the platform, or that the external-tracker credentials exist: that item-level seam is the recommended gate `CM-GITHUB-ISSUES-SYNC-EVIDENCE`, registered as deferral `OWED-GATE-181` and NOT claimed implemented here (the constitution ships no sync engine, no platform client and no run-record store; the consuming project implements it).
