### §11.4.287 — Destructive-path safeguard: no agent, script, hook, test or subagent may recursively delete, re-permission or sync-delete the filesystem root, a system directory, /home, a home directory, an ancestor of it or a protected child of it; enforced by a non-overridable PreToolUse guard, a refusing runtime helper and mandatory script hygiene (User mandate, 2026-10-23)

**Forensic anchor (measured 2026-10-23, CEST).** A review subagent ran a scratch script of the shape `W="$2"; export HOME="$W/home"; rm -rf "$HOME"` with its arguments empty. `$W` was empty, so `$HOME` became `/home` and a recursive delete ran with the operator's own rights against `/home` until a 120-second timeout killed it. Measured damage: the Catalogizer `.git` and `.git/modules`, about 17,100 tracked files, the operator's `~/scripts`, parts of two sibling project trees and of one agent home, and the project `.env` credentials. Nothing in the harness refused the command: the existing forbidden-command guard checked a fixed list of literal commands, not the target of a recursive delete, and no rule bound the scratch scripts that subagents write. A single empty variable became an unbounded delete. Operator mandate, verbatim as typed, typos preserved [sic]: "Yes, do safeguard thing! Absolutely! Do incorparate it into the constitution Submopdule as well!"

**Terms (named once).** A DESTRUCTIVE COMMAND is a recursive `rm`, `shred -r`-class remover, `chmod -R`, `chown -R`, `find` with `-delete` or `-exec rm`, or `rsync --delete`. A PROTECTED TARGET is the filesystem root, a system directory (`/bin /boot /dev /etc /lib* /opt /proc /root /run /sbin /srv /sys /usr /var /mnt /media /snap`), `/home`, a user's home directory, `$HOME` or `~`, an ANCESTOR of `$HOME` (so `/home` and `/` are covered by two routes), or a protected child of `$HOME` (the operator's scripts, project trees and agent homes); the shared list lives in `scripts/lib/protected_paths.list`. A TAINTED VARIABLE is one derived, directly or through assignments, from an unguarded positional parameter, from input read at run time (`read`, `mapfile`, `readarray`) or from an expansion that can be empty.

**(A) The PreToolUse guard (preventive layer).** Every governed project MUST register `scripts/hooks/guard-destructive-paths.py` as a PreToolUse hook for Bash, Write, Edit and MultiEdit (registration is the consumer's `settings.json`, edited only with the operator's consent). It reads the Claude Code hook JSON on stdin, exits 0 to allow and 2 to block with the reason on stderr. It splits shell text with a quote-aware splitter, recurses into `bash -c`, `eval`, `$(...)`, backticks and heredocs, and for Write/Edit/MultiEdit scans shell files (`.sh .bash .zsh .ksh`), Makefiles, justfiles, CI yaml (GitLab CI and GitHub workflows) and Dockerfiles or Containerfiles, or content that starts (after optional blank lines or spaces) with a shell shebang; for Edit and MultiEdit of a file that does not say it is a script by name, the shebang of the file on disk (or of the replaced text when the file cannot be read) counts, and one shared rule set decides this for Write/Edit/MultiEdit content and heredoc destinations. A `for` loop over literal words is judged on the words (so a loop over a protected path is class P). A relative target is resolved against the hook payload `cwd`; unquoted expansions are word-split before the target check, `${X:=v}` and `${X:-v}` are modelled, `$0` of `sh -c` is the word after the script text, a literal producer feeding `xargs` or `read` is modelled with printf and echo escapes, and an environment prefix (`D=/home bash -c`, `env D=/home`), `OLDPWD` and `~-` are resolved. It reports five classes. CLASS P (protected): a destructive command aimed at a PROTECTED TARGET, or at a glob that can match one. Class P is NEVER overridable; the audited marker does not downgrade it. CLASS X (parse error, desync or degraded check): (1) text that cannot be parsed reliably (unterminated quote, `$(`, backtick or heredoc) and that also contains a destructive command; (2) on the DEGRADED CHECK, which runs when the full analysis cannot finish (a string re-parsed as code more than 5 levels deep, total nesting of substitutions and function calls deeper than 40, the work budget or the clock), a recursive or forced delete it cannot judge, or a command word it cannot resolve that is used with a recursive or force flag or a protected path; (3) an internal guard failure, or a Bash command or Write/Edit content that is not a string. It fails closed and is NEVER overridable. CLASS H: `HOME` is reassigned from an expansion that is not guarded, then a destructive command runs under it (the incident shape). CLASS V: a destructive command whose target derives from a TAINTED or empty variable, or a recursive delete whose whole target is a variable that is never assigned in the payload, or an inline interpreter delete (`rmtree`, `rmSync` and similar) with a computed path (a protected literal there is class P). The never-assigned rule is a switch in the guard (`R7_UNKNOWN_RECURSIVE`); `rm -rf /tmp/*` is class P (it can match the temp root) while `rm -rf ~/.cache/*` is class V. CLASS U: code fed to a shell from a source the guard cannot read (a pipe from an unknown producer, an unknown variable). Classes H, V and U block unless a real top-level single-line comment `# guardrails:allow <reason>` with a non-empty reason is present; text inside quotes, heredoc bodies, `bash -c`, traps or `$(...)` does not count. A variable counts as guarded only by `${VAR:?}`, by a `[ -n "$VAR" ]`-class test that exits, or by a literal or `mktemp` assignment. Unparsable text WITHOUT a destructive command is allowed with a warning on stderr, and an internal guard exception BLOCKS as class X (fail closed, §11.4.201(4): an uninspected command is never allowed; the cost, stated honestly, is that a guard defect can block harmless commands until it is fixed, which the false-positive survey over real scripts guards against). Only a payload that is not JSON at all is allowed, with a warning on stderr, because it carries no tool input to inspect.

**(B) The runtime helper (last line of defence).** Scripts that delete recursively MUST call `safe_rm_rf` from `scripts/lib/safe_rm.sh` instead of a bare recursive delete. It refuses, returning 2 and deleting nothing, when any argument is empty or unset, option-like, contains a newline, ends in `.` or `..`, is not absolute after `readlink -m` resolution, is the root, a system directory, `/home`, a user home, `$HOME` or any `SAFE_RM_EXTRA_HOMES` entry (`SAFE_RM_EXTRA_HOME_ROOTS` adds directories whose direct children are homes, like `/home`), an ancestor of one, a protected home child, the temp root, shallower than `SAFE_RM_MIN_DEPTH` (default 3) components, or (when `SAFE_RM_ALLOWED_ROOTS` is set) outside the allowed roots. Every rule is applied to the LEXICAL path (parents resolved, last component not followed, which is what `rm` removes) and, when the argument ends in `/`, also to the fully RESOLVED path, so a symlink leaf pointing at a protected path can be removed as a link while `link/` is refused (deliberately conservative: the deletion itself never follows the link). A temp root that is, or contains, a home or a home root buys no temp-root depth bonus. The protected list is read from `protected_paths.list`; if that file is missing, unreadable or malformed, or the library was sourced without a real file path (for example `eval` of its text), every call is refused (fail closed). Configuration is validated: `SAFE_RM_MIN_DEPTH` must be a non-negative integer without leading zeros, and `SAFE_RM_ALLOWED_ROOTS` and `SAFE_RM_EXTRA_HOMES` must be colon-separated absolute paths, not glob-expanded; anything else is a config error and refuses. Validation is atomic: all arguments are validated before the first deletion, so one bad argument means nothing is deleted, and the deletion then uses the validated path; the deletion is not atomic (if `rm` fails on argument k, arguments before it are already deleted and the status of `rm` is returned). The check-to-use race (a parent directory swapped for a symlink between validation and `rm`) is narrowed, not closed.

**(C) Script hygiene (mandatory for every script a project or a subagent writes).** (1) A variable that names a path to delete is expanded as `"${VAR:?message}"`, never bare. (2) `HOME` is never reassigned from an expansion that can be empty; a test needing a fake home uses an explicit `mktemp -d` root and checks it is non-empty and under the temp root before use. (3) A test that deletes anything runs inside a sandbox whose root it created, with an assertion that the delete target is a child of that root. (4) A script ends no recursive delete with a variable argument it did not itself assign. (5) `set -u` is necessary but not sufficient: an EMPTY variable is set, so `${VAR:?}` is the required form.

**(D) Subagent and reviewer scratch-script briefing.** Every dispatch brief for an agent that may write or run scratch scripts (reviewers running mutations included) MUST state: use `safe_rm_rf` or `${VAR:?}`; never reassign `HOME`; run mutation sandboxes under an explicit `mktemp -d` root; and treat a block by the guard as a defect in the script, never as something to route around. Test payloads that contain destructive text MUST NOT be carried in heredocs or shell strings: the review that built this guard found that a shell-quoted payload is itself a command and a mis-quoted one can execute; build them in a non-shell language (the bypass suite assembles every payload in Python from fragments and feeds the guard JSON on stdin, so nothing in it can run). The independent review of any script that deletes (§11.4.142 / §11.4.209) MUST check clauses (A) to (C) and attempt at least one empty-argument run of the script inside a sandbox.

**(E) Honest boundary (§11.4.6).** The guard is a text scan, not a security boundary. It inspects only the Bash, Write, Edit and MultiEdit tools: `NotebookEdit` and MCP shell or file tools (for example desktop-commander `start_process` or `write_file`) bypass the hook entirely. It cannot see a command assembled at run time by `eval` of a decoded string, command-substitution output used as a target, a downloaded script, a binary, or a language runtime deleting through its own API, and no claim of full coverage of shell syntax is made (the bypass suite lists the shapes found so far, not all shapes); it does not replace file-system permissions, backups (§9.2) or the host-safety rules of §12. Known and tracked limits (measured, not exhaustive): a `# guardrails:allow <reason>` marker downgrades every overridable (H/V/U) finding in the same payload, not only the next statement; a guard token counts when it appears at command position in executable text with a leaving branch, but its position and reachability are not checked (a guard placed after the delete, in a dead branch, in an uncalled function or in a subshell whose exit does not leave is still accepted); `alias`, `source` of an existing file, namerefs and brace ranges are not modelled; a single-quoted `$VAR` literal is treated as a live variable (false positive); a command substitution inside a larger value is not tracked; a heredoc body read into a variable and later used as a delete target, and a script written to a file with a non-script name and later run, are not followed. Further known limits (round 7, measured): namerefs, array append and extglob are not modelled; a script written with `echo >` and run later, inherited environment such as `XDG_*`, runtime deletes beyond inline-literal detection, a Unicode slash, `/HOME` on a case-insensitive file system, IFS tricks, non-recursive `rmdir` and `unlink`, the run-time cwd of a Write or Edit script and script FILES run by an interpreter are not seen; the cwd used for relative targets is the one in the payload. The guard's built-in home-children set is aligned with `protected_paths.list` by a test, but the two are separate data (the helper reads the list, the hook carries its own defaults). An unparsable (non-JSON) hook payload is allowed (fail-open), because Claude Code always sends JSON and blocking would stop all work (§11.4.201(1)); this is in tension with the conservative-safe default of §11.4.201(4) and §11.4.252, and whether any harness can emit a non-JSON payload is UNCONFIRMED. The hook is shipped, not registered: it protects nothing until the operator registers it in the user's settings. Round-7 review findings, documented and NOT fixed (review budget exhausted; operator decision: ship with documented limits). The guard is a best-effort tripwire, not a security boundary, and these seven classes all pass it: (1) bash bracket globs: negation `[^...]` and POSIX classes `[[:alpha:]]` are not modelled (fnmatch semantics), so `rm -rf ~/.[^.]*` and `rm -rf /[[:lower:]]ome` are allowed (the `[!.]` forms are blocked); (2) command-substitution evaluation: `$(printf '\x2fhome')`, `$(echo -e ...)`, `$(printf '/%s' home)`, a trailing newline in the result and `$(cd ~/.. && pwd)` are not evaluated, and an unknown result is not treated as class V; (3) exec wrappers off the fixed list: any wrapper not enumerated (chrt, taskset, runuser and setsid are now enumerated and tested; for example unshare, nsenter, fakeroot, strace, script, tmux, screen, at, ssh, fish, make, a gdb or vim shell escape, sed `e`, awk `system`) hides the command; (4) interpreter shell-out: `python3 -c` with `os.system` or `subprocess`, `perl -e system`, `node -e child_process` are not read (only rmtree-style APIs are); (5) `tar --remove-files` is not counted as a recursive delete, and `shred -u` of a single file inside a protected child (for example a key under `~/.ssh`) is not blocked; (6) a Write or Edit script containing a deep `../` chain, and a Bash payload with no cwd and a deep `../` chain, are not treated as absolute; (7) a symlinked cwd combined with a glob (`rm -rf ./*` in a cwd that is a symlink to HOME) is not resolved on disk. Also unmodelled: `truncate` and `cp` over protected files (not recursive deletes), and `/proc/1/root/...`. Because round 7 was the last permitted review round (`R_max`, §11.4.276(E)(3)) and found these seven new classes (two of them recurrences of earlier classes), the guard is declared a best-effort tripwire; the structural replacement (class-wide rules: wrapper-agnostic embedded-command detection, an uncomputable value reaching a delete treated as class V, real bash glob semantics or any bracket expression treated as matching anything, a `..` chain at least HOME's depth treated as absolute) is a tracked new work item (registered deferrals OWED-GATE-156 to OWED-GATE-160 in `scripts/gates/gate_ledger_deferrals.tsv`: `CM-GUARD-GLOB-BASH-SEMANTICS`, `CM-GUARD-UNCOMPUTABLE-VALUE-IS-V`, `CM-GUARD-WRAPPER-AGNOSTIC-EMBEDDED-COMMAND`, `CM-GUARD-DEEP-DOTDOT-AND-SYMLINK-GLOB`, `CM-SAFE-RM-PROTECTED-LIST-EQUALS-GUARD`), not claimed done. The former `GUARD_R7_UV_OFF` survey switch was removed (round-1 fix of the v72 review): the unknown-recursive-target rule is unconditional and has no environment switch. `safe_rm_rf` reads `protected_paths.list`, which lacks several paths the guard protects (Documents, Desktop, Downloads, Pictures, Music, Videos, Obsidian, bin, go, opt, Android, .git, .aws, .kube, .docker, .password-store), so it is not the same protection. It reduces the probability of the incident class and narrows its blast radius; it does not prove a script safe. `safe_rm_rf` protects only calls routed through it. Backups remain the recovery path, and a copy of the operator's home data outside the host remains the operator's decision.
