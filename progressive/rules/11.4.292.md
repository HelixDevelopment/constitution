### §11.4.292 — Reproduce first: every issue being fixed is REPRODUCED LIVE before any cause hypothesis is acted on or any fix is written; the reproduction is a recorded, closed-vocabulary RED with exact command, identifiers and symptom signature; the fix is proven by a GREEN on the same command and signature, rests on a root cause proven by evidence, and is covered by a deterministic live test; while reproduction is blocked a fix lands only as PROVISIONAL-DONE labelled UNREPRODUCED and never reaches VERIFIED-DONE (User mandate, 2026-11-03)

**Forensic anchor — operator mandate (2026-11-03, CRITICAL), as relayed by the conductor in the operator's words of intent (the operator's own message is not quoted here):** "every issue being fixed MUST FIRST be REPRODUCED LIVE, then systematically and deeply investigated and exhaustively debugged, with root-cause fixes covered by LIVE tests that confirm and verify everything deterministically against rock-solid machine-produced evidence, with no false or faulty results, no AI slop, no bluff. The CRITICAL and absolute priority is to REPRODUCE the reported issue FIRST and gather evidence and data. It must be an integral critical rule of the root constitution and its files (AGENTS.md, CLAUDE.md, others)."

**The gap this anchor closes (stated so it is not restated elsewhere, §11.4.227).** §11.4.43 orders a RED test before a fix; §11.4.115 puts that RED on the pre-fix artifact behind a polarity switch and makes RED and GREEN machine-written verdicts; §11.4.146 names the reproduce-first, same-test-confirms-fix, extend-to-all-cases workflow; §11.4.102 forbids a fix before the root-cause investigation; §11.4.199 fixes HOW a reproduction is driven (the exact sequence). None of them (1) requires the reproduction to be LIVE, on the target where the issue was reported, before anything else is done; (2) defines a machine-checkable reproduction RECORD with a closed result vocabulary and required evidence fields, carried by the item; (3) says what an item may and may not claim while reproduction is blocked or fails; (4) keys the RED-before and the GREEN-after runs to one recorded command, one target identity and one symptom signature. This anchor adds exactly those four and restates none of the others.

**(A) THE RULE — reproduce first, live.** For every issue being fixed (Type `Bug`, and any `Task` or `Feature` whose closure claims that a defect was removed), the FIRST work act is to reproduce the reported symptom LIVE and to record the reproduction (clause (C)). LIVE has the meaning of §11.4.289: on the real target where the issue was reported, that is the device, board, live rig or deployed service running the affected build; for a defect whose faulty code runs only on the host (a script, gate, generator or build step), the real code run on the host against the real input. Reading the report, the logs, the code and the history to find HOW to reproduce belongs to this step. Acting on a cause hypothesis (changing code, configuration or target state to test a theory) and writing a fix do not: both wait until the record exists. Reproduction is the critical and absolute first priority of the item, ahead of every other step; the evidence and data gathered while reproducing (triggers, boundaries, frequency, adjacent failure modes) are captured with it and feed the investigation (§11.4.146 STEP 1).

**(B) REPRODUCTION RESULT — closed set, four values.**

| Result | Meaning | Item label | A fix may land | The item may reach VERIFIED-DONE |
|---|---|---|---|---|
| `reproduced-live` | the symptom signature was observed TRUE on the live target and the RED was captured | `REPRODUCED` | yes | yes, through the clause (E) pair and the clause (G) live coverage test |
| `reproduced-host-fixture` | the symptom signature was observed TRUE by running the real faulty code on the host against a fixture (a captured input, a synthetic tree, a replayed recording, an emulator) instead of the live target | `REPRODUCED` when the record's surface is `host-only`; `UNREPRODUCED` when it is `live-target` | yes; only as PROVISIONAL-DONE while `UNREPRODUCED` (clause (D)) | only when the surface is `host-only` |
| `not-reproducible-with-evidence` | the reported sequence was driven on the live target at the reported build the declared number of times, with a positive control needle, and the signature never read TRUE (clause (F)) | `UNREPRODUCED` | no fix may be written against the symptom | no |
| `blocked-no-device-with-recorded-blocker` | the live target cannot be obtained and a blocker record exists (clause (C)) | `UNREPRODUCED` | only as PROVISIONAL-DONE (clause (D)) | no |

The record names the defect's surface: `live-target` (the symptom manifests on a device, board, live rig or deployed service) or `host-only` (the faulty code runs only on the host and the fixture is its real input class). A `host-only` surface declared for a symptom reported on a live target is a §11.4.6 bluff. An item with no record, or with a record that misses a required field, is `UNREPRODUCED`. There is no fifth result and no third label. The label is reported next to every other state label wherever item state is reported (Issues, summaries, roadmap, burndown, changelog, release notes, status messages, agent replies), for example `PROVISIONAL-DONE, UNREPRODUCED`.

**(C) THE RECORD — required evidence fields.** The result is carried on a `**Reproduction:**` line in the item body, written in the same commit or regeneration as the first status write after the attempt (the carrier pattern of §11.4.34 `Reopened-Details` and §11.4.290 `Verification`). Until the first attempt the line starts `**Reproduction:** none — UNREPRODUCED` (the shipped item template writes it for every `Bug`; `none` is the absence of a result, not a fifth result). The record:

`**Reproduction:** <result> — surface <live-target|host-only> — command <exact command, or the path of the recorded sequence> — red <evidence path> sha256 <hash> at <ISO-8601 timestamp> — ids <item id, run id, test id> — build <environment and build id, artifact fingerprint> — target <board serial | rig id | service fingerprint | fixture sha256> — signature <symptom signature>`

(1) **exact command**: byte-exact and replayable, including its environment variables and the §11.4.115 polarity flag at its RED value; it is the §11.4.199(4) recorded sequence. (2) **captured RED output**: machine-written by the harness (§11.4.115(F), §11.4.262), with path, sha256, timestamp and the item, run and test identifiers. (3) **environment / build id**: the artifact fingerprint read FROM the target the RED ran on (§11.4.200(3)), plus the host and harness version. (4) **target identity**: the board serial or another stable identifier (§11.4.111, never an enumeration ordinal), the rig id or the service fingerprint; for `reproduced-host-fixture`, the fixture's sha256. (5) **symptom signature**: the single machine-checkable predicate that reads TRUE while the defect is present (the negation of the §11.4.108(2) runtime signature), for example an exit status, a log-line pattern or a measured value outside a declared bound; the fix must flip exactly this predicate to FALSE. A `not-reproducible-with-evidence` record adds `attempts <N> — needle <control-needle evidence path>`. A `blocked-no-device-with-recorded-blocker` record adds `blocker <blocker record path or id> — unblock <condition>`, and the blocker record states WHAT, WHY (every self-resolution path tried: another board, a live rig, remote access), UNBLOCK CONDITION and WHO, per §11.4.21. A field that could not be captured is written `UNCONFIRMED: <reason>` (§11.4.6), and a record carrying an `UNCONFIRMED` field is not `REPRODUCED`.

**(D) BLOCKED REPRODUCTION — a fix may land only PROVISIONALLY and stays UNREPRODUCED.** While the result is `blocked-no-device-with-recorded-blocker`, or `reproduced-host-fixture` on a `live-target` surface, a fix MAY land as PROVISIONAL-DONE (§11.4.290) only if ALL hold: (1) the item carries the label `UNREPRODUCED` everywhere its state is reported; (2) the §11.4.290(C) verification job is scheduled and its FIRST step is the live reproduction: the RED on an artifact WITHOUT the fix (the pre-fix artifact, kept or rebuilt from the pre-fix commit, its fingerprint recorded), then the GREEN on the fixed artifact per clause (E); (3) the root-cause claim of the fix is written `UNCONFIRMED:` until that live RED exists (§11.4.6). The item CANNOT reach VERIFIED-DONE while `UNREPRODUCED`: no §11.4.33 closure value, no Fixed-file row, no place in a verified count. When the live run happens: a RED observed TRUE turns the record into `reproduced-live` and promotion proceeds by clause (E); a signature that stays FALSE on the pre-fix artifact turns it into `not-reproducible-with-evidence`, the item returns to `In progress` (it never claimed verified, so this is not a reopen) and clause (F) applies: the change is reported as a change without a proven defect, never as a fix. Neither outcome is contrary evidence in the §11.4.290(D) sense, and neither is promotion evidence.

**(E) RED BEFORE, GREEN AFTER — one command, one target, one signature.** The GREEN that promotes the item runs the SAME recorded command (only the §11.4.115 polarity flag flipped), on the SAME target identity (the same board serial, rig or service; for `host-only`, the same fixture sha256), evaluates the SAME symptom signature, on an artifact whose fingerprint differs from the RED artifact by the fix (both fingerprints read from the target, §11.4.200(3)), and reads the signature FALSE while its control needle proves the instrument would have read it TRUE. A GREEN on a different command, target or signature, a GREEN with no recorded RED, and a GREEN whose instrument is BLIND, INCONCLUSIVE or erroring (§11.4.201) are not a pair and promote nothing. The pair is recorded by extending the same line: `— green <evidence path> sha256 <hash> at <ISO-8601 timestamp> — artifact <fixed fingerprint>`. This IS the §11.4.115 / §11.4.146 STEP 2 pair, keyed so a machine can check it.

**(F) NOT REPRODUCIBLE — no fix against a symptom never observed.** A `not-reproducible-with-evidence` record requires: the reported sequence exactly (§11.4.199(1)) or a variant proven to reach the same precondition (§11.4.199(2)); the reported build, or a build proven to contain the reported code; the reported target class; the declared number of attempts (consumer DATA); and a positive control needle, that is a run where the signature is known TRUE (an injected fault, an older broken artifact, a planted input) and the instrument reads it TRUE. Without the needle the outcome is a BLIND instrument, not a non-reproduction (§11.4.201, §11.4.273). With it: no fix is written against the unobserved symptom, because a fix for a symptom never seen rests on no evidence (§11.4.6); the item is never closed with a fixed, implemented or completed value; the investigation widens the conditions (§11.4.7: same target, build, cycle position and load profile; §11.4.3 topology); and the item closes only through §11.4.90 with reason `not-reproducible` and this record as its triple-check evidence, the reporter being informed with the record.

**(G) INVESTIGATION, THEN A DETERMINISTIC LIVE COVERAGE TEST.** After the record and before the fix, the reproduction is the investigation instrument (§11.4.146 STEP 1) under §11.4.102 systematic debugging, auto-activated. The root cause is established as FACT: a causal chain whose every link carries captured evidence, closed by a decisive experiment that toggles the symptom signature by toggling the cause (cause removed: FALSE; cause restored: TRUE). A hypothesis, however plausible, is written `UNCONFIRMED:` and is not a root cause (§11.4.6). A regression is isolated against the last known good (§11.4.114, §11.4.242); a failed attempt goes to the shared attempt record (§11.4.267). The fix addresses the proven cause, not the symptom. It lands with a LIVE coverage test that: runs on the live target (on the device or on a live rig); is deterministic (§11.4.50, the declared number of identical verdicts); carries a control needle proving that its probe detects the signature (§11.4.273, §11.4.201); writes its own verdict (§11.4.115(F), §11.4.262); is registered as the permanent regression guard (§11.4.135); and is then extended to all cases (§11.4.146 STEP 3). A host-only substitute for the live coverage test is allowed ONLY when live execution is impossible (the surface is `host-only`, or no live target can exist where the test runs) and is then labelled `host-substitute` in the test, in its verdict and in every report that cites it; on a `live-target` surface a `host-substitute` test never carries the item to VERIFIED-DONE (§11.4.289, §11.4.226 class floor).

**(H) WHAT THIS ANCHOR DOES NOT CHANGE.** §11.4.6 (no guessing), §11.4.43 (RED first), §11.4.102 (root cause before fix), §11.4.115 (RED on the broken artifact, polarity switch, machine-written verdicts), §11.4.146 (the three-step workflow and its (D3) status custody), §11.4.199 (exact sequence), §11.4.289 (live evidence), §11.4.290 (PROVISIONAL-DONE and VERIFIED-DONE) and the §11.4.15 / §11.4.33 closure seams keep their full text; this anchor adds the live-first ordering, the record, the `UNREPRODUCED` cap and the pairing key. The Status closed set is not extended: the result rides on the `Reproduction:` line, as §11.4.290 rides on `Verification:`. A consuming project's own root-cause rule (for example a standing "root-cause every issue at its cause, no symptom-only closure" ruling) composes as DATA (§11.4.35) and is not weakened.

**Honest boundary (§11.4.6).** The gate shipped with this anchor proves the RULE is present exactly once, complete, mirrored in the four context carriers, indexed and generated into the group, rule file and catalog, and that the shipped item template (`scripts/reporting/report_item.sh`) and the two workable-item skills carry the `Reproduction:` field. It does NOT prove that any item carries a correct record, that a reproduction was live, or that a RED / GREEN pair matches: that item-level seam is the recommended gate `CM-REPRODUCTION-RECORD-BEFORE-FIX`, registered as deferral `OWED-GATE-174` and NOT claimed implemented (§11.4.227(A)). The workable-items engine in this repository does not yet validate the `Reproduction:` line. A reproduction proves that the symptom existed under the recorded conditions; it does not prove the root cause, which clause (G) establishes separately.
