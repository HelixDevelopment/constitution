### §11.4.235 — Build-and-deploy the moment source fixes are proven-correct (test-side hardening is a parallel stage, never a build gate) + post-deploy version increment + per-group flash-every-eligible-target live verification with a decimal-carry version increment (operator mandate, 2026-07-27; clause (E) added 2026-10-09)

**(A) BUILD-AND-DEPLOY THE MOMENT THE SOURCE FIXES ARE PROVEN-CORRECT — TEST-SIDE WORK IS A PARALLEL STAGE, NEVER A BUILD GATE.** The moment the SOURCE fixes of a batch are done AND proven-correct — proven-correct = the mandatory independent SOURCE-correctness review has returned a clean GO (§11.4.125/§11.4.142/§11.4.194 on the source diff, on the §11.4.209 Opus-`xhigh` substrate, iterated to zero-finding/zero-warning GO per §11.4.134) — the build MUST be triggered, pre-build + post-build tests EXECUTED (§11.4.108 layer-1 before, layer-2 after), and the artifact deployed. IN PARALLEL WITH the build AND the manual-QA session (§11.4.185), NEVER gating the build: (1) gate-instrumentation hardening + new-gate authoring (§11.4.110); (2) paired §1.1 mutations + four-layer §11.4.4(b) coverage + HelixQA Challenges; (3) "gates and checks of all kinds" (§11.4.96); (4) the re-review of THAT test-instrumentation work. The build's GO-SIGNAL is source-correctness alone; test-guard hardening (future-regression coverage) + its re-review are a deploy-independent parallel stage per §11.4.230(A). Holding the build sequentially — waiting for the test-instrumentation buildout + its re-review — when the source is already proven-correct is a §11.4.235(A) violation.

**(B) POST-DEPLOY VERSION INCREMENT + MANUAL-QA-DEPLOY CYCLE BOUNDARY (extended 2026-07-28 — operator mandate, verbatim: "Increase upcoming release to 0.1.5 since new cycle starts every time we deploy release for manual QA testing! This is how we will be working this ALWAYS! Extend the constitution!").** The moment image(s)/artifact(s) deploy, the version code/version is INCREMENTED (next build targets the next version; every deployed artifact carries a distinct, monotonic, greppable id — §11.4.151/§11.4.108/§11.4.200). Two deployments sharing one version id defeats per-deploy artifact identity → §11.4.235(B) violation. EVERY deployment of a release FOR MANUAL QA TESTING (§11.4.185) is a DEVELOPMENT-CYCLE BOUNDARY: the manual-QA deploy CLOSES the outgoing cycle and STARTS a NEW development cycle, and the version code/version is incremented AT THAT POINT — the new cycle's work targets the NEXT monotonic version (§11.4.151 project-prefixed naming preserved) — ALWAYS, the STANDING working model per clause (C), never a per-request opt-in. The manual-QA deploy is the canonical clause-(B) increment trigger (a deploy-for-manual-QA IS a deploy), and it SHAPES the §11.4.126 release-cycle framing: fixes for QA findings against the deployed artifact land in the NEW cycle on the NEW version id, never patched onto the already-QA-deployed version id. Starting a new cycle's work still targeting the QA-deployed version id is a §11.4.235(B) violation.

**(C) STANDING DEFAULT** (§11.4.126/§11.4.230/§11.4.103), never a per-request opt-in.

**(D) FINDING-LAYER CLASSIFIER — the decidable split clause (A) relies on, mandatory at every §11.4.125/§11.4.142/§11.4.194 review verdict (added 2026-10-03; research-derived from the §11.4.230 four-agent audit of this project's own SpecKit-004 T048 remediation saga).** Every finding a code-review verdict records (§11.4.115(F) machine-written) MUST carry exactly one `finding_layer` from the closed set `{source-defect | test-instrumentation | process-doc}` (a field DISTINCT from any other per-finding classification the review record already carries — e.g. this project's own `review_record.py` pre-existing `"class"` field `{mechanical | judgment | false-positive}` is a different axis and is unaffected): `source-defect` — the finding shows the SHIPPED artifact's own behaviour wrong, unsafe or exploitable as it will actually run, OR invalidates the evidence that proves THIS batch's fixes correct (their §11.4.115 RED→GREEN guard, §11.4.108 runtime signature, or covering test per §11.4.125(6) — a proving guard that cannot fail or whose reviewer-authored mutation survives per §11.4.194(6)(d) means the source is NOT proven-correct); `test-instrumentation` — the finding concerns only future-regression coverage, mutation-guard robustness or detection completeness of a guard/gate/meta-test whose protected behaviour was ALREADY proven, with no production decision path shown wrong and no proof-of-this-batch evidence invalidated; `process-doc` — labels, comments, citations or prose with no behavioural effect. The layer is recorded by the REVIEWER (§11.4.240/§11.4.249 producer≠verifier) — the producer MAY contest it only via a fresh review round and MUST NOT lower it unilaterally. A finding that cannot be decidably classified defaults to `source-defect` (the conservative-safe default per §11.4.201(4); secondarily §11.4.101 safe-reversible). §11.4.134 is NOT relaxed: every finding of every layer is still driven to a zero-finding, zero-warning GO in its own loop; clause (D) decides only which GO is the build GO-signal — a batch/slice is BUILD-ELIGIBLE when its `source-defect` findings reach that GO, while outstanding `test-instrumentation`/`process-doc` findings continue as their own tracked §11.4.197 item on a §11.4.230(A)/§11.4.103 parallel stream. A BATCHED review (one review spanning many slices/files) MUST record its verdict PER SLICE/FILE, never one undifferentiated batch verdict, so one slice's unresolved `test-instrumentation` loop cannot withhold build-eligibility from the other slices. Clause (D) applies prospectively; recorded verdicts are never rewritten or reclassified (§11.4.6/§11.4.268). Honest boundary (§11.4.6): this clause does not make classification easy or infallible — it makes it a required, recorded, reviewer-owned decision instead of an implicit one.

**(E) GROUP-COMPLETE ⇒ BACKGROUND FLASHABLE BUILD ⇒ FLASH EVERY AVAILABLE TARGET ⇒ LIVE VERIFICATION OF SANITY + EVERY CONTAINED ITEM, WITH A DECIMAL-CARRY VERSION INCREMENT ON EVERY DEPLOYED IMAGE (operator mandate, 2026-10-09, `IMPORTANT`; added 2026-10-09).** Verbatim operator mandate (2026-10-09): "As group by group of tasks from issues_01 gets done, we MUST create flashing image in the background, flash it to all available Orange Pi connected devices (see the list using adb devices command), and perform LIVE testing on devices of basic system major sanity and all workable items coming in into that particular build! We MUST after each flashing image we build and deploy (using our flashing scripts) regularly increase version or version code! Remember that once we get to 9 at some position we switch it to 0 and first left one we incresae by one! Example: 1.0.0-dev-0.0.9 -> 1.0.0-dev-0.1.0 !!! Make sure that all these mandatory RULES are universally applied acrtoss all projects and added into the constitution Submodule, commited and pushed to all upstreams!!!" (the project names and the device-listing command in that quote are the operator's own example, recorded verbatim; the rule below is generic and consumers supply those names as DATA per §11.4.35). The GAP this clause closes, stated precisely so it is not restated elsewhere (§11.4.227): clause (A) triggers the build on a source-correctness GO and clause (B) increments the version on every deploy; §11.4.230(B) exercises every available device concurrently during VALIDATION and §11.4.230(D.3) cuts a QA deliverable on a declared cadence; §11.4.200 target-isolates and read-back-verifies each single flash; §11.4.236 refuses a QA hand-off without a candidate-fingerprinted verdict — but none of them obliges a completed group's image to be FLASHED onto EVERY available target, none binds LIVE on-device verification of a basic major-sanity suite PLUS every workable item contained in that build, and none fixes HOW a version id is incremented (measured 2026-10-09 with a control-needled census over §11.4.235/.230/.236/.200/.119/.108/.151/.264: zero decimal-carry rule, zero "flash every available target" obligation, zero per-item live-verification binding; the only `carry` hits are the verb "carries"; positive control `version` = 18 hits in §11.4.235, negative control = 0). ALL of the following hold:

**(E.1) TRIGGER + BACKGROUND BUILD.** The moment a group / increment (§11.4.230(D.1) — a project-declared group of tracked items) holds its source-correctness GO per clauses (A)/(D), it is ELIGIBLE for a FLASHABLE image (the consumer's deployable artifact, §11.4.230(D.3)), and that image MUST be built in the BACKGROUND (§11.4.89 / §11.4.230(A) — the loop keeps progressing other items while it builds), through the consumer's official build entry point only, inside the §12 host-safety bounds (§12.6 / §12.11 / §12.12). WHEN the build is cut follows the consumer's declared §11.4.230(D.3) QA-build cadence and its coalescing rule — never a second, competing cadence: under the default `per-increment` trigger each GO'd group triggers a build; a build already in flight covers every group that reached GO before it started, a group reaching GO while it builds rolls into the NEXT build, and a build that fails covers nothing (its groups roll forward); a `periodic` / `whichever-first` consumer cuts at its declared trigger and every group that reached GO since the last covered build rides that build. A group without its GO is NOT built for flashing — clause (A) is unchanged.

**(E.2) FLASH EVERY AVAILABLE TARGET.** When the image exists it MUST be deployed, through the consumer's official flash/deploy tooling only, to EVERY AVAILABLE target device. A device is AVAILABLE for this image only when ALL THREE hold: (i) it is ENUMERATED fresh at flash time by the consumer-declared device-listing command (DATA per §11.4.35, e.g. `adb devices`), keyed by stable serial (§11.4.111), never a remembered or hand-typed list (§11.4.6); (ii) it is ELIGIBLE for this image — its product / hardware class matches the image's target per the consumer-declared eligibility map (DATA per §11.4.35; an image is never flashed onto a board of a different product line or hardware variant); and (iii) its device LEASE is acquired for this deploy under the §11.4.176(B) / §11.4.119 single-owner device lock (all-or-nothing, non-blocking, TTL-reaped — the consumer's lock mechanism). An enumerated device that cannot be exercised is recorded per device by one of TWO DIFFERENT mechanisms, never conflated, and in neither case is it reflashed out from under its owner or silently dropped. (1) An honest §11.4.69 SKIP-with-reason (§11.4.3) — used ONLY when the device is genuinely absent or ineligible; its reason code MUST be a member of the consumer's §11.4.69 CLOSED reason set (this clause mints NO new code and does NOT extend that set; a helper that enforces the set turns an out-of-set code into a FAIL, §11.4.69): no device enumerated ⇒ `hardware_not_present`; enumerated but ineligible for this image ⇒ `topology_unsupported`. (2) DEFERRED — a device whose lease is held by another stream is NOT a §11.4.69 SKIP at all, because it IS present and eligible: recording it as `hardware_not_present` would assert that a present board is absent, exactly the misstatement §11.4.69 / §11.4.6 forbid. It is recorded in the DEPLOY RECORD as `DEFERRED`, with the deploy-record field `device_leased_by_other_stream` naming the holder. The specific cause always travels ALONGSIDE the code — in a deploy-record field, or in the SKIP's description text where the consumer's SKIP helper has no field for it (the §11.4.69 helper takes a description and a reason code and nothing else; no `detail` sub-field exists). A DEFERRED device is retried at the next covered build, never waited on unboundedly, and the retry is BOUNDED: after N consecutive DEFERRED builds of the same device (N is consumer DATA per §11.4.35 / §11.4.267(E)), the stall escalates per §11.4.267(D) — a tracked §11.4.197 item naming the device and the holder, surfaced in every §11.4.97 report until resolved, and routed to a recorded operator decision (§11.4.66) — never an indefinite silent re-deferral. Each flash is target-isolated and verify-after-write per §11.4.200 (the deployed identity read back FROM each intended target). Independent devices are tested CONCURRENTLY; genuinely shared exclusive resources (one flash bus, one single-eligible-target flash tool, one power controller, one sink) serialise per §11.4.119 / §11.4.230(B). Devices count as independent only when their CONTROL TRANSPORTS are independent as well: legs that share one host-side transport daemon whose recovery path restarts that daemon (one debug-bridge server that a recovery step kills and restarts, for example) share an exclusive resource, so a flash or recovery leg on that daemon serialises with every live-test leg on the same daemon — unless each device is given its own daemon instance AND that per-device isolation has been proven to work on that host with captured evidence before anything relies on it (§11.4.6); an unproven isolation is treated as shared. An available device that cannot be flashed or verified is recorded per device as a FAIL or an honest SKIP-with-reason (§11.4.3), never silently dropped; the deploy record lists the enumerated, eligible, leased, flashed, and read-back-verified serials, plus every per-device SKIP reason code with its cause and every DEFERRED device with its holder.

**(E.3) LIVE VERIFICATION ON EACH FLASHED DEVICE.** On each verified device run (a) the consumer-declared basic major-sanity suite (at minimum: boot completed, core services up, no crash/hang loop — the suite named as DATA) AND (b) a LIVE test of EVERY workable item contained in that build — the item set recorded in the hand-off per §11.4.230(D.5) — each producing captured machine evidence on that device (§11.4.262 / §11.4.69 / §11.4.108 runtime layer); metadata-only, config-only, or grep-only PASS is forbidden (§11.4). An item whose live verification is genuinely device- or topology-gated is SKIP-with-reason PER ITEM (§11.4.3 / §11.4.69 reason code), never folded into a group-level PASS. A FAIL on any device is linked to the affected item; an item already in a terminal state is re-opened, while an item still open is only linked (§11.4.214 — 're-opening an open item' is undefined); a huge FAIL triggers §11.4.129.

**(E.4) LATENT BINDING + NO AVAILABLE DEVICE ⇒ HONEST SKIP.** The device legs — (E.2), (E.3), and the zero-device rule of this clause — bind every consumer that HAS an official flash/deploy entry point for a device-targeted artifact, or that has bound a deploy ledger for such an artifact to the §11.4.235 gates (the §11.4.96 / §11.4.275 latent-binding pattern); whether the consumer has declared its device-listing command does NOT decide the binding. A bound consumer MUST declare that command; a bound consumer that has not declared it is in a CONFIG ERROR — a blocking result, never N/A and never a reason to skip the device legs — because a project must not opt out of flashing its devices by leaving the command undeclared. Only a consumer with NO device-targeted flash/deploy entry point and NO deploy ledger bound for a device-targeted artifact (no flashable device tier at all) records the flash and live-verification legs as honest N/A (`feature_disabled_by_config`), never a fabricated device run, and the obligation binds the moment either condition becomes true. When a declared enumeration yields zero AVAILABLE targets (none enumerated, or every enumerated device ineligible or leased per (E.2)), the flash and live-verification legs record what (E.2) prescribes — a §11.4.69 SKIP-with-reason (`hardware_not_present`, cause `no_target_device_attached` carried as (E.2) describes, or `topology_unsupported` per ineligible device) and a DEFERRED record per leased device — plus a tracked §11.4.197 item for the owed live run — never a faked PASS and never a claim that the build was verified on hardware. The build itself still completes and is retained.

**(E.5) DECIMAL-CARRY VERSION INCREMENT ON EVERY DEPLOYED IMAGE.** Every image built and deployed under this clause carries a NEW version id per clause (B). SCOPE — universal in force, fenced in reach (a conservative-safe reading per §11.4.6 / §11.4.201(1), recorded as awaiting operator confirmation): the carry rule binds the dotted numeric group that the consumer's ONE version tool owns under its DECLARED version scheme (DATA per §11.4.35), and applies only where that declared scheme is POSITIONAL-DIGIT style (every non-leftmost position a single decimal digit, as in the operator's own example); a consumer on Semantic Versioning, Calendar Versioning, or any scheme whose positions are unbounded counters or dates declares that scheme and is NOT subject to the carry (`1.2.10` is correct SemVer) — that exemption exists ONLY by explicit declaration backed by a recorded operator decision (§11.4.66) naming the consumer — a declaration without that record is UNDECLARED (the gate requires the declaration to cite the record; whether the record exists and says so stays a review obligation the gate cannot verify, §11.4.6): once a consumer binds a deploy ledger, declaring its version scheme is MANDATORY, and a bound ledger with no declared scheme is UNDECLARED, a distinct result that a release seam consuming the gate MUST treat as blocking, exactly as a FAIL (§11.4.135) — until such a seam exists that is an obligation on the seam, tracked as a §11.4.197 item by each consuming project, not an enforced block — never a silent skip; a consumer that has bound no ledger at all records an honest SKIP whose result is mechanically distinct from a PASS (its own result code and machine-readable verdict, §11.4.1), BUT a consumer bound by (E.4) MUST bind a deploy ledger for its device-targeted artifact, so for such a consumer the no-ledger SKIP is a CONFIG ERROR at the release seam, never N/A — the SKIP stays legitimate ONLY for a consumer NOT bound by (E.4) — and enforcement over a deploy ledger applies only to rows AFTER the consumer-declared adoption marker (the §11.4.224(E) adoption-fence precedent) — ids minted before adoption are history and are never retroactively failed. Within that scope every version id obeys ONE POSITIONAL-DIGIT ID GRAMMAR, implemented identically by the consumer's version tool and by the gate: (i) in EVERY dotted numeric group of the id — any run of two or more dot-joined decimal positions, not only the owned one — every non-leftmost position is a single digit 0..9 and the leftmost has no leading zero (so a dotted suffix or build-metadata group can never hide a no-carry group: `…-0.0.10-rc.1.2` is in violation); (ii) no two numeric runs are joined by a single dash (`0.0-9`, `0.0.1-1`), because which group is owned would be ambiguous; (iii) the OWNED group — the dot-joined positions that END the id after its last dash, or the whole id when it has no dash — has no leading zero in any position (a single-position owned group such as `-dev-7` may grow). The tool refuses to bump any id that violates (i)–(iii) or does not end in its owned group; the gate fails any in-scope id that violates (i) or (ii) or whose owned group violates (iii) — an id ending in a non-numeric suffix (`-rc1`) has no owned group and is held to (i) and (ii) alone. The next id is computed by the DECIMAL CARRY rule: in that owned dotted numeric group (the trailing dot-joined decimal positions after any tag prefix and pre-release separator), every position except the leftmost holds a single digit 0..9; incrementing adds 1 to the LAST position; a position that would exceed 9 becomes 0 and carries +1 into the next-left position; the carry propagates as far as needed; the leftmost position absorbs the final carry and may grow; the tag prefix (§11.4.151), pre-release separators, and every non-group character are preserved verbatim. Worked examples: `1.0.0-dev-0.0.8 → 1.0.0-dev-0.0.9`; `1.0.0-dev-0.0.9 → 1.0.0-dev-0.1.0`; `1.0.0-dev-0.9.9 → 1.0.0-dev-1.0.0`; `0.9.9 → 1.0.0`; `9.9.9 → 10.0.0`. A non-leftmost position above 9 (e.g. `0.0.10`) is the no-carry form and a violation. A rollover is a CARRY, not a reset and not a skip: `0.0.9 → 0.1.0` is the immediate successor, so the §11.4.151 "never reset, never skipped" discipline holds — no id is reused and none is jumped; where a consumer also derives an integer version CODE from the id, its encoding MUST be strictly monotone over carried ids (a positional-weight code is), and an encoder whose domain cannot represent the next carried id MUST refuse loudly rather than wrap or collide (§11.4.6) — widening that domain is tracked work, never a silent truncation. The consumer's ONE version tool (DATA per §11.4.35) is the single implementation (§11.4.28 / §11.4.251); a hand-rolled or hand-edited increment is a violation.

**(E.6) HONEST BOUNDARY (§11.4.6).** Clause (E) makes deploying and live-verifying every completed group mandatory and mechanical. It does NOT replace §11.4.185 manual QA, the §11.4.40 tag preconditions, or the §11.4.236 readiness verdict for a QA hand-off; it never flashes a build lacking its review GO (clause (A)); it never authorises bypassing the consumer's official flash tooling or power-cycling hardware outside its authorised recovery path (§11.4.133 / §11.4.144); and a live PASS on the available devices proves those devices only — hardware variants not attached are an enumerated gap (§11.4.118), never an implied PASS.

**Honest boundary for clauses (A)–(E) (§11.4.6):** this anchor relocates the TEST-INSTRUMENTATION re-review + gate/check hardening OFF the build critical path; does NOT weaken any substantive gate. The SOURCE-correctness review (§11.4.125/§11.4.142/§11.4.194 Opus-`xhigh` §11.4.209 → GO §11.4.134) STILL PRECEDES + gates the build (it IS "source proven-correct"); pre/post-build tests (§11.4.108 L1-2) run at their seams; §11.4.185 manual-QA-final un-weakened; §11.4.129/§11.4.40 un-weakened. "Test-side work is parallel, never a build gate" is bounded to future-regression instrumentation — a check that proves the SHIPPED artifact wrong is a source/artifact-correctness gate (§11.4.108 L1-2), stays on the critical path. Clause (D) supplies the mandatory classification mechanism this boundary's own test presupposes — a review that never classifies its findings has not actually applied this honest boundary, it has merely stated it. Clause (E) adds deployment and live-verification obligations on top of (A)–(D) and weakens none of them: its own boundary (E.6) applies in full — no manual-QA, tag, or readiness gate is replaced, no un-GO'd build is flashed, no device is flashed outside its eligibility or lease, and a live PASS proves only the devices it ran on.
