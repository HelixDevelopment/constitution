### §11.4.230 — Parallelized-pipeline methodology: build↔validate overlap + affected-stages-only re-run + parallel multi-device testing/recording + fan-out-subagents-always + incremental delivery granularity with a declared QA-build cadence + a quick visible first deliverable with a hardening status and ledger tracked to production readiness (research-derived, 2026-07-26; clause (D) added 2026-10-04; clause (E) added 2026-10-12)


Forensic motivation (genericised): the sequential pipeline shape — build FULLY completes → THEN validation begins → on ANY discovery, restart the WHOLE cycle from scratch → all devices tested one-at-a-time — serialises the operator's wall-clock onto build latency + one-device-at-a-time evidence gathering, so a multi-hour containerised build followed by serial per-device validation and a from-scratch restart-on-discovery makes time-to-a-manual-QA-capable-release a multiple of what the genuinely-parallel work requires. §11.4.58's PWU pipeline already overlaps Stage 1 of round N+1 with Stages 4–5 of round N; §11.4.89 already backgrounds long tests; §11.4.103 already mandates ≥3 auto-backfilled parallel streams; §11.4.119 already partitions shared hardware by single-owner; §11.4.128/§11.4.144 already mandate always-on recording + availability-following. §11.4.230 BINDS those into one operating discipline and adds the five invariants they did not each state on their own: (A) the build↔validate CONCURRENCY seam + affected-stages-only re-run-on-discovery, (B) all-devices-concurrent + worker-pool recording/processing, (C) fan-out-subagents as the standing default, (D) incremental delivery granularity + a declared QA-build cadence (added 2026-10-04), (E) a quick visible first deliverable ordered first on the critical path + a machine-computed per-deliverable hardening status and ledger tracked to production readiness (added 2026-10-12). It is the parallelization capstone the way §11.4.103 is the continuous-parallel-stream capstone — a strengthening bind, never a weakening.

**(A) PIPELINE-OVERLAP PARALLELIZATION.** Validation/verification work MUST run CONCURRENTLY WITH the build wherever a validation stage does NOT depend on the build's own not-yet-produced artifact — never deferred until the build finishes when it could have run alongside it. Deploy the moment the build is done (build-completion is the deploy trigger, per §11.4.121 no-commit-while-build-writes-tracked-artifacts + §11.4.108 artifact-must-exist ordering — the deploy waits for the artifact, the deploy-independent validation does not). Concretely, WHILE a build runs, the following run in parallel per the §11.4.96 SAFE-during-build catalogue: pre-build source-layer gates + meta-test mutation sweeps + coverage/clash checks (§11.4.110), the §11.4.125/§11.4.142/§11.4.194 independent code-review on the batch's SOURCE, doc/DB sync (§11.4.106), and on-device validation of the PRIOR build (device-independent of the in-flight build, §11.4.119). On any NON-huge-blocker discovery, the cycle MUST: (1) bump the version code (a new, distinctly-identifiable candidate artifact — never re-use the failing artifact's id, §11.4.111 stable-name + §11.4.200 target-identity); (2) fix at the proven root cause (§11.4.102 systematic-debugging first, §11.4.115 RED-on-the-broken-artifact); (3) RE-RUN ONLY THE AFFECTED STAGES, PARALLELIZED — the stages whose inputs the fix changed (its own targeted validation FIRST per §11.4.130, then the affected regression set), NOT a serial restart-from-scratch of the entire cycle. The explicit efficiency target is a **4–5× reduction in time-to-a-manual-QA-capable-release** versus the fully-sequential shape — a measured target, tracked as build-and-validate wall-clock deltas (§11.4.24 build-resource stats), never an assumed one (§11.4.6). **HONEST BOUNDARY (§11.4.6 / §11.4.108 / §11.4.120):** the CURRENT build's ARTIFACT-layer (§11.4.108 layer 2) and RUNTIME-ON-CLEAN-TARGET-layer (layer 3) validation CANNOT precede its own artifact — a gate whose precondition is the build's output belongs at a post-build seam, never overlapped onto authorship (§11.4.120 seam-placement; §11.4.69 `artifact_not_yet_built`). "Concurrent with the build" therefore means the deploy-INDEPENDENT stages overlap; the CURRENT-artifact runtime validation begins the moment that artifact exists, in parallel across devices per (B). **"Affected-stages-only re-run" is bounded to NON-huge-blocker discovery**: a HUGE BLOCKER (release-blocking-severity defect / regression invalidating the cycle / blast radius reaching the batch's other fixes) still triggers the §11.4.129 STOP → fix-all → full-RESTART protocol (restart, never resume) — §11.4.230(A) does NOT weaken §11.4.129, §11.4.40 full-suite-retest-before-tag, §11.4.130 validate-the-fix-first, §11.4.132 risk-ordered validation, or §11.4.185 manual-QA-final; it narrows the from-scratch restart to exactly the cases those anchors require it, and parallelises everything else.

**(B) PARALLEL MULTI-DEVICE TESTING + RECORDING/PROCESSING.** Every available, reachable test device MUST be exercised CONCURRENTLY — one validation stream per device, never one-device-at-a-time when the devices are independent — each stream the SINGLE EXCLUSIVE OWNER of that device's exclusive resources per §11.4.119 (the owner drives; any concurrent stream targeting the same device is read-only), so per-device evidence is never cross-contaminated (§11.4.119 evidence-integrity). Every device is ALWAYS-RECORDED per §11.4.128 (non-invasive, side-effect-free, deterministic layout) and AVAILABILITY-FOLLOWED per §11.4.144 (a dropped device logs an honest offline event + reconnect-and-resume, never a silent corpus hole, never a faked continuity). Recording CAPTURE + ANALYSIS/PROCESSING MUST be fanned out through a BOUNDED WORKER-POOL (a Go worker-pool or platform equivalent) so N devices' recordings are captured + analysed in parallel and per-device evidence never serialises onto a single processor — the pool bounded by §12.6 memory + §12.12 thread headroom. Per-device PASS cites its own captured-evidence artefact (§11.4.5/§11.4.69/§11.4.107) on a CLEAN/fresh deployment (§11.4.108 runtime-signature, §11.4.200 verify-deployed-artifact-identity-per-device); the highest-risk / most-reopened cases (§11.4.132/§11.4.189) get the deepest scrutiny FIRST on every device. **HONEST BOUNDARY (§11.4.6):** genuinely-shared exclusive resources (one HDMI/audio sink, one media-playback path) serialise per §11.4.119 single-owner-over-time even across devices; "all devices concurrent" means independent devices, never two owners of one exclusive resource.

**(C) FAN-OUT-SUBAGENTS-ALWAYS.** Subagent fan-out (§11.4.20/§11.4.70 subagent-driven; §11.4.187 multi-track ruler; §11.4.192 auto-backfill) is the STANDING DEFAULT for EVERY genuinely-parallelizable effort — batch investigation, test-authoring, gate-authoring, per-device validation (B), per-PWU development (§11.4.58), doc/research work — not a per-request opt-in and not reserved for "big" tasks. A parallelizable effort executed monolithically in the foreground when a fan-out path exists is a §11.4.230(C) violation (the §11.4.94/§11.4.97/§11.4.103 zero-idle discipline applied to HOW work is dispatched, not only WHETHER it runs). **HONEST BOUNDARY (§11.4.6 / §11.4.183):** "always fan out" is BOUNDED by (1) genuine parallelizability (contending/redundant/serially-dependent subagents are NOT fan-out — they are waste, and spawning them is NOT maximization per §11.4.183 maximum-USEFUL-throughput); (2) §12.6 60% memory ceiling; (3) §12.12 `RLIMIT_NPROC` thread headroom; (4) §11.4.58 ≤6 concurrent-agent cap; (5) §11.4.119 single-resource-owner (two subagents may not both drive one exclusive device); (6) critical-state sequencing (commits/pushes/tags stay serial per §11.4.88/§11.4.113). The bar is maximum USEFUL parallel throughput, never agent count; fan-out that exceeds a host-safety ceiling or contends a single resource is a violation, not compliance.

**(D) INCREMENTAL DELIVERY GRANULARITY + DECLARED QA-BUILD CADENCE — a long-running spec/feature ships every already-proven-correct increment as it clears its own bar, never withholding delivery until the WHOLE spec/feature is done (operator mandate, 2026-10-04, `CRITICAL`; research-derived; added 2026-10-04).** Verbatim operator mandate (2026-10-04): "All work we do, especially SpecKit specs, gets incorporated right away. Fully deterministic validation/verification tests of all supported test types relying on machine-produced evidence get incorporated too, aiming to cover everything critical. All intensive testing (gates, checks, fixing, polishing) keeps running in BACKGROUND continuously until fully done. IN PARALLEL we keep building specs one by one, phase by phase, story by story, task by task. We get fast delivery results and AS SOON AS POSSIBLE builds that can be handed to QA teams for manual testing RIGHT AWAY, while in parallel all testing/fixing/polishing/improvement continues exactly as it would anyway. We do NOT wait for all of that to finish first — that can take days [...]. QA reports discovered issues; background agents keep working until everything is absolutely flawless. As background work progresses and fixes/improvements land in the main codebase, we keep producing REGULAR builds periodically delivered to QA teams for ongoing full manual testing. It is critical that background agents keep ALL workable items, documentation, and other materials in sync so nothing ever goes out of date." Forensic anchor (genericised, FACT): in one consuming project a multi-phase spec had RED tests drafted for every phase and many source slices independently reviewed to a source-correctness GO, yet nothing reached QA for days, because delivery was implicitly held at the WHOLE-SPEC boundary while ONE slice's iterate-to-GO review loop ran past forty rounds — the finished, proven work of every other slice sat undelivered. The GAP this clause closes, stated precisely so it is not restated elsewhere (§11.4.227): clause (A) overlaps validation with the build of ONE candidate; §11.4.235(A) makes a batch build-eligible on source-correctness alone; §11.4.235(D) makes that eligibility PER SLICE inside a batched review — but none of them obliges an ELIGIBLE increment to actually be DELIVERED before the rest of its spec completes, none sets a delivery CADENCE, none says how an incomplete spec stays safe to ship, and none binds the hand-off to tracker truth. Build-eligibility that is never exercised is the same withheld delivery under a different name. ALL of the following hold:

**(D.1) THE DELIVERY UNIT IS THE INCREMENT, NOT THE SPEC.** A spec / feature / epic decomposed into phases / stories / tasks (vertical, independently testable slices per the §11.4.148 SLICING extension — Small + Testable) MUST integrate each increment into its INTEGRATION BRANCH — the trunk for `main`-targeted work, or the `feat/` / `product/` / `flavor/` branch (§11.4.195) the increment actually lives on for branch-scoped work — and make it part of the next QA deliverable (D.3) cut from that branch, the moment THAT increment holds its OWN source-correctness GO per §11.4.235(A)/(D). When an increment exists on MULTIPLE coexisting integration branches — for example both a `product/*` AND a `flavor/*` branch per §11.4.195(A) — EACH branch is independently obligated under (D.3)'s own per-branch cadence: the increment's delivery obligation is evaluated separately per branch it lives on, never as a single ambiguous "the branch". A QA build MAY be cut from a `feat/` / `product/` / `flavor/` branch. For a `feat/` branch that QA build IS the live-manual-testing vehicle §11.4.195(B) requires BEFORE the branch may merge to trunk, so the feature-branch QA build is the PRECURSOR to trunk-landing, never a consequence of it; a `product/` / `flavor/` line, which never merges to trunk the standard way (§11.4.195(C)), receives its cadence builds from its own branch. Clause (D) relaxes neither §11.4.195(B) (no `feat/` merge to trunk before live manual QA) nor §11.4.195(C), and a later merge of the branch to trunk still follows §11.4.195 / §11.4.188. Withholding an already-build-eligible increment solely because OTHER increments of the same spec are unfinished, or because its own or another increment's `test-instrumentation` / `process-doc` loops (§11.4.235(D)) are still open, is a §11.4.230(D) violation. An increment WITHOUT its own source-correctness GO is not deliverable — incremental delivery is never a licence to ship unreviewed or unproven work.

**(D.2) INCOMPLETE-SPEC, SAFE DELIVERABLE.** Shipping an increment while its spec is incomplete MUST leave the deliverable correct on every path a user or QA tester can reach: EITHER the increment is a complete, independently valuable vertical slice, OR the unfinished surface is LATENT — unreachable by construction, behind a release toggle (P. Hodgson, "Feature Toggles", martinfowler.com, 2017: "Release Toggles allow incomplete and un-tested codepaths to be shipped to production as latent code which may never be turned on"), or behind branch-by-abstraction (trunkbaseddevelopment.com: a technique "to effect a 'longer to complete' change in the trunk"). A toggle is a PERMITTED mechanism, never a mandated one (consistent with §11.4.265's own statement that it mandates none), and it is inventory with a carrying cost (Hodgson: "Savvy teams view their Feature Toggles as inventory which comes with a carrying cost"): every release toggle carries a tracked §11.4.197 removal item and a consumer-declared expiry (§11.4.35), and a toggle past its expiry is a §11.4.261 finding. A toggle that needs to outlive its expiry — for example because its latent path's (D.4) hardening loop legitimately runs many rounds — is extended ONLY through a §11.4.271 waiver (rostered non-producer authoriser, a new unelapsed expiry, a named tracked item), never by a silent expiry edit, by enabling the still-unproven path, or by deleting finished work. A latent path is NOT an advertised capability (§11.4.266) until it is enabled and proven.

**(D.3) A DECLARED QA-BUILD CADENCE, NOT A ONE-SHOT.** Every project declares as DATA (§11.4.35) its QA-build trigger: `per-increment` (each build-eligible increment landing on its integration branch, D.1), `periodic` (a fixed interval — the release-train pattern; SAFe's "Develop on Cadence. Release on Demand" separates the development rhythm from the release decision), or `whichever-first`; a project that declares nothing gets `per-increment`, the safe default (§11.4.101). A `periodic` or `whichever-first` interval MUST be recorded as DATA together with its written justification (§11.4.35) and stated in every QA hand-off record (D.5), so an interval long enough to defeat this clause is visible rather than silent; this clause sets no numeric maximum — any such cap is an operator decision (§11.4.66). Whenever an integration branch (D.1) holds build-eligible content not yet in a QA build cut from that branch and the declared trigger has fired, a QA deliverable MUST be cut from that branch and handed to QA for ongoing manual testing (§11.4.185). Builds COALESCE: a QA build already in flight covers every increment that had landed on its branch before that build started, and increments landing WHILE it is in flight roll into the NEXT build rather than each demanding a fresh one — the obligation is that eligible content never waits past the next build, not one build per increment. A build that FAILS, or is REFUSED at §11.4.236, covers NOTHING — its increments roll into the next build. "Completed" in this clause and in its two amended gate contracts (D's recommended gates, below) means HANDED TO QA: a build provides coverage only once it has genuinely been handed to QA for manual testing, never merely once the build process itself exits successfully. Each such deliverable is a §11.4.235(B) cycle boundary with its own monotonic version increment (§11.4.151), passing §11.4.236 readiness on its own candidate fingerprint, and built once then promoted (§11.4.264). The §11.4.236 "mandated validation" for a cadence build is AT MINIMUM the source-correctness GO plus the pre/post-build gates of §11.4.235(A), PLUS every operator-declared blocker bound to the QA-deploy seam per §11.4.236 and any §11.4.239 critical-invariant scenarios the increment touches — NOT the open background-hardening backlog, which by §11.4.235(A) never gates a build. "Deliverable" is project-defined DATA (§11.4.35): a binary, a container, a device image — or, for a dev-tooling / governance feature, the feature's own demonstrable, testable state at a fingerprinted commit; no artifact form is implied by this clause.

**(D.4) CONTINUOUS BACKGROUND HARDENING THAT NEVER BLOCKS THE NEXT INCREMENT.** Test-instrumentation hardening, gate / check / mutation authoring, polishing, and the fixes for QA-reported findings on ALREADY-delivered increments run as standing background streams (§11.4.103 / §11.4.192 / clause (C)), each a tracked item (§11.4.197) driven to its own zero-finding GO (§11.4.134 — not relaxed), landing on its integration branch (D.1) as it reaches GO and riding the NEXT cadence build cut from that branch. They never gate a LATER increment's build-eligibility, with two exceptions that follow from existing anchors rather than relax them: an open `source-defect` finding (§11.4.235(D)) in code the later increment touches or depends on is a `source-defect` of that later increment too; and a huge blocker still triggers §11.4.129 STOP → fix-all → full restart.

**(D.5) NEVER-STALE TRACKING IS A PRECONDITION OF EVERY HAND-OFF, NOT AN AFTERTHOUGHT.** With many increments and many background streams in flight at once, the existing sync machinery — §11.4.106(F) write-seam doc/DB sync, §11.4.229 live tracker, §11.4.202 / §11.4.208 / §11.4.210 intake and request history, §11.4.148 item integrity, §11.4.197 completion — applies at EVERY increment landing and EVERY cadence build (cited, not restated). Each QA hand-off records the deliverable's fingerprint and the exact set of tracked items it contains; a hand-off whose tracker or documents disagree with the deliverable (an item marked done whose fix is not in that build, or a fix in the build that no item records) is a §11.4 PASS-bluff at the delivery layer.

**(D.6) QA FINDINGS ON EARLY INCREMENTS ARE STILL COVERAGE ESCAPES.** Earlier, more frequent QA builds surface defects earlier; they do NOT make manual QA the discovery mechanism. Every defect manual QA finds on an increment build triggers the §11.4.238(C) coverage-escape audit and a new automated check, exactly as for a release candidate.

**(D) honest boundary, research grounding, and gates.** Honest boundary (§11.4.6): clause (D) changes WHEN and HOW OFTEN proven-correct work reaches QA; it does NOT change what gates a release candidate. It does not weaken §11.4.129 (huge-blocker full restart), §11.4.40 (full-suite retest before a release TAG — a cadence QA build is not a tag), §11.4.185 (manual-QA-final terminal gate for a release), §11.4.236 (readiness verdict per candidate), §11.4.264 / §11.4.265 (build once and promote; progressive delivery), §11.4.134 (every finding of every layer still driven to GO), or §11.4.235(D)'s conservative-safe default (an unclassifiable finding is a `source-defect` and does block). It does not prove any increment correct — that stays §11.4.108 / §11.4.235. Research grounding, stated honestly: DORA's "Working in small batches" capability (dora.dev) — "break them down into work units that can be completed independently and in short timeframes", with dark launching / feature toggles named as the way to deploy incomplete features hidden from users; Hodgson's toggle taxonomy and toggle-as-inventory discipline (quoted in D.2); branch-by-abstraction (quoted in D.2); SAFe's "Develop on Cadence. Release on Demand" (D.3); and GitHub Next's 2026 "Continuous AI" / Agentic Workflows technical preview, which its principal researcher calls "the agentic evolution of continuous integration" — scheduled or event-triggered agent loops for recurring work such as CI-failure investigation and documentation-drift fixing, cited here only as industry direction for (D.4)/(D.5), not as an adopted mechanism. No single published methodology was found that combines per-increment QA delivery with continuously running agent hardening streams; that composition is this clause's own synthesis, not a claim of prior art. Classification: universal (§11.4.17) — consumers supply the cadence trigger, interval, toggle mechanism and expiry policy, and the deliverable form as DATA per §11.4.35. **(E.1) FIRST-DELIVERABLE CRITICAL PATH, SCHEDULED FIRST.** When a scope starts (a spec, a declared group of tracked items, or any consumer-declared delivery scope — DATA per §11.4.35), the work that makes its FIRST increment build-eligible and deliverable is the CRITICAL PATH and is scheduled FIRST: the increment's source fix; its source-correctness review to GO (§11.4.235(A)/(D), on the §11.4.209 substrate, bounded by §11.4.276); the pre/post-build gates and every operator-declared QA-deploy blocker §11.4.236 requires for that candidate; the build; the flash; and the §11.4.235(E) live sanity and per-item verdicts. Deliverable-independent work — every entry class of the (E.3)(b) ledger that the seams of (E.2) do not require for a QA build — MUST NOT be placed ahead of that path. It STARTS IN PARALLEL from the first moment of the scope (clause (C), §11.4.103, §11.4.183, §11.4.192) as background streams that never sit on the critical path. "Quick" therefore re-orders WHEN hardening COMPLETES relative to the first deliverable; it never decides WHETHER hardening runs and never makes hardening wait to START. The first deliverable MUST contain at least one increment holding its own source-correctness GO (D.1) and MUST exercise a user-visible behaviour of that increment on the target (the "visible" in the mandate) — an empty, trivial or no-behaviour-change build delivered only to stop a clock is a §11.4.6 fabrication. A consumer's own stricter precondition on building (for example a mandatory specification-and-review workflow that must reach GO before any build) still applies in full and is part of the critical path, never shortened by this clause.

**(E.2) EVIDENCE IS NEVER TRADED FOR SPEED — QUICK IS NEVER UNVERIFIED.** A quick deliverable passes EXACTLY the same seams, with the same strength of evidence, as any other QA build; all of these bind unchanged and are cited, not restated: the source-correctness GO (§11.4.235(A)/(D), §11.4.209, §11.4.134, §11.4.276); §11.4.108 artifact-layer and runtime-on-clean-target-layer evidence for the delivered fingerprint; §11.4.236 readiness; the §11.4.235(E) per-device live sanity and per-item verdicts; §11.4.5 / §11.4.262 machine-created evidence; §11.4.50 exactly as that anchor states it — "Every test that PASSes MUST have been executed N times (default N=3, N=10 for cycle-validation suites) against the same firmware MD5 + same device + same topology and produced IDENTICAL PASS in every iteration." — and §11.4.201(6)-(12) / §11.4.273 control-needled nulls. Nothing in this clause lowers, skips, defers, samples or narrates any of these. A deliverable that reached QA by weakening one of them is not a quick deliverable — it is a §11.4 PASS-bluff, and §11.4.236 refuses it. What a quick deliverable MAY still lack is EXACTLY the set of entries the (E.3)(b) ledger can hold — the ledger's entry classes are the one and only list of permitted gaps, so the two lists are identical by construction — except that a seam above is never a gap: a contained item with neither a live verdict nor an honest per-item SKIP-with-reason blocks the hand-off itself, and an (L1) entry is `open` in a delivered ledger only when a later live FAIL reopens it. Every permitted gap is LABELLED in the deliverable's status and ledger per (E.3), never silently absent.

(b) THE LEDGER is a READ-ONLY JOIN over the stores that already own each fact, NEVER a new parallel or hand-maintained store (§11.4.227, §11.4.233(F) reuse). Its entry classes form a CLOSED list: (L1) each contained item with no passing §11.4.235(E.3) live verdict on this fingerprint; (L2) per contained item, the tests still owed — the §11.4.4(b) four layers, the §11.4.27 / §11.4.169 test types and the paired §1.1 mutations (future-regression instrumentation, additional test types, mutation hardening); (L3) each open §11.4.235(D) `test-instrumentation` / `process-doc` finding against contained code; (L4) each open §11.4.261 finding touching contained code; (L5) each tracked polish item recorded against a contained item; (L6) the §11.4.40 full-suite retest, until it has passed on this fingerprint; (L7) each §11.4.260 production-readiness invariant that is not green for a contained component; (L8) each §11.4.271 waiver covering contained code. Every entry carries its own tracked §11.4.197 item id (§11.4.54) — an entry with no tracked id is itself a §11.4.261 finding — and exactly one DISPOSITION from the CLOSED set {`open` | `closed` | `skipped` | `not-applicable` | `waived`}: `closed` — the entry's own closing evidence exists for this fingerprint; `skipped` — an honest per-item SKIP-with-reason whose code is one of the two TOPOLOGY-ABSENT codes of the consumer's §11.4.69 closed reason set, `hardware_not_present` or `topology_unsupported`, never invented (§11.4.3); `not-applicable` — the consumer has no tier for that entry, recorded with the §11.4.69 code `feature_disabled_by_config` (for (L1) this is exactly the §11.4.235(E.4) N/A consumer with no device-targeted flash/deploy entry point and no bound deploy ledger); `waived` — covered by a waiver that is valid under §11.4.271 at computation time (an elapsed or invalid waiver makes the entry `open`); `open` — every other case, and every case whose input cannot be resolved. PERMITTED DISPOSITIONS PER CLASS — a closed table; a disposition outside its class's row is INVALID: (L1) `open` | `closed` | `skipped` | `not-applicable` — a live verdict is an (E.2) seam and is never waived; (L2) `open` | `closed` | `skipped` | `not-applicable` | `waived`; (L3), (L4) and (L5) `open` | `closed` | `waived` — a finding or a polish item never disappears as absent topology; (L6) `open` | `closed` | `not-applicable` — the §11.4.40 retest is never skipped and never waived; (L7) `open` | `closed` | `not-applicable` — an unmet §11.4.260 invariant blocks release and is never skipped or waived, and `not-applicable` means only that the invariant has no subject in that component; (L8) `open` | `closed` | `waived` — `closed` once the waived debt is paid and the waiver retired. `skipped`, `not-applicable` and `waived` entries count as resolved for the status but are NEVER hidden: they are listed with their reason and tracked id, counted per class in every announcement, and enumerated as honest gaps in the release notes (§11.4.135, §11.4.118). (c) THE EVENT RECORDS. Every fact the status reads is an EVENT RECORD in the existing append-only event stream (§11.4.116 — reused, never a second store), carrying: the fingerprint; a SEQUENCE NUMBER assigned by the stream's single writer at append time and strictly increasing within the stream; the wall-clock write time, recorded for audit and NEVER used for ordering, because clocks skew (§11.4.6); the WRITER ROLE, stamped by the seam that performs the write and never supplied by the writer itself (§11.4.240(B), capability not instruction); the record KIND from the closed set {`disposition` (an entry id, a disposition, a reason code and an evidence reference; a class label, if the record carries one, is informational only), `qa-confirmation` (the §11.4.185 act), `release-seam-pass`}; and its payload. Every write to an owning store — creating a row, changing an entry's disposition, deleting a row — is recorded in that store's WRITE-SEAM LOG (§11.4.106(F)), and the seam mirrors at the same write, as a `disposition` record, every write that creates an entry's row or changes its disposition: a creation is mirrored as an `open` BIRTH record with reason code `open-debt`, so every entry is named by a record from birth and a later deletion of its row never removes it from the entry set (V5). The log entry of each mirrored write names the stream position of its mirror record (F7.4). A record carries exactly ONE fingerprint and is never inherited by another fingerprint: a write to a FINGERPRINT-KEYED store is mirrored once, for that fingerprint; a write to a SCOPE-KEYED store is mirrored once per already-delivered fingerprint whose hand-off record (D.5) names a contained item or code path that the written row matches, at the moment of the write, so a later re-close reaches every older fingerprint it matches; a fingerprint delivered AFTER that write acquires no record from it — instead, at that fingerprint's hand-off, the delivering seam writes an `open` BIRTH record for that fingerprint for every row the join matches at that moment (logged as a `birth` write, (F7.3)), so its matching rows are named from delivery and stay `open` until the verifier seam re-checks their closing evidence against that fingerprint and writes a record for it. WRITER ROLES form the closed set {`verifier-seam` | `qa-confirmer` | `release-seam` | `producer`}, and the ALLOWED WRITERS are: a `disposition` record setting `open` — any role, because a downward write is always safe (§11.4.201(4)); a `disposition` record setting any other disposition — the `verifier-seam` only, never the producer of the contained work (§11.4.240, §11.4.249); a `qa-confirmation` record — the `qa-confirmer` only; a `release-seam-pass` record — the `release-seam` only. (V3a) PATH NORMALISATION — one textual rule for every code path, in (F3) and in a row's scope alike, and never a file-system lookup, so a symbolic link is never resolved: split the path on `/`; drop every empty segment and every `.` segment; a `..` segment removes the segment before it; the normalised path is the remaining segments joined by `/`, and a path with no segment left (`.` or `./`) is the repository root, an ancestor of every path. Comparison is exact and case-sensitive, segment by segment: `src/a` is an ancestor of `src/a/b` but not of `src/ab` and not of `SRC/a/b`, and `\` is an ordinary character. (a) THE STATUS takes exactly one value from the CLOSED set {`delivered-unhardened` | `delivered-hardened-awaiting-qa` | `production-ready`}. It is a PURE FUNCTION of the FIELD TABLE's fields and of nothing else: never typed or chosen by hand (§11.4.6, §11.4.262), and never dependent on the order in which records are stored, nor on wall-clock time except through §11.4.271 waiver expiry, which can only lower it. It carries its VALID-UNTIL (V9) and a `pending` field naming what still holds it below `production-ready`, drawn from the closed set {`ledger`, `manual-qa`, `release-seam`, `not-fingerprint-bound`, `unresolvable-input`}. Its inputs are derived from the records as follows. X = at least one input cannot be resolved: a field whose ABSENT column says X is missing, unreadable or outside its set — in particular a missing delivered fingerprint, contained-item set or contained-path set, a contained path that does not normalise (V3a), no store declaration or two declarations of one store, a declared store with no read or with an unreadable read (F5.2) whether it is required or not, a read of an undeclared store, or an unreadable event stream, write-seam log, waiver register or repair list; an owning store that the consumer declares REQUIRED holds no matched row for this fingerprint (a store that is not required, such as a waiver store that may legitimately be empty, contributes zero entries when it is readable and empty, and its readability is shown with a control needle per §11.4.273); a SEQUENCE DEFECT involving this fingerprint (V2); a key matched in more than one row (V4); a row in a scope-keyed or not-fingerprint-bound store whose scope is not an item id in (F2) and does not normalise (V3a); a write-log entry for this fingerprint whose mirror (F7.4) is not an in-scope `disposition` record naming that entry (with disposition `open` for a birth); or a matched row with no `birth` write-log entry for this fingerprint. The DISPOSITION of an entry is the disposition of its LATEST `disposition` record (V7) when that record is valid, and `open` when it is not valid or when the entry has no record. L = the highest sequence number of any in-scope `disposition` record (V1), valid or not, or 0 when there is none. O = the number of entries in the ENTRY SET (V5) whose disposition is `open`. Q = the LATEST in-scope `qa-confirmation` record (V1) is valid, so its sequence number is greater than L. Hence ANY ledger record written after a confirmation — a reopen, and equally the later re-close of that reopen — VOIDS the confirmation, and a new §11.4.185 confirmation is required after the ledger's final record. S = Q holds and a valid `release-seam-pass` record exists, so its sequence number is greater than that of the latest `qa-confirmation` record. Hence voiding the confirmation voids every seam record that relied on it. The release seam MUST refuse to write the record unless O = 0, Q holds and B does not. B = at least one owning store is labelled not-fingerprint-bound (a consumer declaration, below). TRANSITION TABLE, evaluated top to bottom, first matching row wins, so it is total and deterministic over every combination of X, O, Q, S, B: row 1 — X → `delivered-unhardened`, pending `unresolvable-input` (§11.4.201(4) conservative-safe default, never upward); row 2 — O > 0 → `delivered-unhardened`, pending `ledger`; row 3 — O = 0 and not Q → `delivered-hardened-awaiting-qa`, pending `manual-qa`; row 4 — O = 0, Q, and (not S or B) → `delivered-hardened-awaiting-qa`, with pending containing `release-seam` exactly when S does not hold and `not-fingerprint-bound` exactly when B holds; row 5 — O = 0, Q, S and not B → `production-ready`, pending empty. Hence `delivered-hardened-awaiting-qa` means exactly that every automated and hardening entry is resolved by a valid record and only human or release acts remain, and `production-ready` is reachable only after a §11.4.185 confirmation that postdates the ledger's final record and a release-seam record that postdates that confirmation, both for the same fingerprint. A later record that reopens an entry, or changes any disposition at all, recomputes the status downward by the same table, and the status stays below `production-ready` until a new confirmation and a new seam record follow; no status is ever sticky. FRESHNESS: every owning store is one of (i) FINGERPRINT-KEYED — its facts are keyed by the candidate fingerprint (verdict stores, live-verdict records); (ii) SCOPE-KEYED — its facts are keyed by tracked item id or code path and carry a per-record write time (the workable-items database, the §11.4.261 findings ledger), joined through the contained-item set and contained code paths that the hand-off record (D.5) names; or (iii) NOT-FINGERPRINT-BOUND — it can supply neither, and it MUST carry that label explicitly in the consumer's store declaration (§11.4.35). A status is FRESH only while its ledger snapshot includes — by sequence number, never by wall-clock time — the latest event record for every matching record of every owning store (for a fingerprint-keyed store, every record for this fingerprint; for a scope-keyed store, every record for the contained items and code paths). It is recomputed at every announcement, at every write to an owning store (§11.4.106(F) write-seam discipline, §11.4.229), and at its VALID-UNTIL (V9), because a waiver that expires is not an event record: a status is FRESH only while the time is before its VALID-UNTIL, so an expired waiver lowers it on time instead of leaving the older value announced. A status announced from an older snapshot, a different fingerprint, or at or after its VALID-UNTIL is STALE and is itself a §11.4.261 finding. A not-fingerprint-bound store can never be proven fresh for a fingerprint, so it holds the status below `production-ready` (row 4) until the store is bound; its entries are still joined and shown. ANNOUNCEMENT: the status, its `pending` field and the per-class, per-disposition ledger counts MUST be shown wherever the deliverable is announced — the hand-off record, the release or deploy notes, the §11.4.97 progress report, and the §11.4.259 README badge row — and every announced status carries the fingerprint, the ledger-snapshot time it was computed from, its VALID-UNTIL, and every quarantine (V2) it relied on. While the newest deliverable of any open scope is `delivered-unhardened`, or its status is stale or unknown, the §11.4.259 production-readiness gauge MUST NOT read GREEN. "Quick" is never presented as "production ready" (§11.4.6, §11.4.259).

**(E.4) TRACKED CONVERGENCE TO PRODUCTION READINESS — DIRECTION, STALL, STARVATION AND THE LOOP.** For every open scope each cadence build appends a convergence record to the existing append-only event stream and snapshot (§11.4.116 — reused, not reinvented) carrying the fingerprint, the computed status and `pending` field, the ledger counts per class and disposition from (E.3)(b), and the delta against the previous deliverable of the same scope; the trajectory is reported in every §11.4.97 progress report. DIRECTION RULE — a scope's `open` count MUST NOT grow between consecutive deliverables except by entries that NEW increments brought in; growth with no new increment means hardening is going backwards and is surfaced as a §11.4.261 finding. STALL RULE — the `open` count failing to decrease across N consecutive deliverables that brought in no new increment is a STALL under §11.4.267(D), escalated, re-tiered under §11.4.231, or routed to a recorded §11.4.66 decision, never left as a silent background stream; N is consumer DATA (§11.4.35, §11.4.267(E)) and never a constitutional literal (§11.4.267(E) admits only an operator-mandated ceiling recorded in its own anchor), this N is distinct from every other N the constitution leaves to consumers (for example the §11.4.235(E.2) consecutive-DEFERRED bound), and a scope bound by this clause with no declared N is a CONFIG ERROR reported as such, never a silently unbounded stall window. STARVATION RULE — a scope with O > 0 MUST have at least one live hardening stream dispatched against it (§11.4.232(A) registry row, §11.4.147 agent registry) whenever host headroom exists under clause (C)'s bounds; O > 0 with zero live hardening streams while headroom exists is STARVATION and a §11.4.94 / §11.4.97 zero-idle violation, never an acceptable "the deliverable is out, hardening can wait" state. Background hardening keeps running under clauses (C)/(D.4), §11.4.126, §11.4.183 and §11.4.192 until the scope reaches `production-ready`. LOOP DONE-CONDITION: the §11.4.126 done-condition is NOT satisfied while any delivered scope of the current release has O > 0 (unless every open entry is itself blocked on a recorded external dependency under §11.4.101 / §11.4.21). A scope at `delivered-hardened-awaiting-qa` — O = 0, so only the §11.4.185 human confirmation or the release-seam record remains — IS a recorded external block for that scope's done-condition, because those acts are the operator's and the release seam's by design (§11.4.185, §11.4.40); for a non-release scope (§11.4.126(B)), which has no release seam, reaching that status with `pending` naming only `manual-qa` or `release-seam` satisfies the scope's done-condition. An external block NEVER idles the loop: the loop keeps progressing every other actionable item, the pending human act is surfaced in every §11.4.97 report until it is recorded, and the status recomputes the moment it is (§11.4.94, §11.4.97, §11.4.101).

**(E.5) PARALLELISM IS MAXIMAL AND BOUNDED.** The critical path of (E.1) and the hardening streams of (E.4) run concurrently by default under clause (C) and §11.4.183, inside clause (C)'s own honest boundary, which is cited here, unchanged and not restated. The one rule this clause adds: where the critical path and a hardening stream contend for one exclusive resource (§11.4.119 / §11.4.176), the critical path holds it until the first deliverable is handed off, and contention is never resolved by skipping a seam of (E.2).

**(E.6) WHAT "QUICK" MEANS — MEASURED, NEVER GATING.** "Quick" is a MEASUREMENT, never a target that weakens evidence. Each scope records (a) its wall-clock TIME-TO-FIRST-DELIVERABLE, from scope start to the first hand-off that passes §11.4.236 and carries its (E.3) status, and (b) per increment, its GO-TO-HAND-OFF latency, from its source-correctness GO to the first hand-off that contains it, both as §11.4.24-style statistics. They are TREND metrics only. Under §11.4.201(8) they are validated against the definition of done for DIRECTION — a shorter time that still passes (E.2) is better, and a time achieved by failing (E.2) does not count at all — but they are NEVER used to gate, rank, or reward, because a gating speed metric invites exactly the gaming (E.1) forbids. They are reported next to the `open` count and the convergence trajectory of (E.4), never instead of them.

**(E.8) HONEST BOUNDARY (§11.4.6).** Clause (E) re-orders WHEN deliverable-independent hardening COMPLETES relative to a scope's first deliverable, and makes that deliverable's remaining debt visible, tracked and converging.
