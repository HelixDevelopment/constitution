### §11.4.297 — Pull-request delivery: a project that declares it by a recorded operator decision delivers each task on one task branch with one pull request per task id; the pull request is assigned to the project's configured reviewers (requested and read back from the hosting platform; no account is named in this constitution), self-reviewed on the platform by its author agent and merged by that agent (or, where the project configures a human merge gate, by the human merger) only after its source-correctness GO and only in a form that keeps every reviewed commit on `main`, read back and then retired; evidence it cites resolves from its head tree; a submodule change lands as its own pull request before the parent pin bump, with mirror parity read back; every enforcement claim carries ENFORCED, PROVISIONAL or UNCONFIRMED (User mandate, 2026-11-07)

**Forensic anchor — operator order (2026-11-07), as relayed by the conductor of a consuming project in the operator's words of intent (the operator's own message is not quoted here, and the identifier of the order is UNCONFIRMED):** all rules and mandatory constraints about pull requests that the consuming project had adopted at project level are carried into this constitution, except the project-specific parts (the account names of assignees and reviewers); the result is fully decoupled, universal and reusable by every project that uses this constitution. An earlier order of the same operator (2026-11-06) kept the reviewer assignment at project level only; it stands for the NAMES: no account name enters this constitution, while the rule that a project configures its required reviewers and that every pull request is assigned and read back is carried here. A second operator rule of the same day (2026-11-07, relayed the same way, identifier UNCONFIRMED), in the relayed words: the agent that creates a pull request self-reviews it (real review comments in the pull request) and then merges it (the merge process is owned by the agent); the reviewer account names stay project-level configuration. Its universal form here: the author agent of a pull request reviews and merges it, unless the project configures a human merge gate.

**The gap this anchor closes (stated so it is not restated elsewhere, §11.4.227).** §11.4.288 makes direct work on `main` the default, allows a vehicle only when strictly necessary and lands it with `git merge --ff-only`; §11.4.113 forbids force; §11.4.181 names branches; §11.4.142 requires review; §11.4.293(A) binds every commit to a Roadmap item and every out-of-scope path to a closed reason; §11.4.292 defines the reproduction record. None of them describes delivery by pull request: when a project may choose it, how a task maps to a branch and a pull request, who reviews and merges it and in which form, how reviewers are assigned and proven, what evidence a reviewer must be able to resolve, how a submodule change travels through pull requests, how mirrors are reported and how enforcement is worded. A consuming project that adopts pull-request delivery by an operator decision therefore stands in a recorded conflict with §11.4.288: a merge on the hosting platform is not a fast-forward and the merge itself is an approval wait. This anchor resolves that conflict explicitly in clause (A), adds exactly the rest, and restates no other anchor.

**(A) DECLARATION, AND THE RECONCILIATION WITH §11.4.288.** Pull-request delivery is a delivery mode a consuming project selects only by a recorded operator decision (§11.4.66), declared as DATA (§11.4.35) in ONE tracked configuration file that names: the decision's identifier, the mode (`direct`, the default, or `pr`), the base branch, the pull-request remote, the task-branch prefix, the reviewer list of each repository it delivers to (clause (D)), the landing form (`ff-only` or `merge-commit`), the merger (`author-agent` by default, or `human`, a human merge gate, clause (C)(2)), the protected branches, the state of the direct-push guard (`off`, `expected` = warn and write an audit line, `enforced` = refuse), the shared single files (clause (B)(5)), the tool-written paths (clause (E)(3)), the evidence directory (clause (E)(2)) and the merge window (point (A.2) below). An unknown key or a value outside its closed set makes the delivery refuse before anything is committed; it is never ignored. Without the declaration, §11.4.288 applies as written and this anchor has no effect except clause (G). With the declaration, for that project only, this anchor AMENDS §11.4.288 at exactly three points, recorded in the refinement note of §11.4.288; every other sentence of §11.4.288 binds such a project unchanged:

(A.1) NECESSITY. The declared decision is the recorded necessity of §11.4.288(B)(2) for every task branch the delivery tooling creates; its identifier in the configuration is the record. It legitimises no other vehicle.

(A.2) THE MERGE IS THE LANDING. The merge of a pull request that holds its source-correctness GO (§11.4.288 Terms), made under clause (C) by its author agent after the read-back self-review or, where the project configures a human merge gate, by the human merger, is the landing step of §11.4.288(B)(1). It adds no wait beyond the merge conditions of clause (C)(2): no manual QA, no open hardening item and no approval beyond what the project configures as required holds a GO'd pull request open. A pull request whose GO is older than the declared merge window is reported as stale in every report until it lands or is closed; it is never parked silently.

(A.3) THE LANDING FORM. The landing is a fast-forward of `main` to the reviewed head (the form of §11.4.288(B)(3)) or a merge commit on `main` whose first parent is the previous `main` tip and whose second parent is the reviewed head. Both keep every reviewed commit on `main` under its own id, and `main` is still pushed fast-forward to every upstream (§11.4.288(B)(1)). In both forms the reviewed head already contains the remote base tip (merge condition (g) of clause (C)(2)), so the content that lands is the content that was reviewed and tested, as §11.4.288(B)(3) requires; a merge commit made on a stale base is not this form. A squash merge and a rebase merge are FORBIDDEN: they put rewritten copies on `main` and leave the reviewed commits off it, so the §11.4.288(B)(4) count of unique commits never reaches zero and a parent gitlink that records the reviewed commit of a submodule is not on that submodule's `main` (§11.4.288(D)). The project declares the form and, where the hosting platform allows it, configures the platform to offer only that form; that setting is worded under clause (G).

**(B) ONE TASK, ONE BRANCH, ONE PULL REQUEST.** (1) PLAIN TRAILER. Every commit delivered by pull request carries the §11.4.293(A)(3) `Roadmap-Item:` trailer with a plain value: one or more item ids in the project's id syntax (DATA), separated by commas or blanks, and nothing else on that line. An annotation inside the value (a parenthesised note, an UNCONFIRMED marker) makes the value unparseable, and the delivery refuses before anything is staged. (2) ONE BRANCH AND ONE PULL REQUEST PER TASK ID. A task id gives one task branch named `<prefix>/<id>-<slug>` (§11.4.181: one canonical name across every repository the task touches) and one pull request against the base. A commit that names two different ids is refused unless it records its reason in a `Multi-Task-Reason:` trailer (the project may rename the field as DATA); the branch then takes the first id. An existing branch of the task, local or on the remote, is reused for every later commit of that task whatever its subject; two such branches are a refusal. (3) NO FOREIGN COMMIT. A new task branch starts at the remote-tracking tip of the base. When `HEAD` holds commits that the remote base lacks and `HEAD` is not the task's own branch, the delivery refuses and lists those commits: they would ride into another task's pull request. A detached `HEAD` is refused. No ref is moved by force. (4) PUBLICATION IS READ BACK. The task branch is pushed fast-forward only (no force, no delete, no tag push), and the remote tip is read with `git ls-remote` and compared with the local tip before any pull request is opened; a push tool's exit status is not evidence (§11.4.6). Opening is idempotent: the open pull request for the head is looked up first, then created or updated. (5) SERIAL LANDING. Task pull requests of one repository that change a shared single file the project declares (for example a continuation document, a state ledger, a tracker database or an audit log) land one at a time in a recorded order. Before a task branch is created, and after each merge, the local base is fast-forwarded to the remote base. When the base moves under an open pull request, the base is merged into the task branch (§11.4.188: merge, never rebase, never force). (6) THE MERGE IS ONE DELIBERATE STEP. The commit and publish steps of the delivery tooling never merge, close, force-push or delete, and in this mode never push the base branch. The merge is a separate step owned by the merger of clause (C), taken only after the conditions of clause (C)(2) are read back; under a human merge gate no agent and no tool takes it.

**(C) SELF-REVIEW AND MERGE BY THE AUTHOR AGENT, UNLESS A HUMAN MERGE GATE IS CONFIGURED; READ BACK, THEN RETIRED.** (1) SELF-REVIEW. The agent that opens a pull request (its author agent) reviews it on the hosting platform before any merge: it reads the whole diff of the head it will merge and posts a review on that pull request whose body names the head commit id it reviewed, what it checked (every changed file, the evidence cited under clause (E) resolved, the gates and tests run with their results) and the source-correctness GO the merge relies on (its record path or link); every finding is a review comment anchored to the diff line it concerns, and every finding is answered by a follow-up commit (whose delta is reviewed again) or by a written reply that states why no change is needed. A review with no reading record (an approval alone, a bare "looks good" or an empty body) is not a self-review. A platform that refuses an approval by the author records the self-review as a comment review; it is never posted through another account to obtain an approval. The self-review is read back from the platform (the review entry, the head commit id it names and its comments) before the merge. It is the author's own multi-pass check (§11.4.92) made visible in the pull request: it is never the source-correctness GO, which stays the independent review of §11.4.142 / §11.4.209 / §11.4.235 (§11.4.240: the producer never gates its own change), and it never replaces the configured reviewers of clause (D). (2) THE MERGER AND THE MERGE CONDITIONS. By default the merger is the author agent, which owns the merge process. It merges only when all of these are read back: (a) the source-correctness GO is recorded, as a record the merger reads, for exactly the head being merged (a GO for an earlier head, a GO that cannot be read, or no GO refuses the merge); (b) its self-review of that head is on the platform with every finding answered; (c) the reviewer requests of clause (D) are shown by the platform, or a refused reviewer is reported under clause (D)(4); (d) the head on the platform equals the reviewed head (a head that moved after the self-review or the GO is reviewed again first, and the merge call pins the reviewed head where the platform offers it); (e) the serial order of clause (B)(5) admits it; (f) every approval the project configures as required is present; (g) the remote base tip, fetched right before the merge, is an ancestor of the reviewed head (when the base has moved, it is merged into the task branch under clause (B)(5) and the new head is reviewed again first). It merges only in the declared form of point (A.3). A project configures a HUMAN MERGE GATE (merger `human`) by a recorded decision (§11.4.66); then no agent presses a merge button or calls a merge interface of the hosting platform: the author agent self-reviews, reports the pull request ready with (a) to (g) read back, and the human merger lands it. INTERPRETATION (the author's reading, UNCONFIRMED by the operator): the relayed rule makes the author agent the default merger and adds the self-review; it does not say that the self-review replaces the independent review, so the source-correctness GO of §11.4.288 stays merge condition (a). A reading in which the self-review is the GO would amend the §11.4.288 Terms and §11.4.142 and needs its own recorded operator decision. (3) READ-BACK. An agent reports a pull request as landed only after reading it from the hosting platform's interface: the state merged, the merge commit id and the form check. For a merge commit, its second parent equals the reviewed head; for a fast-forward, the base tip equals the reviewed head; in both cases `git merge-base --is-ancestor <reviewed head> <remote>/<base>` holds after a fetch. A landing that fails the form check (a squash or a rebase) is a §11.4.288 violation: it is recorded, an item is filed (§11.4.202), and the task branch is KEPT, because it holds the only copy of the reviewed commits (§9.2). (4) RETIREMENT. After the read-back the local base is fast-forwarded and the remote-tracking refs are pruned (`git fetch --prune`); the task branch is deleted locally and on every upstream that holds it only when its head is an ancestor of `main` on every declared upstream (the §11.4.288(B)(4) count is zero). A platform option that deletes the branch at merge time is used only when the platform is the only declared upstream; otherwise the branch is deleted after the parity read-back of clause (F)(4), never at merge time. A task id whose merged branch still exists on a remote is not given new work until that branch is pruned, because clause (B)(2) would reuse it. (5) REPORT. The report of a delivered task names the pull request, its state as read back, the merger, the self-review as read back, the landing form, the reviewers as read back (clause (D)) and the retirement state. "Merged" or "landed" without the read-back is a bluff (§11.4.6).

**(D) REVIEWERS: A CONFIGURED LIST, REQUESTED AND READ BACK, NEVER NAMED HERE.** (1) CONFIGURATION. The project declares as DATA, in the configuration of clause (A), the required reviewer accounts of every pull request it opens: one list per repository where the repositories differ (the key name is the project's; `pr_reviewers` is the default). A list holds at least one account; an empty or malformed list is refused before anything is committed, and an absent key never means "no reviewers" (the project's declared default applies). Changing a list is a reviewed edit of that file; no environment variable or command-line switch replaces or empties it. This constitution names no account: account names, teams and repository addresses are project DATA (§11.4.17, §11.4.35), and gate `CM-PR-DELIVERY-ACCOUNT-NAME-FREE` proves that the accounts a consumer declares are absent from the rule corpus. (2) AUTHOR SKIP. The account that opens a pull request is its author, and the hosting platform refuses a review request from the author. That account is skipped with a printed note and every other listed account is requested; with a list of two accounts the rule reads "the reviewer is the other account". The author agent's self-review of clause (C)(1) is not a reviewer assignment and never counts as one. When the author is the only listed account no reviewer is possible: the delivery reports it and ends non-zero, never silently. (3) REQUESTED AND READ BACK. The accounts are requested when the pull request is created and again on every update for each listed account that is neither requested nor has already reviewed (a second request after a review re-requests it, so an account that has reviewed is not asked again). The pull request is then re-read from the platform (its requested reviewers and its latest reviews), and an assignment counts only when the platform shows it. The word "verified" is never printed for an assignment without that read-back. (4) A REQUIRED REVIEWER THE PLATFORM REFUSES. An account the platform refuses (not a collaborator, read-only access, suspended, or any other refusal) is reported with the platform's own text; the other accounts are still requested; the pull request stays open; the delivery ends non-zero; and the pull request body or the agent's report states which required reviewer could not be requested and why. The refusal never removes the account from the list, never counts as an assignment and is never worked around by requesting another account. Reading the account's permission on the repository before the request is recommended, so the refusal is known in advance. (5) The same rule binds the pull requests a submodule cascade opens (clause (F)), with that repository's list.

**(E) EVIDENCE A REVIEWER CAN RESOLVE.** (1) Every evidence file a commit of a pull request cites as proof (the `red` and `green` paths of a §11.4.292 `Reproduction:` line, or an evidence trailer of the project) is cited by a repository-relative path, and the file at that path in the tree of the pull request's head commit has the cited sha256 (`git show <head>:<path> | sha256sum`). (2) The evidence file is committed in the same pull request or is already on the base, under the evidence directory the project declares. An absolute host path, a path under a scratch or evidence directory outside the repository, or a path absent from the head tree cannot be resolved by a reviewer: a line that cites only such a path is INCONCLUSIVE for that pull request, never PASS, and a reproduction state that rests only on it does not satisfy §11.4.292 for VERIFIED-DONE (§11.4.290). A host path may be added next to the repository path as a convenience; it never replaces it. (3) TOOL-WRITTEN LEDGER ROWS. A row that the project's own commit or delivery tooling writes into a tracked ledger as a side effect of a run (an audit log, a state ledger, a registry of agents or runs) enters a commit only when its path is on the project's standing list of tool-written paths and the commit lists that path in the §11.4.293(A)(4) trailer with the reason `generated-regeneration` and a justification that names the tool which wrote the row. Such a row is never written or edited by hand. A tool-written path that is not on the list is an unjustified out-of-scope path. No fifth reason is added to §11.4.293(A)(4).

**(F) SUBMODULE PULL REQUESTS, THE PIN BUMP AND MIRROR PARITY.** (1) Under pull-request delivery a change in an own submodule (the §11.4.288 term) is delivered as that submodule repository's own pull request against its base, on a task branch with the same name as the parent's (§11.4.181), under the reviewer rule of clause (D) with that repository's list. A third-party submodule is never committed to (§11.4.288(A)). (2) ORDER. The submodule pull request lands first, in a form of point (A.3), so that the commit the parent records stays on the submodule's `main`; the submodule task branch is kept until the parent pull request that records it has landed. (3) THE PIN BUMP. The parent's gitlink moves in a parent pull request (the task's own or a separate pin-bump pull request) only after the submodule pull request is read back as merged (state and merge commit id). The recorded gitlink is reachable from the submodule's `main` on the hosting platform (§11.4.288(D)), preferably the merge commit itself; the parent pull request body names the submodule pull request, its merge commit and the pinned commit. (4) MIRROR PARITY. A merge on the hosting platform moves `main` on that host only. Every other declared upstream of the submodule (each mirror) receives the merged `main` by a fast-forward push through the project's sanctioned push path (§2.1, never force). The pin-bump pull request body carries a parity table read with `git ls-remote` when the body is written: for each declared upstream its `main` tip and one of `PRESENT` (it contains the pinned commit), `MIRROR-LAG <tip>` (it does not) or `UNREACHABLE` (not read; the parity of that upstream is UNCONFIRMED). The pin bump is reported ready to land only when every declared upstream reads `PRESENT` (§11.4.288(D): a parent records a commit only after every upstream of the submodule holds it). A push tool's exit status is not parity, and "pushed to all upstreams" is never written without the per-upstream read-back (§11.4.6).

**(G) ENFORCEMENT WORDS.** Every statement of how a delivery or protection rule is enforced, in a document, a changelog, a pull-request body or an agent report, carries exactly one of three words: `ENFORCED` (the mechanism exists at the repository's `HEAD` and runs by default on the delivery path), `PROVISIONAL` (it exists only as a staged patch or a draft, or has run only against stubs, with host evidence; it is not applied or not wired) or `UNCONFIRMED` (it is implemented nowhere, or it depends on a human or external fact that has not been read back). These words are not item statuses and never replace the levels of §11.4.290. A claim never exceeds the weakest essential mechanism behind it. No text calls a branch protected on the hosting platform unless the platform's protection read-back records it at the time of writing; a local warn or refuse guard is a local mechanism and is worded as one; a platform setting that a person reports as made is `UNCONFIRMED` until it is read back.

**(H) GATES, TESTS AND PAIRED MUTATIONS.** (1) The consuming project's delivery tooling ships a hermetic test (throwaway repositories, a local bare remote, a stub of the hosting-platform client: a test double is legal here because the test proves the tooling's own logic, §11.4.289) that covers at least the trailer parse and its refusals, the branch name and its reuse, the foreign-commit refusal, the push read-back, the idempotent open or update, the author skip, a refused reviewer, an assignment the platform does not show, the closed value sets of the configuration, a scan proving that the commit and publish steps hold no merge, close, force-push or delete call, and the merge step's refusals (no recorded GO for the merged head, no self-review read back, an unanswered finding, a head that moved after the review, a base tip that is not an ancestor of the head, a squash or rebase form, and any merge call under a human merge gate); each case has a paired §1.1 mutant that the test must kill, and the test carries a control needle (§11.4.273). A stub run is `PROVISIONAL` evidence of the tooling and never evidence that a real pull request exists or was reviewed (§11.4.289). (2) This constitution ships gate `CM-PR-DELIVERY-ANCHOR-WIRED` (the rule is present exactly once, complete, mirrored, indexed, generated and wired) and gate `CM-PR-DELIVERY-ACCOUNT-NAME-FREE` (the reviewer accounts the consumer declares, read at run time from the consumer's own configuration and never stored here, appear nowhere in the rule corpus: `PASS` only when at least one account was read and none was found, `FAIL` naming file and line when one is found, `SKIP` (exit 3) when no consumer list exists, `BLIND` (exit 2) when a list exists and cannot be read or the control needle fails), each with a paired mutation test, and the propagation gate. (3) The item-level seams are recommended gates, registered as deferrals and NOT claimed implemented: `CM-PR-LANDING-READBACK` (`OWED-GATE-182`; FAIL: a pull request reported landed whose read-back is absent, whose merge is a squash or rebase, that was merged without a source-correctness GO recorded for the merged head, without a self-review read back for the merged head, while the remote base tip was not an ancestor of the merged head, or by an agent under a human merge gate, whose reviewers were not shown by the platform, or whose task branch was deleted before every upstream held its head; golden-FALSE: a merge commit whose second parent is the reviewed head, self-reviewed and read back, with the branch pruned after parity), `CM-PR-EVIDENCE-RESOLVES-FROM-TIP` (`OWED-GATE-183`; FAIL: an evidence path of a `Reproduction:` line or evidence trailer in a pull request that is absolute, outside the repository, absent from the head tree or of another sha256, or a tool-written ledger path outside the project's list; golden-FALSE: a repository path with its matching sha256 and a host path added beside it) and `CM-SUBMODULE-PIN-MIRROR-PARITY` (`OWED-GATE-184`; FAIL: a parent pin bump reported ready to land while a declared upstream of the submodule does not contain the pinned commit or was not read; golden-FALSE: every upstream `PRESENT`). Paired §1.1 mutations: a squash landing reported as landed, a merge without a recorded GO for the merged head, a merge on a stale base, a merge with no self-review on the platform, a reviewer counted without the read-back, an evidence path moved outside the repository, a pin bump marked ready with one mirror lagging; each MUST make its gate FAIL.

**(I) WHAT THIS ANCHOR DOES NOT CHANGE.** §11.4.113 (no force-push), §11.4.142, §11.4.209 and §11.4.235 (the independent review and its GO: an approval by a configured reviewer on the platform and the author agent's self-review are additional checks, never a substitute for the source-correctness GO), §11.4.240, §11.4.181, §11.4.188, §11.4.233(G), §11.4.290, §11.4.292 (its vocabulary and clauses), §11.4.293 (its four out-of-scope reasons), §11.4.296 and §11.4.288 outside the three points of clause (A) keep their full text. A project without the declaration keeps §11.4.288 as written.

**Honest boundary (§11.4.6).** The two gates shipped with this anchor prove that the RULE is present exactly once, complete, mirrored in the four context carriers, indexed, generated into the group, rule file and catalog and wired into the seams that carry rules, and that the reviewer accounts a consumer declares are absent from the rule corpus. They do NOT prove that any pull request was opened, assigned, self-reviewed, reviewed, read back, merged by its declared merger, landed in the declared form or retired, or that any mirror holds a commit: those item-level seams are the three deferrals of clause (H)(3), NOT claimed implemented (§11.4.227(A)). The constitution ships no delivery tool and no hosting-platform client; that tooling is the consuming project's. The account scan matches whole account names case-insensitively; it cannot know an account the consumer did not declare, and an account name that is also a common word would be reported wherever that word appears.
