### §11.4.289 — No stubs, mocks or fixture servers as evidence: all testing, validation and verification of produced results is LIVE and deterministic (real artifact, real services, real devices, real models, real data); test doubles are legal only in unit tests and in tests of a gate's own logic; a live-labelled result carries machine fields proving a real target; an absent real dependency is an honest SKIP, never a stand-in (User mandate, 2026-10-26)

**Forensic anchor (operator mandate, 2026-10-26, `CRITICAL`), verbatim:** "There MUST BE no stubs or mocks for LIVE and deterministic driven testing which is MANDATORY way of testing and validating and verifying all results we produce! Make sure this is clear as well from our root constitution (Submodule) with all possible details!"

**Why a new anchor, and what the audit found (§11.4.227 extend-don't-restate, measured 2026-10-26).** §11.4.27(A) already forbids mocks, stubs, fakes and fabricated provider responses outside unit tests, and §11.4.169(1) names unit as the only layer where they are permitted. Neither states what a result labelled LIVE must carry, how a run answered by a test double is to be recorded, what to do when the real dependency is missing, or how the fixture servers of the decision layer are classified. Read against the rest of the corpus, several anchors lean on fixtures, golden files and simulated environments for good reasons (§11.4.107(10) and §11.4.201 golden-good and golden-bad fixtures prove a gate's own logic; §11.4.277(C) feeds known-content screenshots to a real Vision model; §11.4.187 and §11.4.279(H) say a hermetic green proves a contract, not live behaviour; §11.4.202 already requires a real database and real binaries). None of them says in one place that these are different classes of evidence and that only the real one verifies a result. The gap is stated precisely so this anchor adds a classification and a refusal rule, not a second copy of §11.4.27: it EXTENDS §11.4.27(A) (which gains a pointer to this anchor) and binds §11.4.108, §11.4.262, §11.4.50 and §11.4.226 to it.

**Terms (named once).** LIVE means the real artifact, deployed on a clean target (§11.4.108), run against real services, real network, real devices, real models and providers, real data paths and real credentials (referenced by variable name only, §11.4.10); the system under test is not replaced by anything written for the test. A TEST DOUBLE is any stand-in for a part of that system: a mock, stub, fake, spy, dummy, an in-memory substitute for a component the real system does not itself ship, fixture server (a process or library that answers requests the real service would answer), recorded or replayed traffic, a simulated or emulated provider or device, a canned model answer, a loopback server that imitates a vendor API, or a feature flag or environment switch that makes the production code answer from canned data. A FIXTURE INPUT is data fed INTO the real system under test (a sample file, a known-content screenshot, a seed row, a golden manifest of expected answers); it is not a double, because the thing answering is still real. UNIT-CLASS evidence is anything produced with a test double in the path. LIVE-CLASS evidence is anything produced with none. A double is defined by what answers, never by where it runs or who started it: a real service the test boots on demand (a container, a gateway, a database) is part of the real system and is LIVE-CLASS; only an imitation of the service is a double.

**(A) Verification is LIVE-CLASS only.** Every test, challenge, validation, verification, gate verdict, QA run and acceptance claim that reports on whether a feature works for the end user (the §11.4 PASS), outside unit tests, MUST run against the real system as defined above. "Deterministic driven testing" (the operator's term for repeatable, scripted, machine-evidenced runs) is a property of the real run, never a reason to fake it: determinism is N of at least 3 identical results against the same real artifact fingerprint, same real device and same topology (§11.4.50), obtained by controlling inputs and timing, not by replacing the system.

**(B) Doubles are forbidden as the source of any PASS, verification or validation claim outside unit tests.** This covers integration, E2E, full automation, security, DDoS, scaling, chaos, stress, performance, benchmarking, UI, UX, Challenges, HelixQA banks, QA sessions, readiness verdicts (§11.4.236), live verification of a deployed build (§11.4.235(E)), model validation (§11.4.277) and UI QA (§11.4.278). A run answered, in whole or in part, by a test double is recorded as UNIT-CLASS (or as a gate-logic test, clause (C)) and can never be cited as proof that the feature, service, model, endpoint or device works. Presenting it under a live label is a §11.4 PASS-bluff at the evidence-class layer (§11.4.226), of the same severity as a metadata-only PASS.

**(C) Where fixtures and doubles remain legal, and only there.** (1) Unit tests (§11.4.27(A), §11.4.169(1)). (2) Tests of a gate's, hook's or analyzer's OWN logic: golden-good, golden-bad, negative-control and golden-FALSE-with-carrier fixtures, paired §1.1 mutations, control needles (§11.4.107(10), §11.4.201, §11.4.273). Such a test proves the gate decides correctly on a given input; it never proves that the thing the gate guards works. (3) Fixture INPUTS fed to the real system (definition above). (4) Test payloads that carry destructive or hostile text, assembled in a non-shell language (§11.4.287(D)). A fixture server that stands in for the system under test is never legal in (3).

**(D) A result labelled live MUST carry machine fields proving a real target (§11.4.262, §11.4.226).** At least: the target's artifact fingerprint READ FROM THE TARGET at run time (§11.4.115(F), §11.4.200), the endpoint identity actually reached (resolved host and port, socket path or device serial, with a TLS or host-key identity where the transport has one), for a hosted or model provider the provider's own response identifiers (request id, model id as the provider reports it, usage fields), the run timestamp, and the producing command. For an endpoint on loopback, a container bridge or a Unix socket the record MUST also carry the identity of what answered: pid and executable path with its content hash for a process, the image digest for a container. DISPOSITION TURNS ON ONE BIT: is what answered the real service, or an imitation of it (a test double, see Terms)? Where it listens, who started it and where its files live do not decide it. A real service the test boots on demand (a rootless container through the containers submodule, §11.4.76 and §11.4.161; the real llmctl gateway, §11.4.279; a real database) is LIVE whether it listens on loopback, a container bridge, the LAN or a socket, whether the test started it or it was already running; requiring tests to boot real infrastructure and then disqualifying that infrastructure for having been booted would forbid exactly the live testing this anchor mandates (§11.4.201(1) false-positive refusal). The record is reclassified UNIT-CLASS by the gate, and cannot satisfy a seam that requires live evidence, only when (i) the answering executable or image is a registered double (listed in the project's declared double register, consumer DATA per §11.4.35, or by its own identity a fixture server, mock, stub, replay or canned-answer binary or image), or (ii) its identity does not match the real artifact or real dependency the claim names (executable hash or image digest differs from the fingerprint or the pinned digest the record cites), or (iii) its answers are read from recorded or canned data, or (iv) the identity fields needed to decide (i) to (iii) are absent or unresolvable (the conservative default, §11.4.201(4): not proven live, and said so, never claimed). Loopback, test-started, ephemeral port, container-on-demand and a location under a test or scratch directory are NOT disqualifying by themselves: a real binary built or unpacked into a test directory is real when its hash matches the artifact the claim names. Examples that MUST stay LIVE (the check must not fire): a test boots the real Postgres image and queries it on loopback with the image digest recorded; the real llmctl gateway started by the test answers on 127.0.0.1 with its pid, executable hash and bearer-authenticated response ids recorded; a real service answering on a Unix socket with its peer pid recorded; an already-running real service on the LAN with its host-key identity recorded. Examples that MUST be reclassified UNIT-CLASS (the check fires): a fixture HTTP server returning canned bodies, whether the test started it or it was already running; a process whose executable hash is in the double register; a container whose image digest differs from the pinned real one; an endpoint whose answering identity was not recorded; a response replayed from a file. Class is proven by machine fields, never by a label (§11.4.226(2)); a grep or a narrative stating "ran live" is wrong-layer evidence.

**(E) When the real dependency is unavailable, the honest outcome is SKIP-with-reason, never a stand-in.** A missing device, credential, model, provider quota, network path, licence or topology yields an honest SKIP or `not_validated` with a closed reason code (§11.4.3, §11.4.69: for example `hardware_not_present`, `credentials_absent` naming the variable only, `topology_unsupported`, `operator_attended`), plus a tracked item for the owed live run (§11.4.197). Substituting a double and reporting PASS is forbidden; so is retrying until a flaky real dependency happens to answer and discarding the failures (§11.4.248, §11.4.267). A SKIP is never counted as a PASS in any ledger, badge or readiness status (§11.4.259, §11.4.266(D)).

**(F) Test doubles in production code or in non-unit tests are release blockers.** A mock, stub, fake, in-memory substitute or canned-answer path reachable from a production binary, or imported by a non-unit test, is a §11.4.27 violation of §11.4 PASS-bluff severity. A "dry-run", "demo", "offline" or "simulate" mode in production code that answers from canned data is a double; if it exists for a legitimate user purpose it must be unmistakably labelled in its output and can never be the mode in which evidence is gathered.

**(G) Paid and hosted external services: use the real service with minimal safe calls, never a double.** Where a real provider, gateway, vendor API or model endpoint is part of the claim, the live run calls it for real with the smallest call that proves the property (one short prompt, one small object, the cheapest eligible tier, the lowest token cap), with the quota and cost bounded in advance as consumer DATA (§11.4.35) and the credential referenced by variable name only, never printed, logged or committed (§11.4.10). If cost, rate limits or terms genuinely prevent a live call, the result is (E): SKIP-with-reason and a tracked item, with the owner's decision recorded (§11.4.66). A sandbox environment that the PROVIDER operates and documents for testing (for example a provider's own test mode) is a real service, provided the evidence fields of clause (D) show it; a sandbox the project built to imitate the provider is a double.

**(H) Reviewers MUST check evidence class against the claim, and MUST try to detect stub-served evidence.** Every review (§11.4.142, §11.4.194(6), §11.4.209) of a change that makes or relies on a live or verification claim checks: (1) the evidence class actually produced against the class the claim needs (§11.4.226); (2) that the target named in the record is the real one: resolve the endpoint and inspect what answered (its executable hash or image digest against the real artifact or the double register, clause (D)); a test starting its own server, patching the HTTP client, setting a base URL to localhost, swapping an environment variable or injecting a library mock are LEADS to follow, never verdicts: a test that boots the real service and points at its loopback address is expected and LIVE, and the verdict turns on whether the answering identity is real or an imitation; (3) that the run would FAIL if the real service were unreachable (a run that still passes with the network or device removed was not talking to it): the reviewer attempts at least one such disconnection or redirection mutation the author did not write (§11.4.194(6)(d)); (4) that no SKIP was turned into a PASS. A review that does not record this check for a live claim is incomplete.

**(I) Classification of the decision-layer (Jev) fixture servers, stated for the avoidance of doubt.** `tests/jev/fixtures/jev_server.py`, the stub-server end-to-end test, the fixture binaries under `tests/jev/fixtures/bin*`, the synthetic token-reduction fixtures and every `tests/jev/` suite that runs against them are GATE-LOGIC UNIT TESTS (clause (C)(2)): they prove that the detection, wiring, calibration, bootstrap and token-reduction gates decide correctly given a declared input. They are NOT evidence that a decision model, the llmctl gateway, a hosted endpoint, the calibration agreement or any token saving works, and they MUST NOT be cited for that (this restates §11.4.279's own honest boundary as a rule). Live proof of the decision layer requires the real llmctl gateway (HTTPS, with its mandatory bearer key, never a plain-HTTP default) or a real hosted endpoint, a fresh `llmctl require-validated` PASS under `LLMCTL_VALIDATE_STRICT=1` (§11.4.277), measured provider-usage tokens in the §11.4.141 BEFORE/AFTER harness, and the clause (D) fields. Until such a run exists the layer's status stays "gate logic proven, behaviour not live-proven", exactly as §11.4.279 already states.

**(J) Honest boundary (§11.4.6).** This anchor classifies evidence and refuses misclassified evidence; it does not make a live run correct (§11.4.108, §11.4.40, §11.4.185 still apply), does not forbid unit tests or gate-logic fixtures, and does not require paid calls without a bounded budget. A real dependency that is flaky or slow is a finding to fix (§11.4.102), not a licence to stub it. The machine-field check of clause (D) can be defeated by a producer able to forge fields; that residual risk is bounded by §11.4.115(F) harness-written verdicts, §11.4.240 producer-verifier separation and §11.4.268 tamper evidence, not removed. Applicability of each live leg to a project is consumer DATA (§11.4.35); a leg genuinely inapplicable is a recorded SKIP, never silently absent.

Classification: universal (§11.4.17) — the consumer supplies its live targets, call budgets, provider test modes, reason-code set and the list of directories in which doubles are legal as DATA per §11.4.35.
