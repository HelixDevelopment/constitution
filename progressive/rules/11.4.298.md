### §11.4.298 — Release gate per product: a deployable build is deployed or tagged only after a full, deterministic LIVE run of every existing test on connected target hardware of its product and a §11.4.293 comparison against the build that hardware carried before; a product without connected hardware or without a baseline is BLOCKED, never green (User mandate, 2026-11-07)

**Forensic anchor — operator note (2026-11-07 17:13), as relayed by the conductor of a consuming project in the operator's words of intent (the operator's own message is not quoted here, and the identifier of the note is UNCONFIRMED):** a universal release gate: an image or build may be deployed or tagged only after full deterministic LIVE testing on connected target hardware and a proven no-worse comparison against the previously released or flashed build on the same hardware; no existing feature is broken; every existing test is re-run; a baseline PASS that becomes INCONCLUSIVE, SKIPPED or absent counts as a regression; a product without hardware or without a baseline is BLOCKED, never green; the gate holds per product, and its text names no product and no device.

**What already holds, and the gap this anchor closes (stated so it is not restated elsewhere, §11.4.227).** §11.4.40 requires a complete retest with all existing tests before a release tag; §11.4.135 refuses a release without verdicts for the standing regression-guard suite; §11.4.200 verifies a written image on the intended target; §11.4.236 blocks a deploy, a publication and a manual-QA hand-off until the mandated validation produced a PASS whose fingerprint was read from the target; §11.4.289 makes every verdict LIVE; §11.4.290(G) governs what a release may carry and how it is labelled; §11.4.293(B) to (F) define the comparison of a flashing image with its baseline on the same board, the closed verdict set `NO-WORSE-PROVEN` / `REGRESSED` / `INCOMPARABLE-BASELINE-MISSING`, the rule that a baseline `PASS` which is anything but `PASS` on the new image is a regression, and the refusal of a release and its tag. Those texts are not restated here. They leave four gaps: (1) no anchor makes the §11.4.293 verdict the condition of a DEPLOYMENT, and §11.4.293 binds flashing images only, not the other builds a project puts on its hardware; (2) no anchor requires the live run to happen on target hardware CONNECTED to the harness while the run executes and identified from the target, rather than on an emulator, on a host or as a replayed record; (3) no anchor states the gate PER PRODUCT, so that the verdict of one product never stands for another; (4) no anchor gives the gate a closed state in which a missing target or a missing baseline is named BLOCKED. This anchor adds exactly those.

**(A) SCOPE: EVERY DEPLOYABLE BUILD, EVERY DEPLOYMENT, EVERY TAG.** A DEPLOYABLE BUILD is every artifact a consuming project produces to run on its target hardware: a full or partial flashing image, a firmware or over-the-air update package, and an application package installed on the hardware; the project declares its artifact kinds as DATA (§11.4.35), and the one immutable artifact of §11.4.264 is the unit that is tested and promoted. A DEPLOYMENT is any act that puts a deployable build anywhere other than the test hardware of its own live run: writing it to another device, publishing it on a download, update or store channel, attaching it to a release, or handing it to manual QA (§11.4.185, §11.4.236) or to a user. A TAG is any tag that names the build (§11.4.151), of any class. For a deployable build that is not a flashing image, §11.4.293(B) to (F) apply with "flashed" read as "installed on the target and verified there" (§11.4.200).

**(B) THE LIVE RUN: EVERY EXISTING TEST, ON CONNECTED TARGET HARDWARE.** The run that feeds the comparison executes every existing test of the product's suite (the complete retest of §11.4.40; a subset, a spot check or the tests touched by the change is not this run), deterministically (§11.4.50) and LIVE (§11.4.289), on physical target hardware of that product that is connected to the harness while the run executes and is identified by the identity read from the target at run time (its serial and the fingerprint of the build it runs, §11.4.115(F), §11.4.236(1)). An emulator, a simulator, a host-only run, a replayed or copied record, or a run on hardware of another product is never this run. A test that the baseline ran and this run does not report is absent, and absent is not PASS (§11.4.293(B), (C)); no existing test is dropped, skipped or quarantined out of the comparison to let a build pass (§11.4.248). A feature is "not broken" only as far as a test exercises it (§11.4.118), which is why every fixed defect keeps its permanent regression test (§11.4.135).

**(C) PER PRODUCT.** A PRODUCT is each distinct deliverable the consuming project declares as DATA (a product or flavor data pack, §11.4.251, a vendor variant, a target-hardware class), each with its own deployable build, its own target hardware and its own baseline. The gate is evaluated for every product separately, on that product's hardware and against that product's baseline: the verdict, the run and the hardware of one product never stand for another, even when the products share code or a build. A deployment or a tag that covers several products needs the state `RELEASABLE` for every product it covers; for a product in any other state it is refused, and no text describes it as covering that product.

**(D) THE GATE STATE — closed set, four values.**

| State | Holds when | Deployment | Release tag | Dev-class tag (§11.4.293(F)) |
|---|---|---|---|---|
| `RELEASABLE` | the live run of clause (B) completed on connected hardware of the product AND its §11.4.293 verdict against the product's baseline is `NO-WORSE-PROVEN` | allowed, subject to every other seam | allowed, subject to every other seam | allowed |
| `BLOCKED-NO-HARDWARE` | no target hardware of the product was connected and identified for the live run, or the run did not complete on it | refused | refused | refused |
| `BLOCKED-NO-BASELINE` | the live run completed and the §11.4.293 verdict is `INCOMPARABLE-BASELINE-MISSING` | refused | refused | only as §11.4.293(F) states, the blocker stated first |
| `REFUSED-REGRESSED` | the live run completed and the §11.4.293 verdict is `REGRESSED` | refused | refused | only as §11.4.293(F) states, the regressions stated first |

There is no fifth state and no default state. A product's state is computed from machine-written records (§11.4.262, §11.4.293(E)); a product with no live-run record is `BLOCKED-NO-HARDWARE`. Only `RELEASABLE` is green: a blocked or refused product is reported as BLOCKED or REFUSED, with its state, in every report, changelog and release note, never as passed, provisional or skipped. A missing baseline is cured only as §11.4.293(C) states; missing hardware is cured only by connecting hardware of that product and running clause (B), never by a substitute target. A product's first deployable build has no previous build and so no baseline: it stays `BLOCKED-NO-BASELINE` (no deployment, no release tag) until the operator records how a first baseline is accepted (OPERATOR-DECISION-REQUIRED, §11.4.66); this anchor decides nothing about it. The baseline is the build the same hardware carried and was validated with before the new one (§11.4.293(B)). INTERPRETATION (the author's reading, UNCONFIRMED by the operator): the note's "previously released or flashed build" is read as that baseline, which is the previously released build whenever no other build was flashed on that hardware in between.

**(E) RECONCILIATION WITH §11.4.293(F) AND WITH A CONSUMER'S DEV-TAG RULE.** §11.4.293(F) lets a dev-class tag be created whatever the verdict, with the verdict stated first. The operator note says that a build is tagged only after the live run and a proven no-worse comparison. This anchor amends §11.4.293(F) at exactly one point, recorded in a refinement note of §11.4.293: a build without a completed live run on connected hardware of its product (`BLOCKED-NO-HARDWARE`) gets no tag of any class. A dev-class tag of a build in `BLOCKED-NO-BASELINE` or `REFUSED-REGRESSED` keeps the §11.4.293(F) allowance (the verdict first; never described as no worse, stable or validated), and that build is never deployed. A consumer rule that lets a dev tag be cut at any time yields to this point: it tags a build only after the live run. INTERPRETATION (the author's reading, UNCONFIRMED by the operator): the note's "tagged" is read as every tag for the live-run condition and as a release tag for the no-worse condition, because §11.4.293(F) and the consumers' dev-tag classes (consumer DATA, §11.4.290(G)) already permit a labelled dev tag of a compared build; a reading in which a dev-class tag also needs `NO-WORSE-PROVEN` removes that allowance and needs its own recorded operator decision (§11.4.66).

**(F) THE RECORD AND THE REPORT.** For every deployment and every tag the consuming project writes one machine-written gate record per product it covers (§11.4.262): the product, the build identity (version and the sha256 of every artifact file), the target identity read from the hardware, the live-run record (path and sha256), the §11.4.293(E) comparison record (path and sha256) or the reason it is absent, and the state. The changelog and every release note state each product's state first, beside the §11.4.293(F) verdict lines and the §11.4.290(G) lists. A deployment or a tag without the gate record of a product it covers is refused for that product.

**(G) WHAT THIS ANCHOR DOES NOT CHANGE.** §11.4.40, §11.4.50, §11.4.114, §11.4.135, §11.4.151, §11.4.185, §11.4.200, §11.4.236, §11.4.248, §11.4.264, §11.4.289, §11.4.290 and §11.4.292 keep their full text; §11.4.293 keeps every clause except the one point of clause (E). A `RELEASABLE` state does not prove a build correct (§11.4.108): it proves that the build ran whole on connected hardware of its own product and is not worse than its baseline on the measured set.

**Honest boundary (§11.4.6).** The gate shipped with this anchor proves that the RULE is present exactly once, carries its load-bearing phrases and its exact reviewed wording (the canon block, the mirror block and the refinement notes it adds are each pinned in the gate by the sha256 of their text with all whitespace removed, so any change other than whitespace fails the gate until the pin is updated in a reviewed edit of the gate; a pin proves that the wording is the reviewed one, never that it is right), and is mirrored in the four context carriers, indexed and generated, and wired into the seams that carry rules. It does NOT prove that any build was run on hardware, compared, gated or reported: the item-level seam is the recommended gate `CM-RELEASE-GATE-PER-PRODUCT`, registered as deferral `OWED-GATE-185` and NOT claimed implemented (§11.4.227(A)); it and `CM-IMAGE-NO-WORSE-PROVEN` (`OWED-GATE-176`) are the consuming project's work. The constitution ships no flashing, deployment or comparison tool, and it cannot see which hardware a consumer has connected.
