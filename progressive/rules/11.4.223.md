### §11.4.223 — Provenance-marker discipline for design documentation + central open-item registry in the area index (User mandate, 2026-07-22)

**Forensic anchor — proving project (Helix Thready MVP design package, 2026-07-22).** Every statement in the Helix Thready design area carries an inline provenance marker from a closed vocabulary (`[VERIFIED]`, `[OPERATOR]`, `[RESEARCH]`, `[DEFAULT — adjustable]`, `[ASSUMED]`, `[BUILD-NEW]`, `[IN-HOUSE: module]`, `[CONSTITUTION §x]`, `[GAP: id]`, `[OPEN: id]`); the area index maintains the CANONICAL open-item registry — 41 registered ids across nine families, VERIFIED AGAINST THE TREE in both directions (every id in the tree exists in the registry, no registry id is absent from the tree), with per-id state (open / narrowed / closed, each closure citing the closing revision) — and a verified-vs-assumption ledger separating measured fact from proposed default from named scaffold.

**The mandate.** Every design document in a governed project MUST carry provenance discipline: (1) **Mandatory marker vocabulary** — a closed, project-declared marker set whose minimum core is `[VERIFIED]` (established from source/runtime/measurement, with the evidence or check date), `[OPERATOR]` (an operator decision), `[DEFAULT — adjustable]` (a proposed default pending review), and `[OPEN: id]` (an unresolved item with a stable id); projects extend the set (`[RESEARCH]`, `[ASSUMED]`, `[BUILD-NEW]`, `[GAP: id]`, `[IN-HOUSE: …]`, `[CONSTITUTION §x]`) per §11.4.35. A load-bearing claim with no marker reads as UNVERIFIED — and presenting an assumption as verified is a §11.4.6 violation of §11.4 PASS-bluff severity at the design-documentation layer. (2) **Every unresolved decision is an `[OPEN: id]`** — with a stable, never-renumbered id (§11.4.54 discipline), owned by a named file, and never papered over with an invented answer. (3) **Central registry in the area index** — the design area's index maintains the SINGLE canonical open-item registry: every `[OPEN: id]` in the tree appears in it, every registry row names its owning file(s) and state, and the registry is TREE-VERIFIED in both directions on every consolidation pass (an id in the tree missing from the registry, or a registry ghost with no tree presence, is a violation — the §11.4.186 consistency discipline applied to design opens); closures cite the closing revision, and narrowed items record exactly what closed and what remains. (4) **Opens map to tracked work** — registry items map to the project's workable-item tracking (§11.4.15 / §11.4.54 / §11.4.93) so the §11.4.197 completion mandate applies: a design open is driven to closed-with-evidence or explicitly-closed-with-reason, never silently abandoned.

**Honest boundary (§11.4.6).** Markers prove the EPISTEMIC STATUS of each claim, not its truth — a `[VERIFIED]` marker is only as good as its cited evidence (§11.4.123), and the registry proves open-item ACCOUNTING, not progress (§11.4.197 owns completion). This anchor binds the DESIGN area to the same honesty regime the tracker anchors give code — it cites §11.4.15/.54/.93/.186/.197 rather than duplicating them.

Classification: universal (§11.4.17) — the consuming project supplies its marker-set extensions, id families, area-index path, and tracker binding per §11.4.35.
