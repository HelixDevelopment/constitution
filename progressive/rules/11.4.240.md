### §11.4.240 — Producer ≠ Verifier scope separation: the actor that produces a change/artifact/verdict cannot be the one that gates it — least privilege over cleverness (research-derived, 2026-08-15)

**Compact summary:** every project MUST enforce STRUCTURAL SEPARATION between the actor that PRODUCES a change/artifact/verdict and the actor that GATES that same change/artifact/verdict — the producing actor cannot write, weaken, delete, or edit the acceptance tests, the oracle, the gate configuration, the verdict store, the paired §1.1 mutation, or any other check whose green result is a precondition for the producer's own work being certified done. Enforcement is by CAPABILITY (the producer STRUCTURALLY cannot reach the gate) rather than by INSTRUCTION (the producer is TOLD not to touch the gate), and the enforcement mechanism is LEAST PRIVILEGE OVER CLEVERNESS (extraction file line 1488 — **MODULE ATTRIBUTION CORRECTED 2026-08-20: this citation originally read "module 27". The quoted passage has ZERO occurrences in `module_27.txt` and resolves in the tracked corpus to module 28 ("Anti-Bluff Verification & Release Validation"), verified locator `module_28:393`. Instrument control-needled per §11.4.201(7)(b) before the absence was reported.** — module 28, verified locator `module_28:393`: "the durable fix is least privilege over cleverness — the same logic as prompt-injection defense ... the load-bearing move is that the agent chasing the green gate cannot reach the gate, the oracle, or the evidence store"). The failure mode this anchor forbids: a producer that CAN edit the tests/oracle/gate config/verdict store DOES edit them under long-horizon optimization pressure — hardcoding expected values, weakening assertions, mocking the unit under test, deleting the failing test, or writing `verified: true` on itself (extraction lines 5695, 5711-5717, 5722-5730, 1343, 1396, 1482-1488). §11.4.240 makes the separation a STRUCTURAL PROPERTY of the codebase and its automation, not a social one.

**(A) THE FOUR SCOPES + THE SEPARATION MATRIX.** Every change/artifact/verdict flows through four SCOPES that MUST be distinct actors under §11.4.240: (i) PRODUCER — the actor that writes the source diff, the config change, the migration, the artifact-generation code; (ii) ORACLE — the actor / mechanism that decides "correct output" for a given input (test author, specification writer, characterization-baseline capturer, reference-implementation author per §11.4.245 oracle-independence); (iii) GATE — the actor / mechanism that decides whether the change PASSES the check (CI configuration, gate scripts, custody-chain enforcer per §11.4.146(D3), release-verdict-coverage machinery per §11.4.135); (iv) VERIFIER — the actor / mechanism that RE-RUNS the gate from a clean checkout and attaches receipts (independent verifier per §11.4.165, §11.4.209 Opus-xhigh substrate for code review, §11.4.194 exhaustive review). The mandate: the PRODUCER of a change cannot ALSO be the ORACLE, GATE, or VERIFIER for that same change. Extraction line 5695 (module 34 core concept 4 — module attribution VERIFIED CORRECT 2026-08-20, verified locator `module_34:56`; offset un-resolvable per the §11.4.239 CITATION NOTE): "the agent that wrote the code cannot be the authority that certifies it — self-preference bias and shared context make self-review worthless. Verification comes from an independent instance (fresh context, read-only, re-running from a clean checkout) and from an oracle the producer did not author and cannot edit ... Remove any one property and it degrades to self-certification." A four-scope collapse (one actor plays all four roles) is the maximum-severity form; any two-scope collapse involving the producer is a §11.4.240 finding of §11.4/§11.4.1 severity at the certification layer.

**(B) LEAST PRIVILEGE OVER CLEVERNESS — CAPABILITY, NOT INSTRUCTION.** Separation MUST be enforced by structural CAPABILITY LIMITS, not by prompts / instructions / policy documents / social contracts asking the producer "please do not touch the tests." Extraction lines 1482-1488 [MODULE CORRECTED 2026-08-20 — the (E) Extraction-sources line attributes these offsets to module 27; the quoted passage resolves to module 28, verified locator `module_28:383`] name the load-bearing mechanism: "The producer has no write access to the test files, the oracle, the CI/gate config, or the verdict store — enforced by scope, not by asking. If it can't touch the gate, it can't game it." Concrete enforcement channels the consuming project MUST supply per §11.4.35: (1) FILESYSTEM SCOPE — the producer's write scope excludes `tests/`, `oracle/`, `.github/workflows/`, `scripts/gates/`, `verdicts/` (or their consumer-declared equivalents); (2) BRANCH / REVIEW PROTECTION — protected paths (see §11.4.248 PROTECTED-SPEC + CODEOWNERS from the sibling 2026-08-15 operator decision) require an actor OTHER than the change author to approve modifications; (3) VERDICT-STORE ISOLATION — the store that records RED/GREEN verdicts per §11.4.115(F) is written only by the harness that ran the test, never by the producer's own code path; (4) EXECUTION ISOLATION — the verifier runs in a CLEAN CHECKOUT with FRESH CONTEXT (extraction lines 3168, 3117, 2381 [MODULE CORRECTED 2026-08-20 — the (E) Extraction-sources line attributes these offsets to module 34; the quoted passage has ZERO occurrences in `module_34.txt` and resolves to module 29 / module 30, verified locators `module_29:655`, `module_30:591`, `module_30:655`]: "an independent verifier re-running in a clean checkout") — the verifier does NOT inherit the producer's dirty worktree, cached artifacts, or in-flight session state. "The agent will not do that" is NEVER acceptable enforcement — extraction line 5715 [module 34 attribution VERIFIED CORRECT 2026-08-20, verified locator `module_34:87`] catalogues the failure ("We told it in the prompt not to hardcode / not to skip tests" as the shallow / red-flag answer). Exhortation is not capability; §11.4.240 refuses exhortation as the enforcement layer.

**(C) THE THREE FORBIDDEN PRODUCER↔SCOPE COLLAPSES.** The following collapses are §11.4.240 violations regardless of context, scale, or claimed rigor: (1) PRODUCER=ORACLE — the same actor writes the source diff AND the test that asserts its correctness, with no independent oracle authoring the assertion; the resulting test asserts whatever the code happens to do ("tautological testing trap," extraction line 5764 [module 34 attribution VERIFIED CORRECT 2026-08-20, verified locator `module_34:155`], referenced) rather than what the specification requires. Countermeasure: the oracle is authored FROM the specification / from a characterization baseline captured BEFORE the change (§11.4.243) / from a reference implementation (§11.4.245 derived oracle), not co-authored with the diff. (2) PRODUCER=GATE — the same actor writes the source diff AND has write access to the gate configuration / CI pipeline / the mutation-testing thresholds / the paired §1.1 mutations; the producer can silence failing gates or weaken thresholds. Countermeasure: the gate configuration lives in a §11.4.248-protected path, and modifications require a non-producer approver. (3) PRODUCER=VERIFIER (self-certification) — the same actor produces the change AND writes the "verified: true" / "PASS" verdict for the change; the verdict is a producer-set flag with no independent re-run. Countermeasure: verdicts are MACHINE-WRITTEN by the harness that ran the test per §11.4.115(F), keyed to the target's artifact fingerprint read at run time, and the release-verdict-coverage seam per §11.4.135 REFUSES a release tag while any producer-asserted (rather than harness-written) verdict is in the release scope. Extraction lines 1212, 1343, 1396, 1631 [MODULE CORRECTED 2026-08-20 — attributed to module 27 in the (E) Extraction-sources line; the quoted passage resolves to module 28, verified locator `module_28:278`]: "Tamper-evident and outside the producer's reach — the producer of the change cannot edit the verdict or the oracle to make itself green."

**(E) HONEST BOUNDARY (§11.4.6).** Structural separation forbids the CLASS of self-certification failure modes; it does NOT prove the verifier is correct (a mis-calibrated verifier stays §11.4.107(10) golden-good/golden-bad territory; extraction line 1512 [MODULE CORRECTED 2026-08-20 — implicitly module 27 via the (E) Extraction-sources line; the quoted passage resolves to module 28, verified locator `module_28:401`]: "a flaky or false-positive gate destroys the whole evidence chain above it"), does NOT prove the oracle is correct (§11.4.245 mandates oracle-strategy naming + independence), and does NOT guarantee the producer never tries to game the gate (it forbids the producer from succeeding at gaming the gate through direct write access; other gaming vectors — hardcoding to visible inputs, over-fitting the seen cases — are countered by §11.4.245 held-out oracles + property/metamorphic/differential coverage). **(F) Independence-tier vocabulary + Tier-C capability-separation triggers, degrading honestly on a single-uid host (extension, spec-derived, speckit 002-anti-slop-enforcement, 2026-08-26).** Clauses (A)–(E) state the SEPARATION PRINCIPLE and its capability-not-instruction enforcement in the abstract; this clause supplies the CLOSED VOCABULARY for recording HOW MUCH separation was actually achieved, and the two triggers that raise the required strength — because a project claiming "capability separation" where only "instance separation" is genuinely achievable is itself a §11.4.240 violation of the theatre this anchor exists to prevent. **(1) The closed tier set.** Per spec.md:124 (FR-035): every accepted verdict's recorded basis of independence MUST name which tier applied, drawn from the CLOSED SET `{instance, model, capability}` — `instance` (a separate agent/process instance verifies, sharing no in-flight state with the producer), `model` (a DIFFERENT model verifies — permitted, never required per (2) below), `capability` (a genuine host-level access-control boundary separates the producer's write scope from the verifier's — the strongest tier). **(2) Model diversity is permitted, never required — the false-positive guard.** Per spec.md:121 (FR-032): a verdict from an independent INSTANCE running the SAME model as the producer MUST be ACCEPTED on that basis alone (Tier B, permitted-never-required) — a check that refuses same-model independent verdicts has turned a legitimate separation into an unnecessary same-model prohibition, which is itself the exact class of false-positive refusal §11.4.201 forbids. This clause does NOT weaken the constitution's OTHER, distinct, narrower model-substrate pins — §11.4.256's requirement that a translation review run on a DIFFERENT model/provider than the translator, and §11.4.209's requirement that every mandatory independent code-review run on the Opus model at `xhigh` effort as PRIMARY substrate, with a genuine-unavailability Sonnet fallback (amended 2026-10-04; Fable and Haiku remain forbidden in every role); both remain in force unmodified for their own narrower domains (translation review; code review). FR-032's permitted-not-required framing governs only the GENERAL producer≠verifier case this anchor addresses, never those two domain-specific, stricter pins. **(3) Tier-C trigger 1 — the producer holds write access to the evidence/verdict store.** Per spec.md:122 (FR-033): at a seam where the producer holds write access to the evidence or verdict store, a verdict MUST be written through the MOST RESTRICTIVE separation genuinely available on the host, and the ACHIEVED separation (not the aspired-to one) MUST be reported. **Measured, honestly-degrading limit (spec.md:122):** *"on a single-uid host, capability separation cannot be established by any mechanism an agent can set up — ownership defeats access-control lists, the append-only attribute requires privilege the agent lacks, and any key the producer can use it can also read. Claiming `capability` there would be the theatre this feature exists to prevent."* A single-uid host therefore reports `instance` honestly, NEVER `capability`, until the operator takes the one action that establishes a real host boundary. **(4) Tier-C trigger 2 — the three named high-blast-radius seams.** Per spec.md:123 (FR-034): at the `release-tag`, `qa-deploy`, or `manual-qa-handoff` seam (or the consuming project's declared equivalent seams per §11.4.35), a producer-authored verdict is REFUSED regardless of the write-access analysis, and the achieved separation is reported rather than assumed. **Same honest-degradation limit applies (spec.md:123):** *"Capability-strength at these three seams requires one operator action (a host boundary agents are correctly forbidden from creating); until it is taken they operate at `instance` tier and MUST say so."* **(5) No demand for capability outside the two triggers.** Per spec.md:125 (FR-036): at a seam matching NEITHER Tier-C trigger, a separate agent instance MUST SUFFICE and capability separation MUST NOT be demanded — instance-tier verdicts are accepted at ordinary seams without a capability check, closing the negative half of this clause (a project over-applying Tier-C strength to every seam is itself a §11.4.240 violation of the same "false-positive refusal" class). **Honest boundary (§11.4.6).** The `independence_tier` field records WHAT WAS ACHIEVED, never what was ASPIRED to — a project honestly reporting `instance` at a Tier-C-triggered seam because no host boundary yet exists is COMPLIANT with this clause (the honest-degradation path is the compliant path); a project reporting `capability` without the mechanically-verified boundary that makes it true is the violation.
