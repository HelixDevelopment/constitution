### §11.4.219 — Per-app screen catalogues: full-IA coverage per surface, per-platform chrome variants, honesty markers for unbuilt behavior (User mandate, 2026-07-22)

**Forensic anchor — proving project (Helix Thready MVP design package, 2026-07-22).** Helix Thready's `design/screens/` carries a screen catalogue PER SURFACE — 13 web screens + an interactive prototype shell walking the four key journeys, 11 device-framed 390×844 mobile artifacts with an Android/iOS chrome TOGGLE (+ HarmonyOS/Aurora port notes) covering EVERY node of the wireframes' information architecture, a desktop shell with per-OS title bars / menus / tray / file-drop mocks, ten 80-column TUI mockups covering the full state machine, and a 3-page marketing set with a claims-traceability register. Undefined product behavior is rendered HONESTLY: placeholder billing amounts labelled as placeholders, an unspecified forgot-password flow linked with an inline note instead of a fake flow, an undecided channel source rendered as a DISABLED tile — each carrying its `[OPEN: id]`.

**The mandate.** Every application/surface a governed project ships MUST have a screen catalogue: (1) **Full-IA coverage** — the catalogue covers EVERY node of the surface's information architecture (every screen of the wireframe/IA contract); a screen present in the IA but absent from the catalogue is a coverage gap tracked per §11.4.223 — never silently skipped. (2) **Per-platform chrome variants** — where one design serves several host platforms, the catalogue renders the platform chrome variants (mobile OS chrome toggle, per-OS window chrome, terminal-width constraints) rather than pretending one chrome fits all; ports not yet designed are tracked, not faked. (3) **Self-contained, token-bound, both themes** — each screen is a self-contained artifact binding the §11.4.216 tokens, rendered light + dark, populated with REALISTIC product data (never lorem-ipsum for load-bearing content), carrying its per-screen state contract (loading / empty / error / populated states declared). (4) **Honesty markers for unbuilt behavior** — where the backing backend, contract, or product decision does not exist, the screen MUST say so: a `[GAP: id]` / `[OPEN: id]` marker (registered per §11.4.223), a labelled placeholder, an inline note, or a disabled control — NEVER a designed-as-if-real fake flow; designing a flow for an undecided behavior and presenting it as settled is a §11.4 PASS-bluff at the product-design layer.

**Honest boundary (§11.4.6).** A screen catalogue is the DESIGN contract, not the implementation: it proves every IA node has a designed, state-complete, theme-complete rendering — implementation correctness stays with §11.4.170 host-rendered pixel proof, §11.4.190 web-quality proof, and the §11.4.185 manual-QA final gate.

Classification: universal (§11.4.17) — the consuming project supplies its surface list, IA contract, chrome-variant matrix, and realistic-data corpus per §11.4.35. Composes §11.4.6 / §11.4.162 / §11.4.170 / §11.4.185 / §11.4.190 / §11.4.216 / §11.4.218 / §11.4.223. Propagation gate `CM-COVENANT-114-219-PROPAGATION` (literal `11.4.219`) + recommended gate `CM-SCREEN-CATALOGUE-FULL-IA` (every IA node maps to a catalogue screen or a registered `[OPEN]` id; every screen renders both themes; every screen whose backing contract is absent carries its honesty marker) + paired §1.1 mutation (remove a screen without registering the gap → gate FAILs; strip an honesty marker from an unbacked flow → gate FAILs; strip the literal → propagation gate FAILs; gate-code = separate work item).

**Canonical authority:** constitution submodule [`Constitution.md`](Constitution.md) §11.4.219.

Non-compliance is a release blocker regardless of context. No escape hatch — no `--partial-ia-coverage`, `--one-chrome-fits-all`, `--fake-flow-OK`, `--lorem-ipsum-content`, `--single-theme-screens` flag exists.
