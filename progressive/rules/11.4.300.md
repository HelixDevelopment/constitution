### §11.4.300 — Workable items are mirrored to the Issues of every declared upstream, recursively and always in sync, as a default-OFF mechanism a project turns on: the database is the source of truth, the tracker is a one-way mirror, visibility follows the owning repository, an undetermined leg is UNCONFIRMED and never in sync (User mandate, 2026-11-24)

**Forensic anchor — verbatim operator order (2026-11-24, CRITICAL):** all workable items (to do, in progress, done) are always created and kept up to date in the Issues of every supported upstream of the umbrella and of every submodule recursively (GitHub, GitLab, Gitea at m3w and Codeberg, GitFlic, GitVerse), in sync with Docs Chain, the SQLite database, the status documents and all trackers; a constitution-level default mechanism, OFF by default, ON for the project that turns it on.

**The gap this anchor closes (stated so it is not restated elsewhere, §11.4.227).** §11.4.93 makes the SQLite database the single source of truth of workable items; §11.4.294(I) specifies a one-way database-to-tracker mirror and §11.4.296 admits issues assigned to a declared account as items, but nothing kept the Issues of every upstream in step with the database, and no instrument asked a tracker whether it still matched.

**(A) DEFAULT AND SWITCH.** The mechanism is OFF for every project. A project turns it on by a tracked declaration `.workable-items-sync.yaml` (`enabled: true`); recursion over own-org submodules is a declared key (`scope.recursive`); the run mode is `dry-run` unless a recorded operator decision sets `apply`. The constitution ships the engine, the host adapters, the verifier, the template (`templates/workable-items-sync.yaml.template`, which MUST ship `enabled: false`) and the hook and Docs Chain wiring; a consumer never copies them (§11.4.28, §11.4.106) and carries only its small declaration.

**(B) DIRECTION.** The database (§11.4.93) is the source of truth; the tracker is a mirror. No tracker edit changes an item, its status or its closure; a tracker issue that disagrees with its item is reset by the next run. The only inbound path is §11.4.296 intake, once per issue, and an issue the engine created or adopted (recognised by its hidden footer) is never imported again, so no loop exists.

**(C) SCOPE.** Every item of an enabled project, of any status and any type, appears as exactly one issue per declared upstream whose repository exists and whose Issues are enabled. The upstream set of a repository is derived from its declared upstream recipes and remotes, not from a fixed host list; a host or repository that cannot take the item (absent repository, Issues disabled, capability unverified) is reported UNCONFIRMED for that leg and is never counted in sync. Third-party submodules are never synced.

**(D) VISIBILITY.** An item is mirrored only to the trackers of its OWNING repository; visibility is resolved from the live provider answer, never from a cached claim, and an unresolvable visibility is `undetermined` and BLOCKS the item (never defaults to public). A private item is never written to a public tracker, and a public tracker never receives a pointer carrying private title text. Only the fields `atm_id`, `type`, `status`, `title`, `severity` and the description are mirrored; verbatim operator quotes (forensic anchors), the long body, reproduction evidence and test diaries are NEVER sent to any tracker. A redaction gate scans every outgoing payload for secret shapes and personal-data patterns before any write; a hit is a hard stop naming the item by id only.

**(E) NEVER OUT OF SYNC.** The mirror carries a stable key (the item id as a title prefix and a hidden body footer) so identity never depends on the issue number; a per-tracker mapping table in the database; a content hash so an unchanged item makes no API call; idempotent create, update, close and reopen (an obsolete item closes as not planned where the host supports it; an operator-blocked item stays open with a status label); a dry-run default with `--apply` required to write; rate-limit-aware, resumable batches. A three-valued verifier (0 every enabled leg matches the database; 1 drift, naming item ids and trackers; 2 cannot determine; 2 is never a pass; precedence 1 over 2 over 0) with paired mutations runs on the commit and merge triggers, on the Docs Chain verify and on a schedule of at most 24 hours, and never inside CI/CD (§11.4.156).

**(F) DOCS CHAIN.** The mirror is a node of the project's Docs Chain context (§11.4.106): the database, the status documents, the exports and the trackers are regenerated and verified together, and the verify fails when any is stale.

**(G) HONEST BOUNDARY (§11.4.6).** A host whose API for a verb is unverified is reported UNKNOWN, and its leg stays UNCONFIRMED until a live create and read-back proves it (§11.4.289: a test double proves only the tool's own logic, never a host). Mirroring proves the tracker matched the database at that moment, not that the item is correct.

**(H) CARVE-OUT FROM THE §11.4.296 SCOPE RULING (operator order of 2026-11-24 governs).** The operator order quoted above (2026-11-24) is LATER than the scope ruling of 2026-11-05 that §11.4.296(A) quotes ("we will NOT import our other workable items there") and it governs where the two differ. An issue created by THIS engine and recognised by its hidden footer `<!-- workable-item: ID | sha256: HASH -->` is a mirror issue, and a mirror issue is exempt from clauses (1), (2) and (4) of §11.4.296(A): the engine may create it, and may comment on, label, close and reopen it; a configuration that declares this mirror is not "invalid" under clause (4), and the issue-creation check of §11.4.296(J) (and its owed gate `CM-GITHUB-ISSUES-SYNC-EVIDENCE`) MUST NOT fail a footer-marked mirror issue created by `scripts/issue_sync/`. Nothing else is exempt: an issue WITHOUT the footer is never created, adopted, commented, labelled, changed or closed by this engine (an unkeyed issue whose title merely starts with the item id is reported as an anomaly and left alone); no other tooling gains the exemption; clause (3) and every import rule of §11.4.296 stand unchanged; an engine-created issue is never imported back (§11.4.296 "ours" rule).
