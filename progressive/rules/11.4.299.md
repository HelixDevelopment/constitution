### §11.4.299 — Merged is not delivered until pushed: after every merge into `main`, in the project root and in every own-org submodule touched, the merged `main` is fast-forward pushed to EVERY declared upstream and read back per upstream with `git ls-remote` before the work is reported done or the parent pointer moves; a partial push is a defect; a blocked push is reported BLOCKED, never bypassed (User mandate, 2026-11-24)

**Forensic anchor — verbatim operator directive (2026-11-24):** "After we merge PRs and update our main repo(s), all changes we bring into main MUST BE fully pushed to ALL UPSTREAMS! Make sure this is also clear in our root Constitution (submodule) and always respected!"

**The gap this anchor closes (stated so it is not restated elsewhere, §11.4.227).** §2.1 makes the multi-upstream push the norm; §11.4.36 installs the upstream recipes on clone; §11.4.71 and §11.4.113 require the push to every upstream as a fast-forward; §11.4.88 moves the push to the background; §11.4.288(B)(1) ends landing with a fast-forward push to every upstream and (B)(4) requires a vehicle's commits to be on every upstream before it is retired; §11.4.297(F)(4) requires the per-upstream parity table for a SUBMODULE pin bump. What none of them says in one place is the delivery boundary itself: under pull-request delivery the merge is performed ON ONE HOSTING PLATFORM, so at the moment a pull request reads "merged" exactly one upstream carries `main`, and the other upstreams are behind until somebody pushes them. Reporting "merged" as "delivered" in that window, for the project root or for a submodule, leaves every other mirror stale with no signal. This anchor fixes the definition and makes it checkable.

**(A) DEFINITION: MERGED MEANS MERGED AND PUSHED TO EVERY UPSTREAM.** After a merge into `main` of an own repository (the project root, every own-org submodule at any depth, every constitution hub engine; §11.4.288 Terms), whether the merge was made on a hosting platform (§11.4.297), by `git merge --ff-only` (§11.4.288(B)(3)) or by the §11.4.113 merge-onto-latest-main procedure, the work is NOT delivered, NOT done, and MUST NOT be reported as merged-and-done, closed, released or handed back, until the merged `main` tip is on EVERY declared upstream of THAT repository. A DECLARED UPSTREAM is the union, de-duplicated by normalised URL, of (1) every push URL of every remote (all of them, read with `git remote get-url --all --push <remote>`; the form without `--all` prints the first URL only and undercounts a fan-out), and (2) the repository of every ENABLED recipe `upstreams/*.sh` (`UPSTREAMABLE_REPOSITORY`; a `*.disabled` recipe is not enabled), as installed by §11.4.36. The push is a FAST-FORWARD of the remote `main` to the merged sha through the project's sanctioned push path (§2.1, §11.4.88), never forced (§11.4.113 is unchanged and absolute: no `--force`, no `--force-with-lease`, no `+ref`).

**(B) THE READ-BACK IS THE PROOF.** For every declared upstream the agent runs the read-only `git ls-remote <upstream> refs/heads/main` AFTER the push and records the tip. The verdict per upstream is closed: `CURRENT` (tip equals the merged sha), `AHEAD` (the tip contains the merged sha), `BEHIND` (push owed), `DIVERGED`, `DIFFERS` (tip not in the local object store, direction unknown), `NO-BRANCH`, `UNREACHABLE`, `EXEMPT` (clause (E)). Only `CURRENT`, `AHEAD` and `EXEMPT` are parity. A push tool's exit status is not parity; "pushed to all upstreams" is never written without the per-upstream read-back (§11.4.6, §11.4.297(F)(4)); the report carries the table, one row per upstream, tip and verdict.

**(C) ORDER FOR SUBMODULES AND THE PARENT POINTER.** A submodule's merged `main` reaches every upstream of THE SUBMODULE first; only then does the parent record the new gitlink and the `helix-deps.yaml` `ref` (§11.4.31) together in the parent's change (§11.4.288(D), §11.4.297(F)(3)/(4)). A parent pointer to a commit that any upstream of the submodule lacks is a defect: a fresh clone from that upstream cannot initialise the submodule. The parent's own merge is then subject to clauses (A) and (B) for the parent's upstreams. The wave is complete only when the leaf submodule, each intermediate repository and the root all read parity.

**(D) A PARTIAL PUSH IS A DEFECT; A BLOCKED PUSH IS REPORTED.** A push that reaches some upstreams and not others is a defect of the delivery, recorded as such, and re-driven (fetch, integrate per §11.4.113 if the remote moved, push again) until parity or until the block is established. A push refused by a gate, a hook, a branch protection, an authentication failure or a non-fast-forward is reported as `BLOCKED` with the upstream, the refusal text with any credential removed (§11.4.10) and the owed action; it is NEVER bypassed (no `--no-verify`, no hook disabled, no force, no credential borrowed) and never silently skipped. While any upstream is `BLOCKED` or `UNREACHABLE` the work item is not done and the report says which upstream is behind and by how many commits; "UNCONFIRMED parity" is the honest state, never "done".

**(E) VISIBILITY AND DECLARED MIRRORS.** Every push stays inside the visibility rule of the repository: a repository whose only declared upstreams are private stays private, and nothing is pushed to an upstream whose visibility the project cannot establish for a repository that must stay private (the project's content-boundary rules govern). A mirror that is NOT fed by `git push` of `main` — for example a public mirror fed by a reviewed snapshot or export — is exempt from clause (A) ONLY where a RECORDED operator decision (§11.4.66) declares the repository, the mirror and the reason as DATA in a tracked file; the exemption is read by the verification tool, is printed as `EXEMPT` with its reason on every run, never applies by default, and an exemption with an empty reason is refused (the run is `CANNOT-DETERMINE`). This constitution names no repository or account.

**(F) MECHANICAL ENFORCEMENT (§11.4.75, §11.4.205).** The constitution ships the instruments (the clause (H) check is `scripts/sync/verify_constitution_latest.sh`; paired mutations L1 to L5 in the same test): `scripts/sync/verify_upstream_parity.sh` (read-only; enumerates the declared upstreams of one repository with `--repo`, or of a whole fleet derived from `.gitmodules` with `--fleet`, never from a hardcoded roster; exits 0 every upstream `CURRENT`, `AHEAD` or `EXEMPT`, 1 any `BEHIND`, `DIVERGED`, `DIFFERS` or `NO-BRANCH`, 2 cannot determine — a repository with no declared upstream, an `UNREACHABLE` upstream, an uninitialised own submodule, an exemption without a reason; a 2 is never a pass and a 1 outranks a 2) and `scripts/sync/push_all_upstreams.sh` (the guarded post-merge helper: dry run by default, `--apply` pushes `SHA:refs/heads/main` to each `BEHIND` upstream with no force construct, reports `PUSHED` or `BLOCKED`, and ends with the verifier's read-back). The recommended gate `CM-UPSTREAM-PARITY-AFTER-MERGE` is `scripts/gates/cm_upstream_parity_mutation_test.sh`'s subject: its paired §1.1 mutations prove the verifier catches a behind upstream, a diverged upstream, a recipe-only upstream, a second push URL of one remote, an unreachable upstream, an empty declaration and an exemption without a reason, and that the helper never forces and never touches a diverged upstream. A consuming project wires the verifier (a) as a check in its check registry with the paired proof, (b) into its post-merge step of the delivery tooling, so a pull request is reported landed only after the read-back, and (c) into its pre-push or session-end sweep over the whole fleet. Enforcement claims carry ENFORCED, PROVISIONAL or UNCONFIRMED (§11.4.297(G)); a project that has not wired (a) to (c) reports the rule as PROVISIONAL, not ENFORCED.

**(G) WHAT THIS ANCHOR DOES NOT CHANGE.** §2.1, §11.4.36, §11.4.71, §11.4.88, §11.4.113, §11.4.288 and §11.4.297 keep their full text; this anchor adds the delivery definition of clause (A), the read-back of clause (B), the order of clause (C), the defect and BLOCKED vocabulary of clause (D), the visibility and exemption rule of clause (E) and the instruments of clause (F). Force-push stays forbidden without exception (§11.4.113).

**(H) THE CONSTITUTION SUBMODULE IS ALWAYS THE LATEST UPSTREAM, RECURSIVELY.** A consuming project's constitution submodule MUST always be the latest upstream constitution `main`, with every nested submodule of it initialised and at its recorded pin and current against its own remote. It moves only by `git fetch` then `git merge --ff-only` (the pin move classified first: zero divergent; never a rebase, never force; a divergence is stopped and reported), the consuming repository's gitlink and its `helix-deps.yaml` `ref` move together in one change, and that change is delivered and pushed to every upstream of the consuming repository under clauses (A) to (D). `scripts/sync/verify_constitution_latest.sh --root <project>` is the read-only instrument: exit 0 the checkout equals the recorded gitlink and the upstream `main` and every nested submodule is initialised, at its pin and at its remote head; exit 1 BEHIND, AHEAD, DIFFERS, gitlink DRIFT, an uninitialised or not-at-pin nested submodule or a nested submodule behind its remote; exit 2 cannot determine (an unreachable remote, a missing submodule, a recursive submodule status that itself fails because a nested gitlink has no mapping); a 2 is never a pass and a 1 outranks a 2. It reports; it never fetches, moves or pushes anything.

**Honest boundary (§11.4.6).** `git ls-remote` proves what the hosting platform answered at that moment; it proves the tip, not that the content is correct, and a later push by someone else can move it (the read-back is a reading of a time, not a property). The verifier reads `refs/heads/main` (or the `--branch` given); other refs are not covered. The shipped paired test uses throwaway local repositories as upstreams to test the tool's own logic; the proof that a real merge reached the real upstreams is the live per-upstream read-back this anchor demands, recorded with the delivery.
