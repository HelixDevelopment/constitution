### §11.4.220 — Open-first design tooling: self-hosted open platforms are primary; proprietary tools are import/export targets only; design sources live in-repo in open formats (User mandate, 2026-07-22)

**Forensic anchor — proving project (Helix Thready MVP design package, 2026-07-22).** Helix Thready's tooling capability check (`opendesign/TOOLING.md`) and export capstone prove the posture: every design source lives IN-REPO in open formats (7 SVG brand masters, `tokens.css`, JSON manifests + 28 genuine `.od-figma.json` IR captures, 6 hand-authored Lottie JSONs, self-contained HTML screens); the OpenDesign daemon/CLI status was RUNTIME-PROBED (live health endpoint, CLI round-trip, headless-vs-operator matrix), never assumed; and Figma is an IMPORT-ONLY bridge — the import plugin pins `networkAccess: ["none"]`, no cloud token exists, and the docs state verbatim that any "pushed to Figma cloud" claim from that environment would be a fabrication. The actual proprietary-tool file is `[OPEN]`-tracked, not claimed.

**The mandate.** Every governed project's design workflow MUST be OPEN-FIRST: (1) **Self-hosted open platform primary** — the collaborative design platform is an open-source, self-hostable tool (PenPot as the standing default), run SELF-HOSTED; together with the §11.4.162 OpenDesign engine it forms the primary design toolchain. (2) **Consumption ONLY via the PenPot submodule** — ALL PenPot mechanisms and utilities (the deployment recipe, RPC client utilities, access-token minting, import tooling, browser-hydration automation, MCP wiring) live in the dedicated reusable PenPot submodule (working name `vasic-digital/PenPot`; the final repository name was UNCONFIRMED at this anchor's writing — the generic referent "the PenPot submodule" is normative until the name lands), inherited BY REFERENCE per §11.4.28; the PenPot submodule itself consumes the Containers submodule (§11.4.76, rootless per §11.4.161) for orchestration and DECLARES that dependency in its §11.4.31 `helix-deps.yaml` manifest. Projects MUST NOT hand-roll PenPot deployment or client code outside the submodule — a missing capability is extended UPSTREAM in the submodule per §11.4.74, never worked around locally. The submodule carries MECHANISMS/UTILITIES ONLY, never project design content — per-project design sources stay in the project repo per clause (4). (3) **Proprietary tools are optional bridges, never the source of truth** — proprietary design tools (Figma or equivalent) MAY be used as import/export/review targets via documented bridge kits (variables payloads, IR captures, import guides), but NO design value may exist ONLY inside a proprietary tool or its cloud: the moment a decision lands, its canonical form lands in-repo. (4) **In-repo open formats** — design sources are versioned in the repository in open, diffable formats: SVG (vector masters), CSS (tokens per §11.4.216), JSON (manifests, IR captures, variables payloads), Lottie JSON (motion per §11.4.221), self-contained HTML (screens/library per §11.4.218/§11.4.219); binary proprietary formats are derived artifacts at most, never sources — the §11.4.215 discipline applied to design: a design that binds work MUST live tracked in the repo. (5) **Runtime-probed capability claims** — every tooling claim ("the daemon runs", "the CLI exports", "import works") is established by a runtime probe recorded as evidence (§11.4.201 real-condition discipline; §11.4.99 latest-source verification for format contracts), with an explicit headless-vs-operator-interactive matrix and an HONEST-LIMITS section; a cloud push claimed without a real credentialed run is a fabrication of §11.4 PASS-bluff severity. (6) **PenPot automation operational rules (research-verified)** — (a) the HEADLESS write path is the token-authenticated **RPC API**: access tokens (minted under the backend's `enable-access-tokens` flag, handled per §11.4.10) are the MANDATED auth mechanism for all automation — interactive OAuth relays / session-cookie scraping are FORBIDDEN as automation auth; (b) API-created PenPot files REQUIRE a **browser hydration pass** before handoff — thumbnails and text layout are materialized by the browser runtime, not by the write API, so a handoff of an unhydrated API-created file claimed render-ready is a §11.4 PASS-bluff at the design-handoff layer; the hydration pass is automated via the PenPot submodule's browser-hydration utility and its execution is recorded as evidence (§11.4.69).

**Honest boundary (§11.4.6).** Open-first governs WHERE truth lives and WHICH tool is primary; it does not forbid operators using proprietary tools for review/hand-off, and it does not claim bridges exist before they are built — missing bridges (PenPot/Lottie export, proprietary-file creation) are `[OPEN]`-registered work per §11.4.223/§11.4.197; and until the PenPot submodule's final repository name is confirmed, citations use the generic referent honestly rather than asserting an unconfirmed name as fact.

Classification: universal (§11.4.17) — the consuming project supplies its platform choice within the open-first constraint, its PenPot-submodule pointer + configuration (instance URL, token env-var NAMES per §11.4.10), bridge kits, and probe scripts per §11.4.35.
